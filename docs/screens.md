# Карта экранов

> PWA, mobile-first. Все экраны кроме дашбордов/админки рассчитаны на
> вертикальный телефон или планшет. Сканер QR — полноэкранный.
>
> **Шаг 13 / Mobile clean redesign.** `/login`, `/work` и
> `/passports/[id]` переведены на новый светлый интерфейс с крупными
> карточками и мягкими синими акцентами (см.
> [`docs/ui-mobile.md`](./ui-mobile.md)). Бизнес-логика, API, auth и
> redirect-таблица не менялись.
>
> **UI Refresh (visual layer v2).** Поверх Шага 13 добавлен единый
> design-system layer и иконография на базе inline-SVG
> (`apps/web/components/icon.tsx`). Менеджерские экраны
> (`/admin/production-dashboard`, `/production-cost`, `/earnings`,
> `/admin/employees`, `/admin/operations`, `/admin/warehouses`,
> `/admin/equipment`, главная `/`) получили `page-eyebrow + page-title +
> page-subtitle`, `kpi-grid / kpi-card`, `stage-card`, `alert-stack`,
> `quick-link`, `toggle-group`, `filter-card`, `empty-state` (см.
> блок «Modern visual refresh» в `apps/web/app/globals.css`). Цеховые
> терминалы (`/qc`, `/wto`, `/packing`, `/work`, `/shopfloor`)

> заголовки и иконки primary-кнопок. Backend, API, server actions и
> redirect-таблица не менялись.

<a id="role-window-model"></a>
### 1.1. Модель «одно рабочее окно на роль»

Для производственных ролей UI работает как терминал: после
авторизации пользователь сразу попадает в **primary workspace**
своей роли, а отдельной «Главной» страницы у них нет (`/`
редиректит туда же на сервере). Менеджеры и админ продолжают
видеть многосекционный интерфейс с тайлами на `/`.

Источник истины — `apps/web/lib/rbac.ts`:

| Роль               | Primary workspace |
| ------------------ | ----------------- |
| SEAMSTRESS         | `/work` |
| CUTTER_ASSISTANT   | `/work` |
| CUTTER             | `/work` |
| IRONING            | `/wto`  |
| QC                 | `/qc`   |
| PACKING            | `/packing` |
| SHOPFLOOR_MASTER   | `/master` |
| SHOP_MANAGER       | `/`     |
| ADMIN              | `/`     |

Где это применяется:

- **Login redirect** (`apps/web/app/login/actions.ts`,
  `app/login/page.tsx`). После успешного логина или возврата
  залогиненного пользователя на `/login`: если в `?next=` нет явного
  валидного пути (или он равен `/`), редиректим в
  `getPrimaryWorkspace(role)`. Явный `?next=/orders` от
  middleware-редиректа уважаем.
- **Корневой `/`** (`apps/web/app/page.tsx`). Для рабочих ролей
  (`isWorkingRole`) делаем server-side redirect в primary workspace.
  Для менеджеров/админа рендерим прежнюю плитку action-карточек.
- **`/work` для ролей с собственным терминалом** (`apps/web/app/work/page.tsx`).
  QC, IRONING и PACKING на `/work` оказаться не должны: их primary
  workspace — это `/qc`, `/wto`, `/packing` соответственно. Если такая
  роль попадает на `/work` (старая закладка, ручной ввод url, переход
  по чужой ссылке), страница делает SSR-редирект в их собственный
  терминал ещё до загрузки `getShiftMeta` — иначе они увидели бы
  legacy-экран швеи с табами «Получить крой / Сканировать паспорт» и
  кнопкой «Завершить смену», который для их pipeline посторонний.
  Реализовано универсально через `getPrimaryWorkspace`: редиректим
  любую роль, у которой primary workspace ≠ `/work` и ≠ `/`.
- **Глобальная навигация** (`apps/web/app/layout.tsx`,
  `apps/web/components/mobile-nav.tsx`). У производственных ролей
  пункт **«Главная»** скрыт (`canSeeHome` = false), а пункт
  **«Рабочее место»** скрыт там, где `/work` уже primary
  workspace или просто не нужен (`canSeeWorkTab` = true только для
  ADMIN / SHOP_MANAGER) — иначе получалась бы дублирующая вкладка.
  У SEAMSTRESS, CUTTER_ASSISTANT, QC и IRONING (`isSingleWorkspaceRole`)
  `MobileNav` не рендерится вообще: их экран должен выглядеть как
  один сфокусированный терминал, без глобальной навигации (logout
  / завершение смены — в три-точечном меню `SeamstressActionsMenu`,
  верхний `<AppHeader>` уже скрыт на `/work*`, см. §3).

## 2. Общие экраны

### 2.1. `/login` (MVP 1.1, Шаг 13 redesign)
- Полностраничный светлый фон + центрированная карточка `auth-card`
  с brand-mark `S`, заголовком, короткой подсказкой и primary-кнопкой
  во всю ширину (`apps/web/app/login/`).
- Поля `login` и `password` (для seed-учёток это `Demo12345!`).
- Server action вызывает `POST /api/auth/login`. На успех — редирект
  на `?next=...` (или `/`), сессия живёт через cookie `sewing_session`.
- На ошибку показываем нормализованный код (`INVALID_CREDENTIALS`,
  `EMPLOYEE_INACTIVE`) в мягкой красной плашке прямо под полями.
- Маршрут публичный. Все остальные экраны защищены `middleware.ts`:
  без cookie — редирект на `/login?next=<url>`.
- В шапке после логина: ФИО + роль + кнопка «Выйти» (`POST /api/auth/logout`).
  На мобильном — нижняя `MobileNav`. Состав пунктов зависит от роли
  (см. §1.1): для менеджеров/админа — Главная / Работа / ОТК /
  Упаковка / Заказы (по матрице доступа); для QC — только ОТК; для
  PACKING — только Упаковка; для CUTTER / IRONING — пусто; у
  SEAMSTRESS и CUTTER_ASSISTANT (`isSingleWorkspaceRole`) `MobileNav`
  не рендерится вообще.
  Видимость пунктов навигации, кнопок «+ Создать заказ» и тайлов на
  главной зависит от роли — единая логика в `apps/web/lib/rbac.ts`
  (`canSeeQc` = `QC|SHOP_MANAGER|ADMIN`, `canSeePacking` = `PACKING|SHOP_MANAGER|ADMIN`,
  `canSeeOrders` = `ADMIN|SHOP_MANAGER|CUTTER_ASSISTANT` — технический
  read-доступ). Видимость пунктов меню «Заказы» и «Цех» отделена от
  технического доступа: `canSeeOrdersMenu` = `ADMIN|SHOP_MANAGER`
  (CUTTER_ASSISTANT исключён), `canSeeShopfloorMenu` показывает «Цех»
  всем, кроме `CUTTER_ASSISTANT`. **Тайл «Заказы» на главной странице
  использует ту же матрицу `canSeeOrdersMenu`** — поэтому помощник
  раскройщика не видит entry point в admin-раздел заказов вообще
  (ни в шапке, ни в mobile-nav, ни на главной), хотя технический
  доступ к `/orders/*` ему остаётся для flow «Выпустить паспорт».
  У помощника раскройщика остаётся единственная точка входа `/work`
  (упрощённый flow выпуска паспорта + shelf-placement, см. §3 ниже);
  остальные роли разделы `/qc`, `/packing`, `/orders` не видят и не
  открывают (layout `/qc`, `/packing`, `/orders` делает SSR-редирект
  на `/`, backend закрывает `403 FORBIDDEN_ROLE`).

### 2.2. `/shift`
- Кнопка «Сканировать оборудование».
- После скана — выбор операции (чипсы, отсортированные по `sortOrder`,
  отфильтрованные по `Role`).
- Кнопка «Начать смену» → `POST /api/shifts/start`.
- Если активная сессия уже есть — показываем её и кнопку «Завершить».

## 3. Экран сотрудника (`/work`) — Шаг 6 MVP, Шаг 13 redesign

Mobile-first. Для SEAMSTRESS / IRONING / CUTTER_ASSISTANT — это
основной мобильный кабинет. Реализовано: `apps/web/app/work`.

> **CUTTER_ASSISTANT — упрощённый «mobile clean» поток c обязательной
> сменой на оборудовании.** Помощник раскройщика, как и остальные
> рабочие роли (швея, ОТК, ВТО, упаковка), теперь работает строго
> в контексте активной `ShiftSession`. Это нужно для печати:
> print-job выбирает принтер по `equipmentId` активной смены
> (см. `apps/api/src/modules/printers/print-jobs.service.ts`,
> `resolvePrinter` → `SHIFT_SESSION_REQUIRED` /
> `PRINTER_NOT_CONFIGURED_FOR_EQUIPMENT`), а значит без смены
> «Выпустить паспорт» физически не доходит до отпечатанного QR.
>
> Поток на `/work` для CUTTER_ASSISTANT:
>
> 1. **Если смены нет** — рендерится `<SeamstressShiftStart>` (тот же
>    компонент, что и у швеи). Mobile-first scan-driven flow:
>    QR-код раскройного стола → выбор разрешённой операции из
>    `equipment.allowedOperationIds` (источник истины — таблица
>    `EquipmentOperation`, см. ADR-0017) → подтверждение
>    (`POST /api/shifts/start`). Никакого отдельного «scan equipment»
>    экрана для помощника не плодим.
> 2. **Если смена активна** — рендерится `<CutterAssistantWorkPanel>`
>    с двумя action-card одного визуального уровня:
>    - «Выпустить паспорт» → server-route `/work/cut-orders` (см. §3.7);
>    - «Разместить на стеллаж» → scan-driven `<ShelfPlacementPanel>`
>      (см. §3.8).
>
> Глобальный тёмный header (`<AppHeader>`) на `/work*` и на
> `/orders/:id/passports/new` для этой роли скрыт — экран начинается
> сразу с `RoleHeaderCard`. Завершение смены и logout вынесены в
> то же три-точечное меню `SeamstressActionsMenu`, что и у швеи
> (правый верхний угол). Кнопка «Завершить смену» в меню
> показывается только при активной смене.
>
> Это сознательное исключение из правила «`/orders` только
> SM/ADMIN»: backend даёт CUTTER_ASSISTANT read-доступ к
> `/api/orders[/:id][/passports]`, в UI сам admin-раздел `/orders`
> для него скрыт (включая пункты «Заказы» и «Цех» в шапке и
> mobile-nav, см. `canSeeOrdersMenu` / `canSeeShopfloorMenu`), а
> вход остаётся только из `/work`.

### 3.1. Секции экрана

1. **`<RoleHeaderCard>`** — фирменная синяя шапка-профиль (имя
   сотрудника, роль, активная операция и оборудование, индикатор
   статуса смены). Видна всегда, даже если смены ещё нет.
2. **Форма смены (если активной нет):** мягкая `scan-card` с
   двумя селектами (оборудование, операция) и крупной primary-кнопкой
   «Начать смену» → `POST /api/shifts/start { equipmentId, operationId }`.
   Для роли SEAMSTRESS список доступных операций приходит из backend:
   после выбора оборудования показываются только операции из его
   allow-листа (`equipment.allowedOperationIds` в `GET /api/shifts/meta`,
   см. ADR-0017 и `docs/api.md §3a`).    Если у выбранного станка
   нет ни одной активной операции — форма показывает явный
   error-box «Для этого оборудования нет настроенных операций.
   Обратитесь к мастеру.» вместо пустого селекта; настройка
   делается мастером на `/admin/equipment/[id]`.
3. **Панель активной смены** (`<ActiveShiftPanel>`):
   - pill-style таб «Получить крой / Сканировать паспорт» (≥ 44 px);
   - крупный input под QR (моноширинный, dashed border);
   - primary-кнопка действия (≥ 56 px);
   - результат — мягкая `result-card` (зелёная для issue, синяя для
     scan);
   - снизу — небольшая danger-кнопка «Завершить смену»
     (`POST /api/shifts/stop`).
4. **Инпут кода паспорта.** Поддерживает три формата
   (см. [ADR-0008](./adr/0008-qr-format.md)):
   - `passport:{id}` — QR;
   - `P-YYYYMMDD-NNNN` — номер паспорта;
   - голый `id`.

> До MVP 1.1 на этом экране был «пикер сотрудника» (`demo-employee-id`).
> Сейчас сотрудник определяется cookie сессии, поэтому пикер удалён.

### 3.2. «Получить крой»

- Server action `issuePassportAction`:
  1. `POST /api/passports/by-code` → `passportId`;
  2. `POST /api/passports/:id/issue { employeeId }`.
- После успеха — зелёная карточка «Крой получен» с номером паспорта,
  изделием, цветом, размером, `qtyCut`/`qtyGood`, статусом.
- Ошибки (`SHIFT_SESSION_REQUIRED`, `PASSPORT_NOT_IN_CELL`,
  `PASSPORT_ALREADY_ISSUED`, `PASSPORT_NOT_FOUND` и т. п.) — в красной
  плашке `error-box` с кодом.

### 3.3. «Сканировать паспорт»

- Server action `scanPassportAction`: аналогично, но вызывает
  `POST /api/passports/:id/scan`.
- После успеха — синяя карточка «Паспорт принят на операцию»; паспорт
  перешёл на `session.operationId`.
- История последних сканов — **за рамками Шага 6** (появится вместе с
  экраном «Цех»).

### 3.4. Блок «Текущий крой» (для SEAMSTRESS, Шаг 6.1)

После того как швея «Приняла» крой в модалке, на /work всегда виден
устойчивый блок `CurrentWorkCard` — рабочий контекст, а не только
короткий success-state.

- Источник данных — `GET /api/shifts/current-work` (см. `docs/api.md §3a`):
  backend сам режет по сессии и отдаёт паспорта, у которых
  `currentEmployeeId = me AND status = IN_PROGRESS`.
- Карточка показывает: номер паспорта (ссылка на `/passports/:id`),
  изделие/цвет, размер, количество (`qtyGood / qtyCut шт`), номер
  рулона, текущую операцию паспорта и время последнего приёма
  (`acceptedAt` — последнее `ISSUED_TO_EMPLOYEE` события самого
  сотрудника, см. `docs/events.md`).
- Если активных паспортов несколько — вертикальный список карточек,
  самая свежая сверху (`updatedAt desc`).
- Если активного кроя нет — мягкий empty-state «Сейчас у вас нет
  кроя в работе».
- Главная primary-кнопка ниже меняется на «Взять следующий крой»,
  если хотя бы один паспорт уже в работе.

Паспорт автоматически уходит из этого списка, когда:
- другой сотрудник скан-нул паспорт на следующей операции
  (`Passport.currentEmployeeId` перезаписывается, см. F4);
- упаковщик закрыл паспорт в коробке (`status → PACKED`).

Никаких дополнительных «возвратов кроя» делать не нужно — блок
полностью derived от состояния паспортов в БД.

### 3.5. Обновление кэша

После каждого успешного действия web делает `revalidatePath('/work')`,
`revalidatePath('/passports/:id')` и `revalidatePath('/orders/:orderId')`,
чтобы карточка заказа/паспорта тут же увидела новое состояние.

`SeamstressActivePanel` дополнительно зовёт `router.refresh()` после
`acceptPassportForIssueAction`, чтобы серверные props
(`currentWork`) перевыполнились и карточка «Текущий крой» сразу
показала только что принятый паспорт.

### 3.6. Тактильное и звуковое подтверждение

Чтобы швея чётко чувствовала рабочий цикл (скан → принять → следующий)
без необходимости вглядываться в экран, в seamstress flow на `/work`
встроены два коротких feedback-сигнала. Реализация — `apps/web/app/work/feedback.ts`,
оба сигнала best-effort (см. ниже).

- **Вибрация после успешного скана QR паспорта.** В момент, когда
  `Html5Qrcode` распознал содержимое и принял `decodedText`, мы
  синхронно дёргаем `navigator.vibrate(40)`. Происходит ДО `instance.stop()`
  и до `onScan(...)`, чтобы швея получила подтверждение «поймали»
  максимально близко к самому скану и до открытия модалки сверки.
  Если устройство/браузер не поддерживает Vibration API
  (`navigator.vibrate` не определён) — молча пропускаем, ничего не
  падает.
- **Звук «крой принят» после backend SUCCESS.** В `handleAccept`
  (`SeamstressActivePanel`) звук проигрывается ровно один раз — на
  ветке успеха, после early-return по `res.error`. Никаких звуков
  на: открытии модалки, lookup-ветке, отмене, ошибке backend. Файл —
  `/sounds/cut-accepted.wav` (~180 мс, мягкий «дзынь» E5→A5,
  WAV сгенерирован детерминированно, без внешних кодеков). `play()`
  вызывается строго в контексте user gesture (клик «Принять»),
  поэтому autoplay-политика браузеров его не блокирует; любой отказ
  (rejected promise, отсутствие звука у пользователя, 404 ассета)
  глотается, success-state показывается всё равно.

Тесты — `tests/smoke/seamstress-feedback.smoke.test.ts` (порядок
вызовов в исходниках, fail-soft без `navigator.vibrate`/`Audio`,
наличие WAV-ассета).

### 3.7. `/work/cut-orders` — упрощённый выбор заказа (CUTTER_ASSISTANT)

Серверный route специально для помощника раскройщика. Открывается с
`/work` по нажатию primary-кнопки «Выпустить паспорт».

Поведение:

- **Один заказ в `IN_PRODUCTION`** → server-side `redirect()` сразу
  на `/orders/:id/passports/new`. Помощник вообще не видит экран
  выбора — это и есть «один тап».
- **Несколько заказов** → короткий вертикальный список карточек.
  Каждая карточка содержит только то, без чего нельзя выбрать:
  название изделия (`productName`) крупно + номер заказа и цвет
  меньшим шрифтом. Тап = переход на `/orders/:id/passports/new`.
  Никаких таблиц, фильтров, статусов и admin-кнопок.
- **Ноль заказов** → empty state «Нет заказов на раскрое» с
  пояснением и кнопкой «Назад».

Источник истины — backend `GET /api/orders?status=IN_PRODUCTION`
(уже разрешён `CUTTER_ASSISTANT`, см. `docs/api.md §4`). Никаких
новых endpoint-ов не добавляли.

Верхнее меню на `/work/cut-orders` тоже скрыто (по префиксу `/work`
в `AppHeader`); навигация — компактный `←` вверху страницы и
карточки-ссылки.

### 3.8. Shelf-placement flow «Разместить крой на стеллаж» (CUTTER_ASSISTANT)

Второе крупное действие на `/work` для помощника раскройщика. Это
scan-driven session-режим без перехода на отдельный route — вся
state-машина живёт внутри `<ShelfPlacementPanel>`
(`apps/web/app/work/shelf-placement-panel.tsx`).

Состояния клиентской state-машины:

```
idle ──tap──▶ scanning-cell ──QR──▶ confirm-cell ──confirm──▶ placing
                  │                       │                      │
                  └─cancel/close──────────┴──cancel──┐           │
                                                     ▼           ▼
                                                    idle ◀──"Готово"
```

Поведение по шагам:

1. **idle.** На `/work` показаны две action-card. Тап «Разместить на
   стеллаж» переключает state в `scanning-cell`.
2. **scanning-cell.** Используется тот же `<QrScannerModal>`, что в
   seamstress-flow (камера, fail-soft без HTTPS). После успешного
   распознавания QR срабатывает `triggerScanHaptic()` (вибрация
   ~40 мс), web вызывает server action `lookupCellByCodeAction(code)` →
   `POST /api/cells/by-code`. Backend = источник истины: он
   проверяет `active`, кидает `CELL_NOT_FOUND` / `CELL_INACTIVE` при
   проблемах, и эти ошибки выводятся в `error-box` на возврате в
   `idle` (помощник может попробовать снова).
3. **confirm-cell.** Confirm-модалка по образцу
   `<PassportConfirmModal>`: крупный код ячейки, QR-полезная нагрузка,
   срез содержимого `(sizeCode × quantity)`. Кнопки «Отмена» и
   «Подтвердить ячейку». Отмена возвращает в `idle`.
4. **placing.** Заголовок панели меняется на «Ячейка `A-01`» и
   primary-кнопку «Сканировать паспорт». Каждый успешный скан паспорта
   вызывает `placePassportToCellAction(cellId, cellCode, passportCode)`
   → `POST /api/passports/by-code` + `POST /api/passports/:id/place`
   с уже подтверждённым `cellId`. На SUCCESS играем
   `playCutAcceptedSound()` + вибрация и добавляем строку в ленту
   «Размещено» (последние 5, новые сверху). На ошибке — стандартный
   `error-box` с `requestId`, **session не завершается** — помощник
   может сразу пересканировать паспорт или взять следующий.
5. Кнопка **«Готово»** возвращает в `idle` и схлопывает session.

Что важно:

- никаких новых бизнес-правил — переиспользуем `passports.place`
  (`@Roles('CUTTER','CUTTER_ASSISTANT','SHOP_MANAGER')`), `findByCode`
  и новый `findCellByCode` в `PassportsService`;
- `Passport.currentOperationId` не меняется (ячейка — хранение, а не
  этап, см. F3);
- ошибка одного паспорта не разрывает session: подтверждённую
  ячейку повторно сканировать не нужно;
- никаких таблиц/фильтров/dropdown-ов — только три экрана модалок
  и одна action-card в session-режиме.

## 5. ОТК (`/qc`) — scan-driven role-terminal

Mobile-first, оптимизировано под планшет/телефон. По модели «одно
рабочее окно на роль» (см. §1) `/qc` для роли `QC` — это единственный
сфокусированный терминал: AppHeader и MobileNav на нём скрыты
(см. `apps/web/components/app-header.tsx`, `isSingleWorkspaceRole`
в `apps/web/lib/rbac.ts`), а в углу — компактная кнопка «Выйти».
Архитектура повторяет `/work` для швеи (см.
`apps/web/app/work/seamstress-active-panel.tsx`).

> **Доступ.** Раздел доступен `QC`, `SHOP_MANAGER`, `ADMIN`. Layout
> `/qc` редиректит остальных на `/`, backend закрывает
> `/api/qc/*` и `/api/defect-types` через `@Roles('QC','SHOP_MANAGER')`.

### 5.1. `/qc` (рабочий терминал ОТК)

Единственный экран раздела для роли QC. Никаких списков, поисков и
переходов между страницами — открыл смену, отсканировал, действие,
готов к следующему скану.

Состояния (выбираются на SSR, см. `apps/web/app/qc/page.tsx` и
`apps/web/app/qc/qc-terminal.tsx`; страница подтягивает
`getShiftMeta()` + `getCurrentShift()` ровно как
`apps/web/app/packing/page.tsx` для упаковщика):

- **Смена не начата** (`GET /shifts/current` отдал `null` или
  `active=false`). Терминал рендерит reuse-форму
  `SeamstressShiftStart` (та же, что у швеи и упаковщика):
  большая primary-кнопка «Начать смену» открывает камеру и ждёт
  QR оборудования. После скана QR рабочего места ОТК (например,
  `qc-station-01`, см. `prisma/seed.ts`) показывает оборудование +
  список разрешённых операций (`EquipmentOperation`, ADR-0017) —
  для qc-станций это allow-лист из одной операции `QC`. Подтверждение
  вызывает `POST /shifts/start`. Ручной ввод кода оборудования
  сохранён как secondary-action (fallback).
  В `RoleHeaderCard` статус — «Смена не начата — отсканируйте QR
  рабочего места ОТК».
- **Смена активна, но категория операции не `QC`** (например, ОТК
  случайно открыл смену не на том станке). Показываем банер
  «Смена не на ОТК» с подсказкой завершить смену через меню в
  правом верхнем углу. Скан-флоу не показываем сознательно: backend
  всё равно подсадит паспорт в чужой `currentOperationId` и сломает
  shopfloor-проекцию (см. `flows.md §F11` и `F5`).
- **Смена активна, категория `QC`** — штатный сценарий ниже.

Структура штатного сценария (см. `apps/web/app/qc/qc-terminal.tsx`,
внутренний `QcScanTerminal`):

1. **`RoleHeaderCard`** — ФИО сотрудника, роль (ОТК), поля «Операция»
   и «Оборудование» из активной смены, статус «Смена с HH:MM».
2. **Три-точечное меню `SeamstressActionsMenu`** в правом верхнем
   углу (как у швеи/упаковщика): «Завершить смену» (видна только при
   активной смене, с явным `confirm()`) + «Выйти». Глобальный
   `<AppHeader>` на `/qc` для роли QC скрыт
   (`isSingleWorkspaceRole(QC)`), поэтому это единственная точка
   logout/stop-shift.
3. **Большая кнопка «Сканировать паспорт»** — открывает тот же
   `QrScannerModal`, что и швея (`apps/web/app/work/qr-scanner-modal.tsx`).
   Поддерживается резерв «Ввести код вручную» (номер `P-…` или голый id).
3. После успешного скана под кнопкой раскрывается **карточка
   паспорта** (`apps/web/app/qc/qc-work-card.tsx`) — пока ОТК ещё
   не подтвердил «Проверка выполнена» (`qcCompletedAt = null`):
   - meta: номер, изделие, цвет, размер, заказ, рулон, текущая операция;
   - три цифры **Раскроено / Брак / Годных**;
   - блок «Зафиксировать брак» (форма к `POST /qc/passports/:id/defects`),
     прячется при `canRecordDefect = false`;
   - кнопка **«Проверка выполнена»** (`POST /qc/passports/:id/complete`),
     прячется при `canCompleteQc = false` (терминальные статусы);
   - «Сканировать другой паспорт» — очищает карточку и сразу
     открывает сканер;
   - «Обновить карточку» — пере-fetch `getQcPassport`.
4. После успешного «Проверка выполнена» большая карточка **сворачивается**
   в одну компактную строку `QcCompletedRow`
   (`apps/web/app/qc/qc-completed-row.tsx`):
   - содержит только номер паспорта, размер, годное количество и
     бейдж «Проверено ОТК · ⟨время⟩»;
   - никаких action-кнопок («брак»/«проверка выполнена») — это
     чистый view-напоминание;
   - терминал каждые ~10 секунд (`QC_REMOVED_POLL_INTERVAL_MS`)
     перечитывает паспорт через `refreshQcPassportAction`. Как только
     backend возвращает `removedFromQc = true` (см.
     `QcService.loadDetail`, `flows.md §F5`) — то есть паспорт ушёл
     на следующую операцию (свежий `OPERATION_SCAN`) или попал в
     терминальный статус (`PACKED`/`CANCELLED`) — строка **исчезает
     из окна ОТК совсем**.
   - Если ОТК пытается повторно отсканировать тот же ушедший
     паспорт, `lookupQcPassportAction` тоже отвергает его (показываем
     info «Паспорт ушёл на следующую операцию.»), не открывая снова
     рабочую карточку.

UX-фидбек:

- успешный скан → вибрация (`navigator.vibrate`) + распознавание;
- успешная фиксация брака → `playCutAcceptedSound`;
- успешное «Проверка выполнена» → `playOperationCompletedSound`;
- ошибки и `requestId` показываем явным `error-box` под кнопкой
  скана.

> Менеджеры/админ видят `/qc` так же — у них экран дополнен общей
> навигацией (`AppHeader`/`MobileNav`), потому что они не попадают
> под `isSingleWorkspaceRole`.

### 5.2. `/qc/passports/[id]` (карточка ОТК для менеджеров/админа)

- Шапка: номер паспорта + статус-бейдж, ссылка на заказ, дата
  создания/обновления, кнопки «← К списку ОТК» и «Открыть карточку
  паспорта».
- Карточка с meta-информацией: изделие, цвет, размер, рулон,
  дата кроя, текущая операция, текущий сотрудник.
- Большой блок с тремя цифрами: **Раскроено** / **Брак** / **Годных**.
- Форма «Зафиксировать брак»:
  - выбор вида брака из `GET /api/defect-types`;
  - количество (max = `remainingForDefect`);
  - комментарий (опционально, ≤ 500 символов);
  - кнопка `POST /api/qc/passports/:id/defects`.
  Когда `canRecordDefect = false` (статус не `IN_PROGRESS` или весь
  крой уже отмечен браком), форма заменяется заглушкой.
- Таблица «История дефектов»: дата · вид · кол-во · комментарий · кто.

### 5.3. Интеграция в `/passports/[id]`

В карточке любого паспорта появляется блок «Качество (ОТК)»:

- три цифры (Раскроено / Брак / Годных);
- кнопка «Открыть в ОТК» (если `status = IN_PROGRESS`);
- список последних 5 записей дефектов со ссылкой «Показать все в ОТК».

### За рамками текущего MVP ОТК

- Отдельная вкладка «Ожидают» (`currentOperationId = QC`) — на MVP
  фильтр не нужен, ОТК работает со всеми «живыми» паспортами.
- Кнопка «Передать на ВТО» — переход выполняется обычным
  `OPERATION_SCAN` (см. F4), но уже из терминала ВТО (`/wto`,
  `acceptOnWtoAction`). Отдельного действия «передать» у ОТК нет.
  Действие «Проверка выполнена» (`QC_PASSED`) намеренно не двигает
  паспорт по pipeline — это аудит-маркер, а не движение по этапам
  (см. `flows.md §F5`). Без `QC_PASSED` ВТО не сможет принять
  паспорт — backend возвращает 409 `PASSPORT_NOT_QC_PASSED` (см. §5a).
- Расследование виновной операции, аналитика по причинам брака,
  возврат брака в производство.

     (`PACKED`/`CANCELLED`) — строка **исчезает из окна ВТО совсем**.

UX-фидбек повторяет `/qc`: вибрация на скан, sound-эффект на
«Завершить ВТО», явный `error-box` с `requestId` для бизнес-ошибок.

> Менеджеры/админ видят `/wto` так же — у них экран дополнен общей
> навигацией (`AppHeader`/`MobileNav`).

### 5a.2. Что НЕ делает терминал ВТО

- Не фиксирует брак — он считается за ОТК (см. §5).
- Не имеет своего листинга паспортов: менеджеры/админ смотрят прогресс
  по ВТО на `/shopfloor` (колонки `ВТО` и `ВТО завершено`,
  см. ADR-0013 §«WTO_DONE bucket»).
- Не двигает `Passport.status` — `WTO_PASSED` это аудит-маркер,
  как и `QC_PASSED` (см. `flows.md §F6`).

## 6. Упаковка (`/packing`) — scan-driven role-terminal

Сценарий упаковщика — единое scan-driven рабочее окно по той же
модели, что `/qc` и `/wto`. Реализовано как Шаг 8 MVP + редизайн
терминала под scan-driven UX (см. ADR-0011 и `flows.md §F7`).

> **Доступ.** Раздел доступен `PACKING`, `SHOP_MANAGER`, `ADMIN`.
> Layout `/packing` редиректит остальных на `/`, backend закрывает
> `/api/packing/boxes/*` через `@Roles('PACKING','SHOP_MANAGER')`.
> Исключение — публичные `GET /api/packing/boxes/:id/qr` и `/label`:
> они помечены `@Public()`, чтобы оставаться доступными для печати
> этикетки и сканера на физическом устройстве.

> Layout/page ветвится по роли: для `PACKING` `/packing`
> рендерит `<PackingTerminal />` (см. ниже §6.1), для
> `SHOP_MANAGER`/`ADMIN` — управленческий список (см. §6.3).
> `<AppHeader>` для роли `PACKING` на `/packing` тоже скрыт
> (см. `components/app-header.tsx`, флаг `hideForPacking`).

### 6.1. `/packing` (рабочий терминал упаковщика)

Структура (см. `apps/web/app/packing/packing-terminal.tsx`):

1. `RoleHeaderCard` — имя сотрудника, бейдж «Упаковка», поля
   активной смены (операция/оборудование/время старта). Аналогично
   `/qc`, `/wto`, `/work` (швея).
2. Три-точечное меню справа сверху (`SeamstressActionsMenu`) —
   «Завершить смену» (если активна) + «Выйти». Это единый паттерн
   для mobile-clean ролей.
3. Состояние терминала зависит от смены:
   - **Нет активной смены** → встроенный `<SeamstressShiftStart />`
     (тот же scan-only flow «QR оборудования → выбор операции», что
     у швеи на `/work`). Backend требует операцию категории
     `PACKING`, иначе мутации возвращают 409 `PACKING_SHIFT_REQUIRED`.
   - **Активна смена не на упаковке** → карточка «Смена не на
     упаковке» с указанием текущей операции и инструкцией завершить
     смену через меню.
   - **Активна смена на упаковке без открытой коробки** → primary
     scan-card «Новая коробка» с большой кнопкой «Создать коробку»
     и вторичной формой «Указать другой лимит» (1…100). По нажатию
     — `createBoxTerminalAction` (`POST /api/packing/boxes`) и
     переход к stage 2.
   - **Активна коробка** → `qc-card`-стиль карточка коробки:
     номер, статус-бейдж, сводка партии (изделие/цвет/размер
     по `box.summary`), заполнение `totalQty/maxQty` + %.
4. На карточке открытой коробки:
   - primary-кнопка «Сканировать паспорт» → `<QrScannerModal />`
     (та же камера, что у швеи и ОТК) → `scanPassportToBoxAction`
     (`POST /api/packing/boxes/:id/add-passport`). Скан вибрирует,
     играет «дзынь» (`playCutAcceptedSound`) и обновляет список;
     последний добавленный паспорт получает бейдж «✓ только что».
   - вторичная форма «Ввести код вручную» (fallback для слабой
     камеры), отдельной кнопкой;
   - сворачивающаяся секция «Упаковано: N паспорт(ов)» с
     `<details>`: номер паспорта, qty, заказ, время добавления;
   - крупная success-кнопка «Закрыть коробку (N шт.)» → 
     `closeBoxTerminalAction` (`POST /api/packing/boxes/:id/close`).
     Это финальный шаг цепочки — backend в той же транзакции
     апрувит все pending-начисления цепочки (см. `flows.md §F7`,
     ADR-0005). По успеху играет «арпеджио»
     (`playOperationCompletedSound`) и возвращает терминал к stage
     «Создать коробку»;
   - `Свернуть карточку` (вернуться к stage «Создать коробку», не
     закрывая коробку — id коробки запоминается в localStorage,
     чтобы при перезагрузке вкладки восстановить state) и
     `Обновить карточку` (re-fetch без побочных эффектов).

UX-фидбек повторяет `/qc` и `/wto`: вибрация на скан паспорта,
sound-эффекты на «принят»/«коробка закрыта», бейдж «только что»
для последнего добавления.

### 6.2. Восстановление активной коробки

Id текущей открытой коробки сохраняется в `localStorage` под ключом
`sewing.packing.activeBoxId`. При повторном входе на `/packing`
терминал попробует подгрузить коробку через `getActiveBoxAction`
(`GET /api/packing/boxes/:id`). Если коробка уже закрыта или id
невалиден — storage чистится и показывается стандартный stage
«Создать коробку». Это удобство для цеха: вкладка может «уснуть»,
а коробка остаётся открытой в БД, и упаковщик возвращается ровно к
тому же экрану.

### 6.3. `/packing` (управленческий вид для `SHOP_MANAGER` / `ADMIN`)

- Header «Упаковка» + ремарка «Управленческий вид: список коробок
  и быстрый доступ к карточкам».
- Фильтр статуса: `OPEN` / `CLOSED` / все. Применяется submit-кнопкой
  (`?status=...`).
- Таблица `Box[]` из `GET /api/packing/boxes?status=...`:
  `номер · статус · totalQty/maxQty · кол-во паспортов · создал · создана/закрыта`.
- Клик по номеру → `/packing/boxes/:id`.
- Форма «Новая коробка» (`createBoxAction`) — POST `/api/packing/boxes`,
  по успеху redirect на карточку. Disabled, если у пользователя нет
  активной смены упаковщика.

### 6.4. `/packing/boxes/:id` (карточка коробки)

Управленческая карточка для глубокого debug/мониторинга. Скан-driven
терминал упаковщика на нее обычно не заходит, но она остаётся
доступной по прямой ссылке (например, из `/passports/:id`).

- Шапка: номер, QR (`/api/packing/boxes/:id/qr`), статус (`OPEN`/`CLOSED`),
  заполненность `totalQty/maxQty`, автор, даты создания/закрытия,
  комментарий, кнопка «Этикетка» → `box.labelUrl`
  (`GET /api/packing/boxes/:id/label`, HTML).
- Сводка партии (если есть `BoxItem[]`): изделие, цвет, размер
  (homogeneity, ADR-0011 §3).
- Таблица `BoxItem[]`: паспорт, заказ, изделие, цвет, размер, qty
  (= `passport.qtyGood`), время добавления. Клик по паспорту →
  `/passports/:id`.
- Форма «Сканировать паспорт» (`addPassportToBoxAction`) — поле под
  QR-сканер, отправляется на `POST /api/packing/boxes/:id/add-passport`
  (см. F7). Disabled для закрытой коробки или без `PACKING`-смены.
- Форма «Закрыть коробку» (`closeBoxAction`) → `POST /api/packing/boxes/:id/close`.
  Disabled, если коробка пустая или уже закрыта. По факту вызова
  backend идемпотентно апрувит pending-начисления цепочки
  (см. `flows.md §F7`, ADR-0005).
- На карточке паспорта (`/passports/:id`) показывается ссылка на
  коробку, если паспорт уже упакован.

## 7. Заказы (`/orders`) — Шаг 4 MVP

Три экрана: список, создание, карточка. Desktop-first, но работает и на
планшете. Список паспортов из карточки заказа на MVP **не показываем** —
это управленческий экран по размерам (ТЗ §17).

> **Доступ.** Раздел открыт `ADMIN` и `SHOP_MANAGER`. `CUTTER_ASSISTANT`
> имеет read-доступ (список, карточка, паспорта заказа) — для запуска
> «Выпустить паспорт» с `/work`. Кнопки «Создать заказ»,
> «Редактировать», `/orders/[id]/edit`, `start`/`complete`/`cancel`
> (`<OrderActions>`) ему НЕ показываются и закрыты на backend
> (`@Roles('SHOP_MANAGER')`). Layout `/orders` редиректит на `/`
> всех остальных, `/orders/new` и `/orders/[id]/edit` — на `/orders`
> и `/orders/:id` соответственно для не-менеджеров.

### 7.1. `/orders` — список

- Заголовок «Заказы» + кнопка «Создать заказ» (только `ADMIN`/`SM`).
- Тулбар: поиск по номеру, фильтр по статусу, сортировка
  (`createdAt_desc` / `createdAt_asc` / `orderDate_desc` / `orderDate_asc`).
- Таблица: `номер · дата · изделие · цвет · план, шт · статус ·
  комментарий (сокр.) · создан`.
- Клик по номеру → `/orders/:id`.

### 7.2. `/orders/new` — создание

Форма (`NewOrderForm`), отправляется через server action `createOrderAction`:

- **Дата заказа** (date, по умолчанию сегодня).
- **Изделие** (select из `GET /api/products`).
- **Цвет** (text; по умолчанию подставляется `Product.color`, можно
  перезаписать).
- **Комментарий** (textarea).
- **Блок размеров**: сетка из всех размеров справочника в бизнес-порядке
  (`sortOrder`) — рядом с каждым поле `qty`. Пустые поля игнорируются,
  в DTO уходят только `qty > 0`.
- **Шаблон маршрута** (select из `GET /api/routes?isActive=true`,
  опционален). Пустая опция — «Без шаблона». Блок целиком скрыт,
  если активных шаблонов нет.
- **Техкарта** (select из `GET /api/tech-cards?isActive=true`,
  опционален; MVP техкарт, ADR-0022). Пустая опция — «Без техкарты».
  Блок целиком скрыт, если активных техкарт нет. UX повторяет
  «Шаблон маршрута», без preview материалов в форме.

После успеха — redirect на `/orders/:id` и `revalidatePath('/orders')`.

### 7.3. `/orders/:id` — карточка (управленческий dashboard)

**Шапка:** номер, статус, дата, изделие, цвет, срок, комментарий,
метки `createdAt / updatedAt`.

**Действия (`OrderActions`):**

- `DRAFT` → «Редактировать» (`/orders/:id/edit`), «Запустить в
  производство» (`POST /api/orders/:id/start`), «Отменить»
  (`POST /api/orders/:id/cancel`).
- `IN_PRODUCTION` → «Завершить» (`POST /api/orders/:id/complete`),
  «Отменить».
- `DONE` / `CANCELLED` → только просмотр.

**Блок «Маршрут производства».** Компактная карточка между meta-данными
заказа и `OrderActions`. Источник истины — snapshot
`order.routeSteps` (`OrderRouteStep` на заказе), а **не** живой
`RouteTemplate`: правка шаблона после запуска уже не меняет того, что
видит карточка. Read-only представление:

- если `routeSteps.length > 0` — нумерованный список шагов в порядке
  `index ASC` вида «`Оверлок 1` (`SEW_OVERLOCK_1`)»; нумерация ol
  совпадает с `index + 1`;
- если `routeSteps` пуст — нейтральный empty-state «Маршрут для заказа
  не зафиксирован» (заказ ещё не запущен или запущен без шаблона).

В этой секции нет edit-контролов, drag/drop, timeline и прогресса
паспортов — это чисто план маршрута заказа. Прогресс по конкретному
паспорту/смене подсказывают `/work` и `/api/passports/by-code`
(см. §17 в `docs/api.md`).

**Блок «Материалы» (MVP техкарт, ADR-0022).** Read-only карточка
рядом с «Маршрутом производства». Источник истины —
`order.materialRequirements` (`OrderMaterialRequirement[]`), **не**
live-`TechCardTemplate`. Сортировка по `sortOrder ASC`.

- если `materialRequirements.length > 0` — компактный список строк:
  `name` крупно, под ним мета — `totalQty unit`, опционально вторая
  мета-строка «Норма: `qtyPerUnit unit / 1 шт» и `note` (если есть);
- если массив пуст — спокойный empty-state «Материалы для заказа не
  зафиксированы». Этот же текст показываем и в DRAFT (snapshot ещё
  не создан), и в `IN_PRODUCTION` без `techCardId` — это нормальное
  состояние, не ошибка.

Никаких чек-боксов «выдано / получено / отгружено», никакого assign
vendor, никакого inline-edit — это план потребностей.

**Блок «Внешние потребности» (MVP техкарт, ADR-0022).** Зеркальная
карточка с `order.outsourceRequirements`. Те же правила, плюс:

- если `totalQty != null && unit != null` — показываем
  `totalQty unit`; иначе строка просто без количества (типичный
  кейс «подряд за партию», где `qtyPerUnit` в шаблоне не задан);
- если `vendorName != null` — мета-строка «Подрядчик: `vendorName`»;
- empty-state: «Внешние потребности для заказа не зафиксированы».

**Композитный display-статус (MVP-2 + MVP-3 техкарт, ADR-0022).**
Под основной строкой показывается мета-подпись `displayStatusLabel`
из derived-поля `displayStatus` (см. `api.md §«orders»`):

- `RECEIVED` → зелёная подпись «Получено» + строка «Получено: dd.mm.yyyy hh:mm»
  (если есть `receivedAt`);
- `ORDERED` → янтарная подпись «Заказано» + строка «Отмечено: dd.mm.yyyy hh:mm»
  (если есть `orderedAt`);
- `READY_TO_ORDER` (только для `CUT_READY` + `isReadyToOrder = true`) →
  зелёная подпись «Готово к заказу»;
- `PLANNED` + `triggerType = CUT_READY` → янтарная «Ожидает размещения кроя»;
- `PLANNED` + `triggerType = MANUAL` → подпись не рисуется
  (`displayStatusLabel = null`, UI остаётся нейтральным).

Если в заказе хотя бы одна `CUT_READY`-строка ещё не готова, над
списком показывается единственная общая заметка «Часть внешних
потребностей станет доступна после размещения кроя в ячейки».

**Action-кнопки «Отметить как заказано / Отметить как получено»
(MVP-3 техкарт, ADR-0022 §«Manual execution status»).** Под строкой
рендерится 0–1 кнопка (минимум визуального шума, никаких dropdown/
select, никаких inline-edit полей, никакого vendor-edit):

- кнопка **«Отметить как заказано»** (`PLANNED → ORDERED`):
  - `triggerType = MANUAL` → доступна сразу из `PLANNED`;
  - `triggerType = CUT_READY` → доступна только когда
    `isReadyToOrder = true` (т.е. `displayStatus = READY_TO_ORDER`);
    пока крой не размещён, кнопка скрыта (UI guard) и backend
    дополнительно даёт `409 OUTSOURCE_NOT_READY_TO_ORDER` (защита
    от прямого вызова API).
- кнопка **«Отметить как получено»** (`ORDERED → RECEIVED`):
  доступна, когда `displayStatus = ORDERED`.
- `displayStatus = RECEIVED` → кнопок нет, статус терминальный
  (отката через UI нет).

Кнопки видят только `SHOP_MANAGER` и `ADMIN` (page-level RBAC).
Каждая кнопка перед action-ом просит подтверждение через
`window.confirm` — переход операционно значимый. После успеха
выполняется `revalidatePath('/orders/[id]')`.

Это **не** закупочный документ: vendor master, purchase orders,
счета, оплаты и складской приход вне scope (см. ADR-0022).
Карточка остаётся компактной операционной плашкой, а не ERP-формой.

Оба блока используют существующие `card`/`meta` стили, без нового
дизайна. См. `apps/web/app/orders/[id]/page.tsx` —
`MaterialsSnapshotCard` и `OutsourceSnapshotCard`.

**Summary cards** по полям `OrderSummary`:
`План всего · Раскроено · В пошиве · На ОТК · На ВТО · На упаковке ·
Выпущено · Брак · Отклонение (крой − план)`.

**Таблица по размерам** (`OrderSizeBreakdownRow[]`), сортировка по
`sortOrder`:
`Размер · План · Раскроено · В пошиве · ОТК · ВТО · Упаковка · Выпущено ·
Брак · Остаток · Δ`.

> На Шаге 5 заполнен `qtyCutFact` / `qtyCutFactTotal` — берётся из
> `Σ Passport.qtyCut`. Остальные факт-поля пока = 0 (Шаги 6–8 подключат
> их к тем же ячейкам без изменения экранов).

**Блок «Паспорта» (Шаг 5).** Сразу под таблицей по размерам:

- кнопка «Выпустить паспорт» → `/orders/[id]/passports/new` (доступна
  только когда `order.status = IN_PRODUCTION`; в остальных статусах
  кнопка задисейблена с подсказкой);
- компактная таблица последних паспортов: номер · размер · qtyCut ·
  рулон · ячейка · статус · дата кроя. Клик по строке → `/passports/[id]`.

**Блок «Закрытие раскроя по размерам» (ADR-0018).** Показывается
`SHOP_MANAGER`, `CUTTER_ASSISTANT` и `ADMIN`, если по заказу есть
хотя бы одна `REQUESTED` или `APPROVED` заявка
(`GET /api/cutting-close-requests?orderId=...`). Внутри:

- список pending заявок с размером, планом/фактом/остатком, причиной
  и быстрой ссылкой «открыть паспорт →» (используется первый паспорт
  той же размерной строки);
- список уже подтверждённых закрытий с заметкой мастера.

Решает мастер на карточке паспорта (см. §7.6). Баннер на `/orders/:id`
нужен, чтобы менеджер не искал заявки вручную.

**Блок «Очередь выдачи кроя» (`OrderCutIssueRule`).** Карточка живёт
прямо в `/orders/:id` (legacy) и во вкладке `?tab=plan` admin-карточки
`/admin/orders/:id`. Источник — `OrderCutIssueRulesCard`
(`apps/web/components/orders/order-cut-issue-rules-card.tsx`),
данные — `GET /api/orders/:id/cut-issue-rules`. Сверху —
status-badge (`Выключена` / `Активна` / `Выполнена`) и пояснение
«Пока очередь активна, швея может получить только паспорта размеров
из списка». Дальше — таблица строк
`Размер | Нужно | Выдано | Осталось | Прогресс | Активна` (с
inline progress-bar по `progressPct`).

Менеджерская тройка (`SHOP_MANAGER` / `SHOPFLOOR_MASTER` /
`ADMIN`) видит редактируемую форму ниже: select «добавить размер»
(только из `OrderItem.size` заказа), inline `requiredQty` с
валидациями «не больше плана» / «не ниже уже выданного», кнопки
«Сохранить очередь» и «Отключить очередь». Остальные авторизованные
роли видят блок read-only — нужно цеху для диагностики «почему
сейчас не выдаётся крой». Сообщение для швеи на `/work` приходит из
backend без UI-префикса (см.
`apps/web/app/work/actions.ts::RAW_API_ERROR_CODES`,
`ORDER_CUT_ISSUE_RULE_VIOLATION`): «Сначала нужно выдать: S —
осталось 20 шт, M — осталось 10 шт, 4XL — осталось 50 шт».

### 7.5. `/orders/:id/passports/new` — выпуск паспорта (Шаг 5)

Доступна, если `order.status = IN_PRODUCTION` (иначе показываем баннер
«Запустите заказ в производство»). Форма (`NewPassportForm`,
`createPassportAction`):

- **Размер** — select только из `OrderItem` заказа; для каждого размера в
  лейбле показано «остаток `N` шт». Размеры с остатком `0` задисейблены.
- **Дата кроя** — date, по умолчанию сегодня.
- **Количество** — number, `min=1`, `max = qtyPlan − Σ выпущенного по
  размеру`.
- **Номер рулона** — text, обязательно.
- **Раскройщик** (PHASE 2 STEP 3) — select из активных
  `Employee.role = CUTTER`, обязателен для **не-CUTTER** ролей
  (`CUTTER_ASSISTANT` / `SHOP_MANAGER` / `ADMIN`). Для creator с
  ролью `CUTTER` поле скрыто — backend подставит самого creator
  (`PassportsService.create::resolveCutter`, см. `docs/api.md §24a
  «Cutter attribution»`). По умолчанию выбран первый активный
  CUTTER. Если активных раскройщиков нет — показываем красную
  плашку со ссылкой на `/admin/employees`, без неё backend
  отвергнет создание паспорта (`CUTTER_REQUIRED`). Возможные
  бизнес-ошибки backend: `CUTTER_REQUIRED` (поле не заполнено),
  `CUTTER_NOT_FOUND` (id не существует или не CUTTER),
  `CUTTER_INACTIVE` (CUTTER c `active = false`). Старого fallback-а
  по seed-логину `cutter` нет — это сознательный регресс-стоп
  (см. JSDoc `PassportsService.create`).

Изделие и цвет — readonly из заказа. После успеха redirect на
`/passports/[id]` + `revalidatePath('/orders/[id]')` — **только
для `SHOP_MANAGER`/`ADMIN`/`CUTTER`**. Для `CUTTER_ASSISTANT` см.
блок «Компактный post-create блок для помощника раскройщика»
ниже.

**Компактный post-create блок для помощника раскройщика
(`CUTTER_ASSISTANT`).** Серийный оперативный выпуск идёт прямо в
рабочем поле, поэтому большая карточка `/passports/[id]` не
открывается автоматически. Server action `createPassportAction`
получает `mode = 'inline'` через `bind()` со страницы (источник
истины — роль на сервере; не доверяем клиентскому полю формы) и
вместо redirect возвращает `success` со снимком созданного
паспорта (`id`, `number`, `qtyCut`, `rollNumber`). Форма
заменяется компактным блоком `CutterAssistantSuccessCard`:

- зелёная плашка «Паспорт `P-…` выпущен» + `qtyCut` и `rollNumber`;
- primary-кнопка **«Распечатать паспорт»** — переиспользует общий
  `<PrintButton sourceType="PASSPORT_PRINT" sourceId={passport.id}
  fallbackHref={buildPassportPrintPath(passport.id)} />`. То же
  поведение, что в hero-блоке `/passports/[id]`: сначала пытаемся
  `POST /api/print-jobs` (принтер выбирается по `equipmentId`
  активной смены), при `PRINTER_NOT_CONFIGURED_FOR_EQUIPMENT` /
  `SHIFT_SESSION_REQUIRED` — открываем печатную HTML-форму в новом
  табе. Никакого нового print-subsystem не заводим;
- secondary-кнопка **«Выпустить следующий»** — сбрасывает
  `useFormState` через перемонтирование внутреннего компонента
  (key-bump в обёртке `NewPassportForm`) и возвращает пустую
  форму. **Заказ остаётся выбранным** — помощник продолжает
  выпуск по тому же заказу без перехода на `/work/cut-orders`.
  `qtyCut` и `rollNumber` сбрасываются (поля uncontrolled,
  remount возвращает `defaultValue`); размер выбирается заново
  как «первый с остатком > 0»;
- ghost-ссылка «← На рабочее место» возвращает на `/work`;
- внизу — мелкий hint со ссылкой на `/passports/[id]` (на случай
  ОТК / детального просмотра) и на `/work/cut-orders` (для
  выпуска по другому заказу).

Если в этом же сабмите помощник попросил подать заявку на
закрытие раскроя (`closure.kind === 'created' | 'failed'`),
итог заявки показывается тут же небольшой плашкой над
кнопками — без отдельного mixed-result UX.

Для всех остальных ролей (`SHOP_MANAGER` / `CUTTER` / `ADMIN`)
поведение прежнее: redirect на `/passports/[id]` либо
`CombinedResult` со ссылкой «Открыть паспорт» (когда чекбокс
«Подать заявку на закрытие раскроя» включён).

**Inline-опция «Подать заявку на закрытие раскроя» (ADR-0018, для
`CUTTER_ASSISTANT`).** Под полями формы рендерится
checkbox-карточка `.checkbox-card` «Подать заявку на закрытие
раскроя» с подсказкой «Мастер цеха подтвердит закрытие этого
размера. После подтверждения новые паспорта по размеру выпускать
будет нельзя». При включении раскрывается короткое поле «Причина
(необязательно)». Чекбокс показывается только помощнику раскройщика
(`me?.user.role === 'CUTTER_ASSISTANT'`) и только если у заказа
заполнен `productId` (иначе backend не сможет создать заявку — см.
`docs/api.md §14`). Для `SHOP_MANAGER` / `ADMIN` / `CUTTER` /
`SEAMSTRESS` / `QC` / `PACKING` / `IRONING` чекбокс не показывается
— форма работает как раньше.

Поведение submit (`createPassportAction`):

1. Чекбокс выключен, `mode = 'redirect'` (менеджерский UX) →
   старая логика: создаём паспорт и redirect на `/passports/[id]`.
2. Чекбокс выключен, `mode = 'inline'` (помощник раскройщика на
   `/work`) → паспорт создан, форма заменяется компактным
   `CutterAssistantSuccessCard` (см. блок выше). Никакого
   redirect-а в большую карточку.
3. Чекбокс включён, паспорт создан, заявка создана → форма заменяется
   зелёным success-блоком «Паспорт `P-…` создан. Заявка на закрытие
   раскроя отправлена мастеру цеха.» + кнопки «Открыть паспорт →» и
   «← К заказу» (для менеджеров — `CombinedResult`; помощнику
   раскройщика тот же исход показывается в `CutterAssistantSuccessCard`
   мини-плашкой «Заявка на закрытие раскроя отправлена мастеру цеха»).
4. Чекбокс включён, паспорт создан, заявка не создана → mixed-result:
   красная плашка «Паспорт `P-…` создан, но заявку на закрытие
   раскроя отправить не удалось» + текст ошибки backend (например,
   `[CUTTING_CLOSURE_ALREADY_REQUESTED] …`) + кнопка «Открыть паспорт
   и подать заявку →». Паспорт **не откатывается** ни при каких
   ошибках заявки.
5. Паспорт не создан → обычная `error-box` над формой, заявка не
   подаётся.

Источник истины — server action `createPassportAction(orderId,
productId, mode, …)` в `apps/web/app/orders/[id]/passports/actions.ts`.
Контракт state расширен полем
`success?: { passport: { id, number, qtyCut, rollNumber }; closure:
{ kind: 'created' } | { kind: 'failed'; error } | { kind: 'skipped' } }`.
`mode: 'redirect' | 'inline'` пробрасывается через `bind()` со
страницы (`isCutterAssistant ? 'inline' : 'redirect'`) — клиентскому
полю формы здесь не доверяем.

### 7.4. `/orders/:id/edit` — редактирование

Аналогично форме создания. Доступна **только при `status = DRAFT`**:

- PATCH заменяет строки заказа целиком (передан `items` — пересоздаём

  доходит, потому что страница edit недоступна вне `DRAFT`.
- Если клиент попадёт на страницу для заказа не-`DRAFT`, показывается
  сообщение и ссылка «Вернуться к заказу». Серверный API независимо
  от этого отдаёт 409 `ORDER_LOCKED` (ADR-0006).

## 8a. Мастер цеха (`/master`, MVP)

Мобильный «дежурный» экран роли `SHOPFLOOR_MASTER`. Источник истины:
`apps/web/app/master/*`, `apps/api/src/modules/master-calls/*`,

### 8a.1. Кнопка «Мастер» на рабочих экранах

`<CallMasterButton>` (`apps/web/components/call-master-button.tsx`)
встраивается в layouts `/work`, `/qc`, `/wto`, `/packing` и
показывается только для рабочих ролей (SEAMSTRESS, CUTTER,
CUTTER_ASSISTANT — на `/work`; QC — на `/qc`; IRONING — на `/wto`;
PACKING — на `/packing`).

Поведение:

- Floating action-button (`call-master-btn--fab`), фиксирован в
  правом нижнем углу с учётом `safe-area-inset-bottom` — не
  перекрывает основной flow и доступен одной рукой на телефоне.
- Один клик → server action `callMasterAction` → `POST /api/master-calls`.
  Кнопка не блокирует работу: ответ обрабатывается локально, основной
  скан-flow не приостанавливается.
- После успешного вызова кнопка переходит в `data-state='called'` и
  показывает «Мастер вызван». Повторный клик идемпотентен (backend
  возвращает тот же `OPEN`-вызов).
- На ошибку backend'а — inline-плашка с сообщением и `requestId`,
  основной flow продолжается.

### 8a.2. `/master` — мобильный экран мастера

Server-component (`apps/web/app/master/page.tsx`):

- Гард сессии и роли через `canSeeMasterPage`
  (`SHOPFLOOR_MASTER`, `ADMIN`, `SHOP_MANAGER`); все остальные
  получают редирект на `/`.
- Initial fetch очереди через `listOpenMasterCalls` →
  `GET /api/master-calls`. Ошибка SSR не валит экран — отдаётся в
  клиент как `initialError`, polling сам восстановится.

Client-component (`apps/web/app/master/master-page-client.tsx`):

- Header: «Мастер цеха» + бейдж с количеством открытых вызовов.
- Карточный список (`master-call-card`, не таблица): ФИО, роль,
  оборудование (с `displayNumber`, если есть), операция, текущие
  паспорта активной смены (number / size / color), время ожидания.
- Время ожидания тикает раз в секунду на клиенте (`Date.now()` vs
  `MasterCallDto.createdAt`). Список целиком обновляется polling'ом
  раз в 5 секунд (`refreshOpenMasterCallsAction`).
- Кнопка «Сканировать QR сотрудника» в каждой карточке — большая,
  во всю ширину, минимальная высота 56px (одна рука, перчатки).
- По нажатию открывается общий `<QrScannerModal>`. После
  распознавания payload идёт в `parseEmployeeQr`; если префикс не
  `EMPLOYEE:` — показывается inline-ошибка, очередь не дёргается.
  При успехе — `resolveMasterCallByEmployeeQrAction` и success-toast
  «Вызов закрыт» (3 сек). Карточка убирается оптимистично, polling
  принудительно дёргается на синхронизацию.

Mobile-first ограничения, которые UI обязан выдерживать:

- Никаких таблиц / grid'ов на узких экранах — только карточки.
- Все интерактивные элементы — `min-height: 44–56px`.
- Контент не выходит за `safe-area-inset-bottom`, чтобы не
  конфликтовать с системным навигационным баром.
- Никаких alerts/sounds: визуальный pulse на `/shopfloor/display`
  и polling на `/master` достаточны.

### 9.3. Stage buckets (что считается на каждом этапе)

| Колонка    | Что попадает                                                                   | qty       |
|------------|--------------------------------------------------------------------------------|-----------|
| `Крой`     | `Passport.status = CREATED`                                                    | `qtyCut`  |
| `Пошив`    | `IN_PROGRESS` + `currentOperation.category ∈ {CUTTING, SEWING}` (и `null`)     | `qtyCut`  |
| `ОТК ▶`    | `IN_PROGRESS` + `category = QC`, исполнитель ещё не закрыл проверку (`hasFreshQcPassed = false`) | `qtyCut`  |
| `ОТК ✔`    | `IN_PROGRESS` + `category = QC` + есть `QC_PASSED` новее последнего `OPERATION_SCAN` (= буфер «проверено, ждёт ВТО»; очищается, как только следующий step делает `OPERATION_SCAN`) | `qtyCut`  |
| `ВТО ▶`    | `IN_PROGRESS` + `category = IRONING`, ещё нет свежего `WTO_PASSED`             | `qtyCut`  |
| `ВТО ✔`    | `IN_PROGRESS` + `category = IRONING` + есть `WTO_PASSED` новее последнего `OPERATION_SCAN` (буфер «отглажено, ждёт упаковку»; очищается при следующем `OPERATION_SCAN`) | `qtyCut`  |
| `Упаковка` | `PACKED` + есть `BoxItem` в OPEN-коробке (MVP-аппроксимация, см. ADR-0013)     | `qtyGood` |
| `Выпущено` | `PACKED` И НЕ попал в «Упаковка»                                               | `qtyGood` |
| `Брак`     | `Σ Passport.qtyDefect` среди не-`CANCELLED`. Не stage; отдельная колонка/итог. | —         |

Бакеты взаимоисключающие — суммы по строке/столбцу складываются без
двойного счёта (см. ADR-0013).

### 9.4. Анимация / подсветка изменений

Клиент сравнивает каждый новый снапшот с предыдущим (по
`(sizeId, stage)` и для summary). При расхождении ячейка получает
короткую (~1.1 сек) flash-подсветку:

- **зелёный** flash — значение выросло («что-то приехало»);
- **красный** flash — значение уменьшилось («что-то уехало»);
- одновременно с обеими — обе ячейки мигают своим цветом
  (заменяет «перелёт» MVP-аппроксимацией).

Реализация — чистый CSS keyframes (`shopfloor-flash-up` /
`shopfloor-flash-down` в `globals.css`). Без Canvas, WebGL, JS-анимации
координат и реальной timeline — это сознательное упрощение Шага 10
(см. ADR-0013 §«Аппроксимация анимации»).

### 9.5. Drill-down

На MVP кликабельных переходов из ячеек нет. Чтобы посмотреть детали по
заказу, начальник переключает «Заказ» в селекте и/или открывает
карточку заказа (`/orders/:id`) отдельно.

### 9.6. Адаптив

- ≥ 1500 px — увеличенный шрифт цифр (для ТВ/моноблока).
- ≤ 900 px — компактный шрифт, но таблица всё ещё горизонтально
  скроллится (`overflow-x: auto`), чтобы экран не «ломался» на
  планшете в портретной ориентации.

### За рамками Шага 10

- Реальная анимация перелёта объекта между ячейками (Canvas/WebGL).
- WebSocket/SSE и любая отдельная realtime-инфраструктура
  (см. ADR-0007).
- BI/reporting-модуль, отдельный event-processor, материализованные
  снапшоты `ShopfloorSnapshot` (см. ADR-0013).
- Drill-down с экрана «Цех» в список паспортов.
- Сложные фильтры (дата, изделие, цвет, сменная бригада) сверх
  единственного селектора заказа.

### 9a.2. Источник данных

- Initial render — RSC: `GET /api/shopfloor/display` (см. `api.md §11`).
  Один запрос даёт KPI + матрицу `цвет × размер × stage` +
  оборудование одним «снимком». Вся группировка по цветам считается
  на backend (см. `ShopfloorService.getDisplaySummary`,
  `projectShopfloorDisplay`).
- **Фильтр по подразделению.** Страница читает
  `searchParams.divisionCode` (любой `CompanyDivision.code`) и
  пробрасывает в `getShopfloorDisplaySummary`, а та — в
  `?divisionCode=…` бэкенда. Тот же код передаётся в
  client `ShopfloorDisplayBoard` и попадает в каждый последующий
  polling-запрос — `MARKETPLACE`-экран остаётся `MARKETPLACE`-
  экраном между тиками. Без параметра — поведение прежнее (общий
  экран по всем активным заказам). Web-уровень также принимает
  старый `?division=<code>` как deprecated alias и тихо мапит его
  в `divisionCode`, чтобы старые TV-закладки не падали в 404 —
  алиас будет убран после переезда всех закладок.
- В шапке экрана при наличии `divisionCode` дорисовывается
  маленький саб-лейбл с самим кодом рядом с «ЦЕХ · LIVE». На
  остальной layout/сетку TV-режима это не влияет.
- URL-конвенция MVP — query-param: `/shopfloor/display?divisionCode=MARKETPLACE`.
  Query-param по-прежнему работает (для отладки и закладок), но
  с появлением админки display-экранов появилась альтернатива:
  создать отдельную DISPLAY-учётку через
  `/admin/display-screens/new`, привязать к ней
  `companyDivisionId` — и логиниться сразу под этим логином.
  `/api/shopfloor/display` сам подставит нужный `divisionCode` из
  `DisplayScreenConfig.companyDivision.code`, без query в URL.
  См. §10g и `api.md §11a`. Slug-роуты
  (`/shopfloor/display/marketplace`) по-прежнему отложены — см.
  `domain.md §9.6.2` и ADR-0007.
- Дальше клиент-компонент `ShopfloorDisplayBoard` поллит тот же
  endpoint по recursive `setTimeout`-планировщику с двумя cadence'ами
  (окно 5–10 c, см. ADR-0007):
  - `POLL_INTERVAL_MS = 7 c` — пока всё хорошо;
  - `POLL_INTERVAL_DEGRADED_MS = 15 c` — после первой же ошибки и до
    возврата успеха.

  Следующий tick ставится только из `finally` предыдущего, поэтому
  запросы не наслаиваются и cadence честно реагирует на backoff.
- `FETCH_TIMEOUT_MS = 6 c` — комфортный запас над реальной p99 latency
  `getDisplaySummary`. Раньше при «3000/2500» полл'е timeout срабатывал
  даже на честных 1–2-секундных ответах при чуть-чуть деградировавшей
  сети, и экран ложно показывал «Нет связи».
- **Retained snapshot.** Последний УСПЕШНО полученный срез
  никогда не очищается ошибкой и продолжает отрисовываться даже в
  degraded/offline-режимах — меняется только индикатор в шапке.
- **Классификация ошибок** (`FetchErrorKind` в `display-board.tsx`):
  - `timeout` — наш `AbortController` сработал по `FETCH_TIMEOUT_MS`;
  - `network` — `fetch` упал до получения HTTP-ответа (DNS, обрыв);
  - `auth` — HTTP 401/403 (истёк session-cookie или нет прав);
  - `server` — HTTP 5xx (backend ответил, но не справился);
  - `client` — прочие 4xx (для read-only эндпоинта в идеале не
    встречаются, но классифицируем явно);
  - `parse` — HTTP 200, но тело не валидный JSON.
- **Полная политика индикатора** (`MAX_SOFT_ERRORS = 5`):
  - 0 ошибок → «онлайн» (зелёный);
  - 1–4 подряд soft-ошибок (`timeout/network/server/client/parse`) →
    «обновление замедлено» (жёлтый), polling уезжает на 15 c;
  - ≥ 5 подряд → «Нет связи» (красный), snapshot всё ещё на экране,
    «обновлено N сек назад» уезжает дальше;
  - любой `auth` (401/403) — отдельный жёлтый чип «Сессия истекла»;
    soft-счётчик при этом НЕ инкрементируется, чтобы реальная
    проблема сессии не маскировалась под «Нет связи». Polling
    продолжается на degraded-cadence — первый же успешный ответ
    после восстановления сессии возвращает экран в «онлайн».
  - первый успешный ответ мгновенно сбрасывает оба состояния.
- На unmount (`/login` редирект, ребют) планировщик и
  in-flight `AbortController` корректно очищаются — fetch не пытается
  setState на размонтированном компоненте.

### 9a.4. Production flow matrix

| Колонка                  | Что попадает                                                                                          |
|--------------------------|-------------------------------------------------------------------------------------------------------|
| Крой                     | `qtyCut` бакет — те же правила, что в §9.3                                                             |
| Пошив (динамические)     | по одной колонке на каждую SEWING-операцию с ненулевой Σ; рендерятся как split `▶/✔` — см. ниже         |
| ОТК (split `▶/✔`)        | `▶ = qtyQc` (на проверке), `✔ = qtyQcDone` (буфер «проверено, ждёт ВТО») — см. ниже                    |
| ВТО (split `▶/✔`)        | `▶ = qtyWto` (на ВТО), `✔ = qtyWtoDone` (буфер «отглажено, ждёт упаковку») — см. ниже                  |
| Упаковка                 | `qtyPacking`                                                                                           |
| Выпущено                 | `qtyFinished` (зелёный акцент)                                                                         |
| Брак                     | `qtyDefect` (красный акцент)                                                                           |

Поток на дисплее идёт строго слева направо:

```
КРОЙ │ SEWING (динамические split ▶/✔) │ ОТК ▶/✔ │ ВТО ▶/✔ │ УПАКОВКА │ ГОТОВО
```

`✔`-буфер каждого этапа очищается, как только следующий этап начинает работу
(сделан `OPERATION_SCAN` или его аналог): `Оверлок ✔ → 0` при `Киперка ▶`,
`Киперка ✔ → 0` при `ОТК ▶`, `ОТК ✔ → 0` при `ВТО ▶`, `ВТО ✔ → 0` при
`Упаковка ▶`. Никаких «исторических» сумм — на экране только текущее WIP,
буферы между операциями и финальные итоги (Упаковка/Выпущено/Брак).
Прежние отдельные колонки `Проверено ОТК` и `Проверено ВТО` (исторические
накопления) удалены — вместо них единый split-формат `▶ | ✔`, как у sewing.

**Динамические колонки пошива (весь маршрут активных заказов).**
Раньше «Пошив» был одной суммарной колонкой. Теперь между «Крой»
и «ОТК» вставляется столько колонок, сколько SEWING-операций
включено в маршруты активных заказов прямо сейчас — **независимо
от того, есть по операции работа или там 0/0**. Источник правды —
снимок `OrderRouteStep` активных заказов, а не «у каких операций
сейчас лежит хотя бы один паспорт»:

- источник колонок — `OrderRouteStep` с `operation.category = SEWING`
  по всем активным заказам в текущей выборке (`getDisplaySummary`).
  Пройденные исторические шаги или операции «вообще не из маршрута»
  на дисплей не попадают — никакой «фантомной» колонки появиться
  не может;
- `label` колонки = `Operation.name`, порядок = `Operation.sortOrder`
  с fallback на `OrderRouteStep.index` (UI берёт уже отсортированный
  массив `sewingRoute` с backend, никаких хардкодов «Оверлок/Киперка»
  в TSX нет);
- если одна и та же `operationId` встречается в маршрутах нескольких
  активных заказов — это **ровно один блок** в `sewingRoute`,
  `rows` блока — union активных размеров всех таких заказов
  (см. `buildSewingRoute` → второй pass);
- **операция, у которой сейчас 0/0 (▶=0 и ✔=0), всё равно видна
  и показывает строки по размерам как `M 0/0`, `L 0/0`.** Это и
  есть переключение со старой «scan-driven» модели колонок на
  «route-driven»: пока в маршруте активного заказа есть SEWING-шаг —
  он на TV виден, даже если паспорта до него ещё не дошли;
- при этом WIP-семантика `▶`/`✔` не меняется (см. ниже): нули
  означают «никто здесь сейчас физически не работает и в буфере
  ничего не лежит», а не «эту операцию вычеркнули»;
- общий `qtySewing` и KPI «В работе» сохранены — пустые колонки
  ничего не добавляют к сумме `▶`, поэтому старые консьюмеры
  значений изменения не замечают.

Зачем это нужно — bottleneck-подсветка соседней пустой операции.
Эвристика «узкое место» (`detectBottlenecks` в `display-board.tsx`,
порог `BOTTLENECK_MIN_QTY = 10`) работает по правилу: если у какой-то
операции ✔-буфер максимален и при этом ≥ 10 шт., то тормозит
**следующая операция** (`processSplits[i + 1]`) — она просто не
успевает разбирать буфер, и подсвечивается именно её столбец.
Чтобы это правило вообще могло сработать в реальном цехе, следующая
операция должна **уже лежать в `processSplits`** — а значит, в
`sewingRoute` с backend. Раньше пустые операции скрывались, и
подсветка молчала ровно в тот момент, когда она была нужнее
всего. Теперь — не молчит:

```
Оверлок:
▶ 0 │ ✔ 32        ← у Оверлока в буфере 32, никто ещё не забрал

Киперка:
▶ 0 │ ✔ 0         ← пусто, но колонка ВИДНА — её и подсветит coral pulse
```

Контракт ответа (`sewingRoute` — массив `ShopfloorDisplayRouteOperationDto`
с `rows: ShopfloorDisplayRouteSizeRowDto[]`, где каждая строка
несёт `{size, inProgress, done}` и `0/0` — допустимое значение)
описан в `docs/api.md` → `GET /api/shopfloor/display` и в JSDoc
`packages/shared/src/shopfloor.ts`. Старое поле `sewingColumns`
оставлено для KPI/проекции, но матрица его больше не читает —
источник колонок единственный: `sewingRoute`.

**Двухстрочная шапка процессных операций (split `▶` / `✔`).** Каждая
process-колонка матрицы (sewing-операция, ОТК, ВТО) по факту состоит
из двух подколонок:

```
… │ КРОЙ │     ОВЕРЛОК 1     │      КИПЕРКА      │       ОТК       │       ВТО       │ УПАКОВКА │ …
   │      │   ▶    │    ✔     │   ▶    │    ✔     │   ▶    │   ✔   │   ▶    │   ✔   │          │
```

- первая строка `<thead>` — название операции (`<th colSpan={2}>`,
  класс `display-matrix__th--sewing-op`, `scope="colgroup"`);
- вторая строка `<thead>` — иконки `▶` (в работе) и `✔` (готово),
  по одному `<th>` на каждую (`display-matrix__th--sub`,
  `display-matrix__th--sew-in` / `display-matrix__th--sew-done`);
- ОТК и ВТО рендерятся через тот же `ProcessSplit`-механизм, что и
  sewing-операции (см. `buildProcessSplits` / `SplitSubHeader` в
  `display-board.tsx`), поэтому шапка/тело/делители для них —
  по идентичному контракту;
- статичные колонки (`Размер`, `Крой`, `Упаковка`, `Выпущено`, `Брак`)
  идут с `rowSpan={2}` и визуально занимают обе строки шапки;
- значения в `▶` и `✔` — это Σ `qtyCut` (штуки), а НЕ количество
  записей `Passport`. Один паспорт — это «партия из N изделий»,
  и оператор смотрит на штуки. См. `buildSewingRoute` в
  `shopfloor.service.ts` и `ShopfloorDisplayRouteSizeRowDto.{inProgress,done}`
  в `packages/shared/src/shopfloor.ts`;
- **семантика — текущее накопление WIP, а НЕ исторический факт
  выполнения операции.** Если паспорт уже двинулся дальше по
  маршруту, старая sewing-операция БОЛЬШЕ ЕГО НЕ ПОКАЗЫВАЕТ ни
  в `▶`, ни в `✔`. Иначе оператор видит «у оверлока висит 12»,
  хотя физически эти 12 уже у следующей швеи;
- `▶ inProgress` = «паспорт сейчас ФИЗИЧЕСКИ в работе на этой
  sewing-операции». Источник —
  `resolveCurrentSewingOperationId(p)` в `shopfloor.service.ts`:
  - сначала `assignedShiftSewingOperationId` — операция активной
    смены закреплённой швеи; это самый точный физический сигнал
    (после `issueToEmployee` без OPERATION_SCAN, и в момент,
    когда следующий sewing-step берёт паспорт, всё ещё хранящий
    `currentOperationId` от предыдущего шага, — паспорт уже на
    станке этой швеи);
  - иначе fallback — `Passport.currentOperationId`, если его
    категория `SEWING` (типично для seed/тестов и редких ситуаций
    со снятой сменой);
  - жёсткие гварды: `status = IN_PROGRESS` и
    `currentEmployeeId != null`. После `completeOperationByEmployee`
    исполнитель снимается, и такой паспорт в ▶ не считается —
    он переезжает в `✔` (буфер «готово, ждёт следующего шага»).
    Расходимость с матричным `sewingColumnKeyOf` (он отдаёт
    приоритет последнему явному `OPERATION_SCAN`) — намеренная:
    матрица отвечает на вопрос «куда отнести WIP в сетке колонок»,
    ▶ — на вопрос «где паспорт ФИЗИЧЕСКИ сейчас»;
- `✔ done` = «паспорт ЗАВЕРШИЛ эту sewing-операцию и ещё НЕ
  передан следующему step'у». То есть это БУФЕР между текущей и
  следующей sewing-операцией, а не исторический факт выполнения.
  Условия одновременно:
  - `currentEmployeeId == null` (исполнитель снят
    `completeOperationByEmployee`);
  - `status = IN_PROGRESS` (CANCELLED/PACKED-паспорта sewing-цикл
    закрыли, в ✔ им делать нечего);
  - `currentRouteStepIndex == step.index` (как только следующий
    step делает `OPERATION_SCAN`, индекс сдвигается и ✔ старого
    шага автоматически становится 0 — никаких «висящих исторических»
    ✔). Для последней sewing-операции маршрута это значит: ✔
    показывается ровно до момента, пока ОТК не отсканировал
    паспорт; после QC-scan ✔ исчезает;
- отдельного нижнего блока «Маршрут пошива» НЕТ — данные `sewingRoute`
  раскрываются прямо в split-колонках основной матрицы (никакого
  второго экрана/таблицы, никаких процентов);
- equipment-панель эта шапка не трогает: компактная сетка плиток
  (номер + цветной статус, см. §9a.5) остаётся как есть.

Группировка строк — по цвету (`Passport.color`):

- сначала канонические **Чёрный** и **Белый** (нормализуются
  кириллица/латиница/регистр в один блок — см. `normalizeColor`);
- затем остальные цвета по алфавиту;
- пустой `color` попадает в служебный блок «Без цвета»;
- внутри каждого цвета — строки по размерам (только ненулевые),
  плюс «Итого по цвету»;
- снизу — общий «Итого» по всем цветам.

Цифры между `/shopfloor` и `/shopfloor/display` сходятся ровно:
обе проекции пересоздают суммы по одним и тем же правилам
(см. `bucketOf` + `pickQty` в `shopfloor-projection.ts`).

### 9a.5. Equipment panel

Компактные плитки (≈ 30 рабочих мест) вместо текстовых строк.
Сознательно «бедный» формат: чтобы 30+ станков уместились на 1080p
TV без скролла, в плитке нет ни иконок, ни имени оборудования,
ни ФИО — только то, что оператору нужно увидеть за полсекунды:

- крупный `displayNumber` (или `·`, если номер не задан) —
  идентификатор станка;
- маленькая тонкая line-иконка типа оборудования (`eq.kind`) —
  ВТОРИЧНЫЙ маркер слева от номера, не возвращающий «карточный»
  вес плитки. Маппинг (`EquipmentKindIcon` в `display-board.tsx`):
  - `SEWING` → локальная SVG `IconSewingMachine` (швейная
    машина: стол + корпус + игла). Прежний `Shirt` из `lucide-react`
    читался как футболка / готовое изделие и путал оператора;
  - `IRONING` → локальная SVG `IconIron` (утюг: подошва +
    корпус + ручка + штрихи пара). Прежний `Heater` читался как
    «обогреватель»;
  - `CUTTING` → `Scissors` (lucide);
  - `QC` → `Search` (lucide, лупа);
  - `PACKING` → `Package` (lucide, коробка);
  - `OTHER` → иконка не рисуется.
  В `lucide-react@1.9.0` нет ни `SewingMachine`, ни `Iron`, поэтому
  под две главные категории цеха используются собственные line-SVG в
  едином стиле с lucide (stroke="currentColor", `fill="none"`,
  thin stroke);
- **актуальный размер / размеры**, если на станке прямо сейчас
  есть изделие в работе. Источник — `currentSizes: string[]` из
  `ShopfloorEquipmentStatusDto`. Если массив пустой (станок
  свободен / простаивает / завершил операцию) — строка размеров
  не рендерится вообще, чтобы плитка не «прыгала» по высоте.
  Несколько размеров пишутся через запятую без пробела (`M,L`),
  длинное обрезается ellipsis'ом — плитка остаётся квадратной;
- **цвет всей плитки** (`display-equipment-tile--<status>`) несёт
  статус оборудования. Бизнес-семантика для TV-витрины:
  - **зелёный (`ONLINE`)** — `equipment.active = true`, есть
    открытая `ShiftSession` И на станке прямо сейчас есть хотя
    бы один паспорт в работе (`currentSizes.length > 0`). Только
    этот цвет означает «реально шьётся», а не «недавно
    сканировали»;
  - **жёлтый (`WARNING`)** — есть открытая смена, но паспорта в
    работе нет (швея зашла, но крой ещё не взяла или только что
    закончила и ждёт следующий). Это «занят, но простаивает»;
  - **серый (`OFFLINE`)** — нет открытой смены ИЛИ
    `Equipment.active = false`.

  Раньше `ONLINE`/`WARNING` различались time-based порогом
  (`WARNING_AFTER_MS = 15 мин` по последнему `OPERATION_SCAN`):
  смена открыта без паспорта первые 15 минут была «зелёной», что
  давало ложный сигнал начальнику цеха на TV. Новая логика
  напрямую сверяется с `currentSizes` (тем же источником, что и
  колонка ▶ split-таблицы sewing-route), поэтому зелёный плитки
  и непустая ▶-колонка по этому станку всегда совпадают.

Под сеткой — компактный totals-чип «N / M / K» по статусам
(только цвет + цифра, без подписей). Никакой «полной» легенды
статусов / имени станка / ФИО в плитке нет — это и есть главное
обещание «компактный equipment-grid». Поле `lastActivityAt` в DTO
сохранилось как диагностический ISO-таймстамп последнего
`OPERATION_SCAN` сотрудника (для UI-подсказок и логов), но
больше не управляет цветом плитки.

Что считается «изделием на станке» (`currentSizes`). Backend
синхронизирован с sewing split-таблицей (▶/✔), см.
`ShopfloorService.listEquipmentStatus`:

  1. `Passport.status === IN_PROGRESS`;
  2. `Passport.currentEmployeeId === ShiftSession.employeeId`
     активной смены этого станка;
  3. либо `Passport.currentOperationId === shift.operationId`
     (паспорт уже отсканирован на эту операцию), либо смена —
     sewing-категории, и тогда любая активная привязка швеи
     считается «на её станке» (assigned-shift fallback). Это
     закрывает кейс «крой только что выдан швее (`issueToEmployee`),
     до первого `OPERATION_SCAN` `currentOperationId` ещё
     `CUT_DIVISION`, но физически 12 шт M уже на её Оверлоке».

`currentSizes` — это «что прямо сейчас физически на этом
оборудовании», а не маршрутная статистика; он одинаков с тем, что
показывает split-таблица в колонке ▶ для той же sewing-операции.

### 9a.7. Геометрия fullscreen / TV layout

Экран рассчитан на **fullscreen-режим** на больших мониторах в цеху
(target: 44" 1920×1080 или 4K панель в browser fullscreen). Все
ключевые геометрические инварианты явно зафиксированы в CSS и
покрыты структурными smoke-тестами; описаны они здесь, потому что
их случайная поломка визуально проявляется как «на TV видно только
заголовки, данные пропали».

#### Цепочка высот (overflow chain)

```
.display-screen   position: fixed; inset: 0; height: 100dvh
                  display: grid; grid-template-rows: auto auto minmax(0, 1fr)
                  overflow: hidden                       ← обёртка не скроллит
   │
   ├─ header (auto)
   ├─ KPI    (auto)
   └─ .display-board     min-height: 0; min-width: 0
        │  display: grid; columns: minmax(0,2fr) minmax(320px,1fr)
        │
        ├─ .display-board__production    flex column; min-height: 0
        │     └─ .display-block          flex 1 1 auto; min-height: 0;
        │           │                    overflow: hidden
        │           ├─ <h2> title (auto)
        │           └─ .display-matrix__scroll
        │                  flex: 1 1 auto; min-height: 0;
        │                  overflow: auto                ← скроллит МАТРИЦА
        │
        └─ .display-board__equipment     flex column; min-height: 0
              └─ .display-block          flex 1 1 auto; min-height: 0;
                    │                    overflow: hidden
                    ├─ <h2> title  (auto)
                    ├─ legend      (auto)
                    ├─ .display-equipment-grid
                    │      flex: 1 1 auto; min-height: 0;
                    │      overflow-y: auto              ← скроллит СЕТКА
                    └─ totals      (auto)
```

Главные инварианты, которые ОБЯЗАТЕЛЬНО держать вместе:

- `min-height: 0` (а кое-где и `min-width: 0`) на каждом узле цепочки.
  Без этого у flex/grid-items неявный `min-height: auto` равен
  intrinsic height содержимого (длинная таблица), и внешний
  `overflow: hidden` на `.display-block` срезает матрицу так, что
  на экране остаются только заголовки.
- `flex: 1 1 auto` на `.display-matrix__scroll` и
  `.display-equipment-grid` — именно они являются scroll-зонами и
  должны явно занимать остаток высоты.
- Сама `.display-screen` НИЧЕГО не скроллит (`overflow: hidden`) —
  скроллятся только внутренние области.
- `height: 100dvh` (а не `100vh`) — устойчивее на TV/embedded
  WebView, где address-bar/UI overlay могут «сжимать» классический
  `100vh`.

Эти контракты заверены тестами в
`tests/smoke/shopfloor-display.smoke.test.ts → describe('UI layout:
fullscreen / TV geometry на /shopfloor/display')`.

#### Sticky table header

`.display-matrix__th` — `position: sticky; top: 0;` относительно
своего scroll-ancestor (`.display-matrix__scroll`). Для устойчивости
на TV/WebKit добавлены:

- `background-clip: padding-box` + непрозрачный фон — иначе под
  заголовком при быстром скролле «протекают» строки;
- `z-index: 2` — чтобы заголовки строк блока цвета (`color-row`,
  `z-index: 1`) не наезжали поверх sticky;
- `contain: layout paint` на scroll-обёртке — даёт более
  предсказуемый repaint sticky без «прыгающих» заголовков.

#### Breakpoints / TV layer

| Слой              | Условие              | Что меняет                                                                 |
|-------------------|----------------------|-----------------------------------------------------------------------------|
| Default           | —                    | Двухколоночный board, KPI на 8 карточек в ряд                              |
| KPI compact       | `max-width: 1399px`  | KPI переключается с 8×1 на 4×2 (узкие лэптопы)                             |
| Single column     | `max-width: 1199px`  | Board из двух колонок схлопывается в одну (планшеты/малые экраны)          |
| **TV / large**    | `min-width: 1600px`  | Крупнее KPI, заголовки блоков, ячейки матрицы и плитки оборудования. **Board остаётся двухколоночным**, KPI — в одну строку из 8. |
| **4K / huge**     | `min-width: 2400px`  | Ещё один шаг апскейла шрифтов и плиток поверх TV-слоя                      |

TV-слой (`min-width: 1600px`) — компактный набор переопределений
font-size / padding / icon-size, скоупанный под `.display-screen`.
Он намеренно НЕ меняет layout-цепочку (никаких новых `display:` /
`grid-template-columns:`), чтобы не ломать инварианты overflow выше.
Брейкпоинт `1600px` сознательно выше десктопного `1199`, чтобы
laptop-вид (1280-1440) не «перерастал» в TV-режим случайно.

#### Изоляция от глобального layout

`.display-screen` — fixed overlay, но на всякий случай
`body:has(.display-screen)` дополнительно:

- обнуляет `padding`, `max-width`, `min-height` у `.app-main`
  (чтобы под overlay не мог проявиться scrollbar у body);
- ставит `overflow: hidden` у `<body>`.

`AppHeader` уже скрыт у этой страницы для всех ролей
(см. `apps/web/components/app-header.tsx → isShopfloorDisplayPath`),
поэтому пространство экрана действительно полное.

### 10a. Карточка оборудования и печатная QR-этикетка

**Список `/admin/equipment`** (см. ADR-0017 §5):

   таблицу).
2. **Все оборудования** — `data-table`: «№» (`displayNumber` или «—»),
   «Код», «Название», «Активно», «Операций» (или «0 — не настроено»),
   ссылка «Настроить →». Если оборудования ещё нет — пустой стейт
   с inline-ссылкой «Добавьте первый станок» на ту же
   `/admin/equipment/new`.

**Страница создания `/admin/equipment/new`** — отдельный detail-экран
со своим back-link'ом «← К списку оборудования» и единым header'ом
(`DetailPageHeader`, как и `/admin/equipment/[id]`). Внутри одна
карточка «Параметры оборудования» с формой `CreateEquipmentForm`
(переиспользуется без копий). Поля: «Название оборудования»
(обязательно, до 120 символов), «Номер оборудования» (опциональный
`displayNumber`, до 16 символов), «Код» (опциональный технический
slug; если пусто — backend сгенерирует из имени), и чек-лист
«Операции» (тот же `option-list`, что и на detail-странице — порядок
выбора задаёт `sortOrder` на /work). Submit — «Создать оборудование»;
источник истины — `POST /api/equipment` (роли `ADMIN`/`SHOP_MANAGER`).
После успешного создания action редиректит на карточку нового
оборудования (`/admin/equipment/[id]`), чтобы менеджер сразу мог
напечатать QR-этикетку и/или допроставить операции — тот же паттерн
использует `/admin/warehouses`. Если задаётся явный код, при
коллизии backend отдаёт `409 EQUIPMENT_CODE_TAKEN`; для
автогенерации добавляется суффикс `-2`, `-3`, …

**Карточка `/admin/equipment/[id]`** устроена как несколько небольших
секций, каждая со своим Save:

1. **Шапка** с крупным `№displayNumber` рядом с названием станка,
   кодом и QR. Справа — две кнопки: «Печать QR» (открывает
   печатную HTML-форму в новой вкладке) и «← К списку».
2. **Название оборудования** — точечная форма для `Equipment.name`
   (`required`, до 120 символов). После сохранения ревалидируется
   `/work`, чтобы швея видела новое имя в форме старта смены без
   задержки. `code` и `qrCode` при переименовании не меняются —
   printer-bindings и уже отсканированные QR продолжают работать
   (см. ADR-0017 §5).
3. **Номер станка** — точечная форма для `displayNumber`. Это
   ручной отображаемый номер для физической маркировки (см.
   `docs/domain.md §5c`). Пустая строка = сброс в `null`.
   Источник истины — `PATCH /api/equipment/:id`.
4. **Разрешённые операции** — чек-лист, как и раньше (ADR-0017).
   Полная замена набора через `PATCH /api/equipment/:id/operations`.

**Печатная этикетка `GET /api/equipment/:id/print`** — отдельная
HTML-страница, оптимизированная под `@page A6` и термопринтер
(см. `apps/api/src/modules/equipment/equipment-print.ts`).
Визуальный приоритет на этикетке:

1. `displayNumber` — крупно, жирно, ~6rem; самый «бросающийся в
   глаза» элемент. Цель — глядя на наклейку с расстояния метра,
   мгновенно различить «станок №1» и «станок №2».
2. QR-код (`equipment:{id}` по ADR-0008 — формат не меняется,
   scan flow на /work остаётся совместимым).
3. Название оборудования (`Equipment.name`).
4. Технический код (`Equipment.code`).

Этикетка отдаётся `@Public()` — той же логикой, что и
`/api/passports/:id/print` и `/api/packing/boxes/:id/label`:
принтер-станция в типографии работает без сессии. RBAC
сохраняется только на изменение (PATCH-ах).

### 10b. Склад (`/admin/warehouses`, ADR-0019)

Управленческая группировка ячеек физического хранения. Источник
истины — backend (`/api/warehouses` + `PATCH /api/cells/:id`, см.
`api.md §15`). Доступ — `SHOP_MANAGER` и `ADMIN`; защищён
`app/admin/layout.tsx` через `canSeeAdmin`. На главной (`/`) и в
админ-нав-баре пункт показывается только этим ролям. Существующий
flow «scan cell → place passport» не меняется — `Cell.warehouseId`
nullable, помощник раскройщика продолжает сканировать ячейки как
раньше.

#### Список `/admin/warehouses`

- **Шапка** с пояснением: «Управленческая группировка ячеек
  физического хранения. Привязка ячейки к складу и печать QR — на
  карточке склада. Создание нового склада — на отдельной странице».
  В правом краю шапки — primary-кнопка **«Добавить склад»**, ведёт
  на `/admin/warehouses/new`.
- **Все склады** — `data-table`: *Название*, *Код*, *Активен*,
  *Ячеек*, ссылка «Открыть →». Если складов нет — пустой стейт
  «Складов пока нет», в подсказке ссылка на `/admin/warehouses/new`.

#### Создание `/admin/warehouses/new`

Отдельная страница с `DetailPageHeader` (eyebrow «Хранение», icon
`warehouses`, back-link «К списку складов»). Форма (`detail-form`):
`name` обязательно (max 120), `code` опционально (max 32, попадает в
QR-этикетку ячейки «Склад: <name> (<code>)»). Уникальность
`name`/`code` валидируется на backend бизнес-ошибками
`WAREHOUSE_NAME_TAKEN` / `WAREHOUSE_CODE_TAKEN`. На успехе
`createWarehouseAction` редиректит на карточку нового склада, чтобы
менеджер сразу мог создать линию (`A1..A20`) и/или привязать
существующие ячейки. Тот же UX уже применён к `/admin/equipment/new`
(ADR-0017) и `/admin/operations/new` (ADR-0020).

#### Карточка `/admin/warehouses/[id]`

Секции, каждая — Server Action:

1. **Реквизиты склада** — точечная форма для `name`/`code`/`isActive`.
   Источник истины — `PATCH /api/warehouses/:id`. Чекбокс «Активен»
   управляет `isActive` (на MVP это и есть «удаление склада», см.
   ADR-0019 — настоящего DELETE в API нет).
2. **Ячейки склада** — `data-table` с привязанными ячейками:
   *Код*, *QR-payload*, *Активна*, кнопка «Печать QR» (открывает
   `GET /api/cells/:id/print` в новой вкладке — `@Public()` HTML
   38×58 с QR `cell:{id}`), кнопка «Отвязать» (server action поверх
   `PATCH /api/cells/:id { warehouseId: null }`). Если ячеек нет —
   подсказка «К этому складу ещё не привязано ни одной ячейки».
   В шапке секции — primary-кнопка **«Печать всех ячеек»**
   (см. ниже), которая запускает массовую печать через очередь
   принтера; кнопка disabled, если активных ячеек нет.
3. **Линии склада** — `CreateLineForm` для массового создания
   ячеек: менеджер вводит код линии (`A`) и количество (`12`),
   backend атомарно создаёт `WarehouseLine` и `A1..A12`. Дубликаты
   кодов отдают понятный 409 (см. `api.md §15`).
4. **Привязать ячейку** — select из активных ячеек, ещё не
   привязанных к этому складу (фильтрация на сервере). Если ячейка
   уже привязана к другому складу, рядом с её кодом показывается
   «переедет из «<имя другого склада>»» — менеджер видит, что
   привязка явно переедет (никаких блокировок «нельзя двигать
   ячейку с активными паспортами»: складская группировка не влияет
   на flow `place`/`issue`).

##### Окно «Печать всех ячеек» (массовая печать)

Click по primary-кнопке в шапке секции «Ячейки склада» открывает
аккуратное модальное окно (тот же CSS-паттерн `.qr-modal`, что у
сканера на `/work` — backdrop, заблокированный скролл фона, Esc /
крестик / клик по бэкдропу = закрыть). Внутри:

- **Заголовок** — «Печать всех ячеек: <название склада>»;
- **Настройки**:
  - select «Принтер» — список логических `Printer` (`isActive=true`),
    подпись каждого = `name — equipmentName • онлайн/офлайн`. Если
    активных принтеров нет — option «Нет активных принтеров» и
    подсказка «Создайте и подключите принтер на странице
    Администрирование → Принтеры», submit заблокирован;
  - select «Размер этикетки» — пока единственный вариант
    `38 × 58 мм (горизонтально, QR + номер)` (`WAREHOUSE_LABEL_SIZES`,
    архитектура готова к расширению — например, A6 для крупных
    стеллажей);
  - input «Копий каждой» — int 1..50, default 1;
- **Сводка** — три плитки «Ячеек к печати / Копий / Всего заданий»,
  пересчитываются live при изменении копий;
- **Превью этикеток** — сетка плиток-«этикеток», каждая повторяет
  layout `cell-print.ts` (QR слева, номер справа, пропорция 58:38).
  QR-картинка тянется через `@Public()` `GET /api/cells/:id/qr` —
  тот же байтовый QR, что и в реальной этикетке. Показываем первые
  24 ячейки + подсказка «ещё N ячеек попадёт в печать»;
- **Действия** — `Отмена` (ghost) + `Печать` (primary). Submit
  идёт через server action `printWarehouseCellsAction` поверх
  `POST /api/warehouses/:id/print-cells` — модалка не закрывается,
  показывает success-плашку «Поставлено N заданий в очередь
  принтера (M ячеек × K копий, формат 38×58)» или error-плашку с
  кодом и `requestId` для багрепорта. Менеджер может прогнать
  второй залп (например, на другой принтер) без переоткрытия
  окна.

Backend создаёт по одному PENDING-`PrintJob` на каждую копию
каждой активной ячейки склада, в стабильном порядке `lineId →
lineIndex → code`. Агент рядом с принтером заберёт очередь FIFO
и распечатает HTML 38×58 (`payloadUrl` job-а указывает на
`GET /api/cells/:id/print`).

Печатная форма QR ячейки — отдельная HTML-страница (см.
`apps/api/src/modules/passports/cell-print.ts`). Жёсткий формат —
**38×58 мм горизонтально** (стандартная термоэтикетка для
маркировки полок), левая половина = QR, правая половина =
крупный номер ячейки. Шрифт номера подбирается под длину кода
(`A1` рисуется крупнее, чем `WH-MAIN-12`), чтобы и короткие и
длинные коды влезали без обрезки. На самой этикетке в реальной
печати **никакого** другого текста нет: ни имени склада, ни
internal id, ни payload-строки `cell:...`, ни кнопки «Печать»
(она спрятана через `@media print`). Print-safety: `@page { size:
58mm 38mm; margin: 0 }`, `overflow: hidden`, `page-break-inside:
avoid`, `print-color-adjust: exact` — чёрный QR не «оптимизируется»
драйвером в серый, и контент гарантированно влезает в одну
этикетку. При открытии страницы в браузере (single-cell flow)
кнопка «Печать» остаётся видимой, чтобы менеджер мог нажать её
руками. QR-payload `cell:{id}` (ADR-0008) **не меняется** — уже
напечатанные стикеры остаются валидными.

### 10c. Операции (`/admin/operations`, ADR-0020)

Управленческий блок «Операции» — единый источник истины для
сдельного тарифа. Источник истины — backend (`/api/operations`, см.
`api.md §15a`), доменная модель — `domain.md §4`/§4a. Доступ —
`SHOP_MANAGER` и `ADMIN`; защищён `app/admin/layout.tsx` через
`canSeeAdmin`. На главной (`/`) и в админ-нав-баре пункт показывается
только этим ролям. Существующий pipeline (выпуск паспорта, scan на
операцию, упаковка, начисления) **не меняется** — карточка лишь
переключает источник ставки между `Operation.fixedRate` и
`OperationRateBySize`.

#### Список `/admin/operations`

- **Шапка** с пояснением: «Операция = этап производства. Тариф
  выбирается на карточке: фиксированная цена за единицу, цена по
  размерам или окладная (без сдельной ставки)». В правом краю шапки —
  primary-кнопка **«Добавить операцию»**, ведущая на отдельную
  страницу `/admin/operations/new`. На пустом стейте — inline-ссылка
  «Создайте первую операцию» туда же.
  *(History note.* Изначально форма создания жила прямо на списке —
  при росте числа операций она перегружала страницу и мешала
  просмотру таблицы; пост-Equipment CRUD вынесли её на отдельный
  экран по аналогии с `/admin/equipment/new`. Backend
  `POST /api/operations` и server action `createOperationAction` не
  менялись.)
- **Все операции** — `data-table`: *Название*, *Код*, *Категория*,
  *Тариф* (бейдж `FIXED` / `BY_SIZE` / `SALARY_ONLY`), *Ставка*
  (одно число для `FIXED`, «по размерам (N)» для `BY_SIZE`, «—» для
  `SALARY_ONLY`), *Активна*, ссылка «Открыть →». Сортировка по
  `sortOrder, name`.

#### Страница `/admin/operations/new`

Отдельный detail-экран создания операции:

- `DetailPageHeader` с back-link'ом «← К списку операций» и
  subtitle «Создайте новую операцию и настройте её тарифный режим…».
- Одна карточка «Параметры операции» с переиспользуемой формой
  `CreateOperationForm` — `detail-form` layout, поля сгруппированы:
  - **Метаданные**: `code` (UPPER_SNAKE_CASE, обязательно, под
    подсказкой «pipeline/сиды завязаны на него»), `name`,
    `category`.
  - **Тариф**: select `pricingMode` с подсказкой под ним; для `FIXED`
    рядом появляется поле «Ставка за единицу», для `BY_SIZE` /
    `SALARY_ONLY` — info-плашка с пояснением, что вводить ничего не
    нужно (для `BY_SIZE` ставки задаются на карточке, для
    `SALARY_ONLY` сдельная ставка не применяется).
  - **Привязать к оборудованию** *(опционально)* — компактный
    чек-лист активного оборудования (порядок: `displayNumber`, потом
    `name`). Если ничего не отмечено, операция создаётся как
    глобальная, но **не появится в выборе на /work после сканирования
    QR станка**, пока её явно не отметят на карточке оборудования.
    Под заголовком фиксированно висит warn-плашка с этой формулировкой —
    менеджер не «забывает» в момент создания. Список — облегчённая
    проекция `EquipmentSummaryDto` из `GET /api/equipment`, активные
    станки выводятся со счётчиком уже разрешённых на них операций.
    Привязка делается уже **после** успешного `POST /api/operations`
    через существующий `PATCH /api/equipment/:id/operations`
    (full-replace) — server action сначала читает текущий allow-list
    каждого выбранного станка и аккуратно дописывает в него новый id,
    не стирая существующие связи (см. `actions.ts createOperationAction`,
    `api.md §3a`). Это сознательно — отдельной ручки для «добавить
    одну операцию ко многим станкам» мы не вводим, чтобы не плодить
    backend под одноразовый UX.
- Submit — primary-кнопка «Создать операцию».
  - **Полный успех** (создание + все привязки прошли) — server action
    редиректит на `/admin/operations/[id]` нового объекта; менеджер
    сразу попадает в карточку, чтобы донастроить таблицу `BY_SIZE` или
    поправить `isActive`.
  - **Частичный успех** (операция создана, но какой-то PATCH к
    оборудованию упал) — редиректа нет, форма показывает явную
    ошибку с перечислением сбоев и ссылкой «Открыть карточку операции →»;
    созданная операция не удаляется, чтобы не потерять управленческий
    `code` (на нём может уже висеть pipeline/сиды).
- Ревалидация после успеха: `/admin/operations`, `/admin/equipment`
  и `/work` — швея на следующем сканировании QR станка увидит новую
  операцию в списке без ручной перезагрузки.

#### Карточка `/admin/operations/[id]` — адаптивная под тариф

Три секции, каждая — Server Action:

1. **Реквизиты операции** — точечная форма для `name`/`category`/
   `isActive` и переключателя `pricingMode`. `code` отображается, но
   read-only (это идентичность). Источник истины — `PATCH
   /api/operations/:id`.
2. **Тариф** — секция полностью зависит от выбранного `pricingMode`:
   - **`FIXED`**: одно числовое поле «Ставка за единицу»
     (`fixedRate`). Сохраняется в одном PATCH с `pricingMode =
     FIXED`. Если переключаемся из `BY_SIZE` — backend в
     транзакции стирает все строки `OperationRateBySize`.
   - **`BY_SIZE`**: таблица «Размер ↔ Ставка» с inline-редактированием
     и кнопкой **«Заполнить всем одну ставку»** (быстрое
     copy-all для типичного оверлок-кейса). Под таблицей —
     подсказка: «Ставка нужна для каждого размера, который реально
     встречается в плане. Если ставки нет — начисление упадёт с
     `OPERATION_RATE_MISSING` при ближайшем создании паспорта».
     Сохранение — полная замена набора (см. `api.md §15a`).
   - **`SALARY_ONLY`**: блок-плашка «Операция окладная — сдельная
     ставка не применяется. Начисления (`OperationEntry`) для неё
     не создаются». Никаких полей.
3. **Опасная зона** (только для `BY_SIZE`): кнопка «Очистить все
   ставки», отправляющая `PATCH ... { ratesBySize: [] }`. На MVP
   удаления операции через UI нет — менеджер выключает `isActive`.

#### UX-поведение при смене `pricingMode`

- Изменение selectа в форме сразу перерисовывает блок «Тариф» (без
  PATCH-а): пользователь видит правильную форму до сохранения.
- При сохранении смены режима server action чистит несовместимые
  поля транзакционно (см. `api.md §15a`). Это защищает от
  «осиротевших» строк `OperationRateBySize` после `BY_SIZE → FIXED`
  и не требует от менеджера ручной уборки.
- Если переключение прошло успешно, страница `revalidate`-ится и
  показывает актуальную форму — никаких stale-полей.

### 10d. Сотрудники (`/admin/employees`, ADR-0021)

Управленческий блок «Сотрудники» — единая точка для настройки
окладной модели (`compensationType` + `salaryPerShift`),
soft-выключения сотрудников и создания новых карточек. Источник
истины — backend (`/api/employees`, см. `api.md §3b`), доменная
модель — `domain.md §9a`. Доступ — только `SHOP_MANAGER` и `ADMIN`;
защищён `app/admin/layout.tsx` через `canSeeAdmin`. На главной (`/`)
и в админ-нав-баре пункт показывается только этим ролям. Удаление
карточек по-прежнему out-of-scope (ADR-0021): менеджер мягко
гасит сотрудника через `active = false`.

#### Список `/admin/employees`

- **Шапка** с пояснением: «Тип компенсации и ставка управляют и
  окладным (`SalaryEntry`), и сдельным (`OperationEntry`) контурами:
  `PIECEWORK`/`MIXED` участвуют в сдельщине, `SALARY`/`MIXED`
  получают дневной оклад». В правом краю — primary-кнопка
  **«Добавить сотрудника»** на `/admin/employees/new` (тот же UX,
  что у `/admin/equipment`, `/admin/operations`, `/admin/warehouses`,
  `/admin/tech-cards`).
- **Активные сотрудники** — `data-table`: *ФИО*, *Логин*, *Роль*,
  *Тип компенсации* (бейдж `Сдельная` / `Оклад` / `Смешанная`),
  *Ставка за смену* (число для `SALARY`/`MIXED`, «—» для
  `PIECEWORK`), *Активен*, ссылка «Открыть →». Сортировка по
  `fullName`.
- **Архив** — отдельным сворачиваемым блоком ниже: те же столбцы,
  но `active = false`. Показывается, только если в системе есть
  деактивированные.
- Фильтры (опционально, в шапке): по роли и по типу компенсации.

#### Создание `/admin/employees/new`

Отдельный detail-экран со своим `DetailPageHeader` и back-link'ом
«← К списку сотрудников». Форма (`CreateEmployeeForm`) собирается
строго из текущей модели `Employee` — никаких новых полей задача
не вводит:

- **ФИО** (`fullName`) — обязательно, max 200.
- **Логин** (`login`) — уникальный, нормализуется в lower-case
  (тот же приём, что и на seed-аккаунтах). Конфликт по логину
  возвращается из backend как `EMPLOYEE_LOGIN_TAKEN` (409) — UI
  показывает текст ошибки рядом с формой.
- **PIN/пароль** (`pin`) — храним только bcrypt-hash в
  `Employee.pinHash`; сам PIN не отдаётся ни в одном DTO. Минимум
  4 символа.
- **Роль** (`role`) — селект по `EMPLOYEE_ROLES` (Role enum без
  служебной `DISPLAY` — её админ заводит напрямую через seed).
- **Тип компенсации** (`compensationType`, default `PIECEWORK`)
  и **Ставка за смену** (`salaryPerShift`) — единственная ось «как
  платим» (см. `domain.md §9a`). Тот же UX-инвариант, что и на
  карточке: для `SALARY`/`MIXED` поле «Ставка за смену»
  обязательное и `> 0`; для `PIECEWORK` его можно оставить пустым.
- **Активен** (`active`, default `true`) — мягкий флаг.
- **Подразделение** (`companyDivisionId`, PHASE 2 STEP 2) — select
  с опциями активных карточек `CompanyDivision`. Опционально:
  «— без привязки —» (default) пишет `null` в БД, и сотрудник
  попадает в payroll-фильтр «Все подразделения». Если у проекта
  нет ни одного активного подразделения, поле прячется — форма
  работает как раньше. Используется payroll-фильтром
  «Подразделение» для окладной части (см. ниже §«Зарплата
  /admin/payroll»). Сдельные начисления автоматически попадают в
  подразделение **заказа** независимо от этого выбора.

После успешного создания server action `createEmployeeAction`
ревалидирует `/admin/employees` и редиректит на карточку нового
сотрудника `/admin/employees/[id]` — там менеджер при необходимости
доуточняет окладную пару (тот же паттерн, что у `createEquipmentAction`,
`createWarehouseAction`, `createOperationAction`).

#### Карточка `/admin/employees/[id]`

Три секции, каждая — Server Action:

1. **Реквизиты сотрудника** — read-only поля `fullName` / `login` /
   `role` + строка «Подразделение» (`Employee.companyDivision`,
   PHASE 2 STEP 2). Эти поля управляются вне управленческого блока
   (паспортная карточка приходит из `prisma/seed.ts`/будущей
   админки PIN-ов). Историческое поле `Employee.salaryBase`
   («месячный оклад») удалено в PHASE 2 STEP 1 — payroll-движок
   его никогда не использовал.
2. **Оплата за смену** — точечная форма для `compensationType`,
   `salaryPerShift`, `active`, `companyDivisionId` (PHASE 2 STEP 2).
   Источник истины — `PATCH /api/employees/:id`. Поведение:
   - выбран `PIECEWORK` → поле «Ставка за смену» скрывается
     (visual hint: «Сдельщик не получает дневной оклад»);
   - выбран `SALARY` или `MIXED` → поле «Ставка за смену»
     обязательное и `> 0`. Если оставить пустым — backend вернёт
     `EMPLOYEE_SALARY_RATE_REQUIRED` (422), форма покажет ошибку под
     полем (`useFormState` + bubble error);
   - чекбокс «Активен» — soft-disable. Текущая открытая смена не
     закрывается (см. `api.md §3b`), но новые `SalaryEntry` уже
     не создаются.
   - select «Подразделение» (PHASE 2 STEP 2) — пустое значение
     стирает привязку (`companyDivisionId = null`), любая активная
     карточка `CompanyDivision` ставит её. Soft-deleted
     подразделение, если оно сейчас на сотруднике, остаётся в
     списке с пометкой `(отключено)` — менеджер видит «откуда»
     убирает привязку. Если у проекта нет ни одного активного
     подразделения, select прячется. Backend: 404
     `COMPANY_DIVISION_NOT_FOUND` для несуществующего id, 409
     `COMPANY_DIVISION_INACTIVE` для soft-deleted.
3. **Последние окладные начисления** — таблица из
   `GET /api/salary?employeeId=...&pageSize=10`: *дата* · *сумма* ·
   *исправлено вручную?* · *комментарий менеджера*. Менеджеру удобно
   сразу проверить, что ставка приехала туда, куда нужно. Если
   записей нет — пустой стейт «Окладных начислений пока нет».

#### UX-поведение при смене `compensationType`

- Изменение selectа в форме сразу перерисовывает поле «Ставка за
  смену» (без PATCH-а): пользователь видит правильную форму до
  сохранения.
- При сохранении сервер атомарно валидирует пару
  `(compensationType, salaryPerShift)` — нельзя оставить
  `SALARY`/`MIXED` без ставки (см. `api.md §3b`).
- На успехе страница `revalidate`-ится, сводка «Последние окладные
  начисления» обновляется на следующем `start shift` (асинхронно).

### 10e. Маршруты производства (`/admin/routes`, soft-route MVP)

Управленческий каталог **шаблонов маршрутов**: упорядоченных
последовательностей операций, которые потом фиксируются snapshot-ом
на заказе при `start()`. Доменная модель — `domain.md §18`,
backend-контракт — `api.md §17`. Доступ — `SHOP_MANAGER` и
`ADMIN`; нав-бар админки и `app/admin/layout.tsx` показывают
пункт только этим ролям.

#### Список `/admin/routes`

- **Шапка** — заголовок «Маршруты производства», подзаголовок
  поясняет soft-route модель: при создании заказа можно привязать
  шаблон, при запуске он зафиксируется snapshot-ом, и UI на `/work`
  будет подсказывать швее текущий и следующий шаг. Scan «не туда»
  не блокируется. В правом краю — primary-кнопка
  **«Новый шаблон»** на `/admin/routes/new`.
- **Таблица** — `data-table`: «Код» (`<code>`), «Название»,
  «Активен», «Шагов» (если 0 — приглушённое «0 — пусто» с
  тултипом «snapshot не создастся»), «Обновлён», ссылка
  «Настроить →». Если шаблонов нет — пустой стейт со ссылкой на
  создание первого.

#### Создание `/admin/routes/new` и редактирование `/admin/routes/[id]`

Используют общую клиентскую форму `RouteTemplateForm` (одна и та
же UI-модель для create / edit). Header — `DetailPageHeader` со
своим back-link'ом «← К списку шаблонов».

Форма:

1. **Шапка формы** — поля `code` (валидация `^[A-Z0-9][A-Z0-9_-]*$`),
   `name`, чекбокс «Активен». Поля компактно живут в одной строке
   (`admin-equipment-form__meta`).
2. **Шаги маршрута** — раздел из двух частей:
   - **Выбранные шаги** — упорядоченный `<ol class="option-list">`
     с подписью «Шаг N» и кнопками **↑** / **↓** для смены порядка
     и **×** для удаления; на каждом шаге — чекбокс «опц.» (UI-only
     hint, MVP).
   - **«Добавить операции»** — свернутый `<details>` с чек-листом
     остальных активных операций (отсортированы по `sortOrder`).
     Отметить операцию = добавить шаг в конец списка.
3. **Submit** — единая кнопка «Создать шаблон» / «Сохранить
   изменения». Сохранение шагов идёт **полной заменой** набора (см.
   `api.md §17`); порядок шагов нормализуется по позиции в форме
   (`stepOrder[<id>]` → `index = i`).

В режиме `edit` под формой — секция **«Опасная зона»** с кнопкой
**«Удалить шаблон»**. В тексте предупреждаем: уже запущенные
заказы продолжают идти по своему snapshot-у — `OrderRouteStep[]`
самодостаточный и не зависит от шаблона. Для типового «убрать из
списка выбора» предлагаем снять чекбокс «Активен» в форме выше.

#### Использование шаблона на `/orders/new` и `/orders/:id/edit`

В формах создания и редактирования заказа появился селект
«Шаблон маршрута» (только активные, отсортированные по `name`).
Если шаблонов нет — селект скрывается, и заказ создаётся без
маршрута (полный backward-compat). На `/orders/:id/edit` опция
показывается ровно до запуска заказа в производство; после
`start()` snapshot фиксируется, и шаблон менять нельзя
(`ORDER_ROUTE_ALREADY_STARTED` 409).

#### Подсказка маршрута на `/work`

Подсказка по маршруту появляется в **двух** местах на /work — обе
read-only, обе ничего не блокируют (ТЗ `STEP 8`, soft-route MVP):

**1. В модалке проверки паспорта** (`PassportConfirmModal`, открывается
после скана QR паспорта перед нажатием «Принять»/«Завершить»). Под
блоком «Операция / Оборудование» текущей смены отрисовывается блок
маршрута заказа:

- **Сейчас**: «Шаг N: <Operation>» — `routeHint.currentRouteStep` из
  `OrderRouteStep` snapshot заказа.
- **Далее**: «Шаг N+1: <Operation>» или «— последний шаг маршрута».
- Если у заказа нет snapshot маршрута (`routeHint = null`) — блок не
  рендерится вообще, модалка остаётся в исходном виде.
- Warning при `routeHint.routeMismatchWithActiveShift = true`:
  «Внимание: ваша смена идёт на операции <X>, а маршрут заказа
  ожидает <Y>. Это подсказка, паспорт не блокируется». Кнопки
  «Принять» / «Завершить» остаются доступны.

Дополнительно (после soft-route MVP backend-фикса route-WIP без
ячейки, см. ниже подраздел «Route-WIP UX в /work»): рядом с номером
паспорта появляется компактный inline-бейдж **«Из маршрута»**, если
`Passport.currentRouteStepIndex !== null`. Если ячейки у паспорта при
этом нет (`currentCell = null` — типичный случай между маршрутными
шагами), вместо «склада» рисуется спокойный subtext **«Паспорт идёт
по маршрутному потоку — ячейка не требуется»** (`role="status"`,
без alert-семантики). Кнопка «Принять» по-прежнему disabled только
по `pending` — никакой блокировки на route-WIP / отсутствие ячейки.

**2. В блоке «Сейчас в работе»** (`current-work-card.tsx`) — для уже
принятых паспортов под обычными полями появляется тот же блок маршрута
с warning при mismatch со сменой. Источник данных —
`GET /api/shifts/current-work` (`routeCurrentStep` / `routeNextStep`).
Для route-WIP паспортов (`currentRouteStepIndex !== null`) рядом с
номером в шапке карточки показывается тот же inline-бейдж «Из
маршрута», чтобы оператор видел маршрутный контекст не только в
модалке проверки, но и в активной работе.

#### Route-WIP UX в /work (после backend-фикса route-WIP без ячейки)

Backend разрешает «Получить крой» для route-WIP паспорта без
обязательной `currentCell` (см. `PassportsService.issueToEmployee`,
`docs/domain.md §«Маршруты производства»`, `docs/flows.md §F3a`,
ветка B). UI /work симметрично подстроен по тому же критерию
`Passport.currentRouteStepIndex !== null`:

- Подсказки приёма стали нейтральными по складской модели:
  «Сканируйте QR паспорта — откроется проверка перед приёмом»
  (вместо прежнего «QR паспорта в ячейке»). Это работает и для
  legacy cell-based flow, и для маршрутного потока — backend сам
  выбирает ветку.
- Для CUTTER / админа / менеджера в дефолтной двухтабовой
  `ActiveShiftPanel` подсказка табы «Получить крой» теперь явно
  описывает обе ветки: «… если он лежит в ячейке, система спишет с
  ячейки; если идёт по маршруту, примет напрямую».
- Empty-state блока «Сейчас в работе» больше не упоминает ячейку —
  оператору одинаково удобно сканировать QR из ячейки или из руки.
- **Legacy сохранён.** Для заказов без маршрута (`currentRouteStepIndex
  IS NULL`) UI не рендерит бейдж «Из маршрута», не показывает subtext
  «ячейка не требуется», и backend по-прежнему просит ячейку
  (`PASSPORT_NOT_IN_CELL` — без изменений). Shelf-placement flow
  для CUTTER_ASSISTANT (`ShelfPlacementPanel`) тоже не меняется:
  ячейка остаётся возможным **опциональным буфером** маршрутного
  flow и обязательным якорем для no-route-заказов.

UI-критерий route-WIP единый и совпадает с серверным:
`currentRouteStepIndex !== null`. Прокидывание полей через server
action описано в `apps/web/app/work/state.ts`
(`PassportLookupResult.passport.currentRouteStepIndex` /
`currentCellCode`) и `actions.ts:lookupPassportAction`.

Источник истины для обоих мест — `OrderRouteStep` snapshot заказа +
`Passport.currentRouteStepIndex`. Конвенция «expected = currentRouteStep»
единая в обоих местах (см. `docs/api.md §17` и
`docs/domain.md §«Маршруты производства»`). Server-side enforcement
маршрута на MVP **не введён**: backend не возвращает 409 за «не туда
сканировал» и не disabled-ит кнопки.

### 10f. Техкарты (`/admin/tech-cards`, MVP техкарт)

Управленческий каталог **техкарт**: «потребности на единицу
изделия» (материалы + внешние подрядные размещения), которые потом
фиксируются snapshot-ом на заказе при `start()`. Доменная модель —
`docs/domain.md §19`, backend-контракт — `docs/api.md §18`,
архитектурное обоснование — ADR-0022. Доступ — `SHOP_MANAGER` и
`ADMIN`. Маршрут и техкарта — независимые оси: можно создать заказ
без техкарты, можно с техкартой без маршрута, можно с обоими.

#### Список `/admin/tech-cards`

- **Шапка** — заголовок «Техкарты», подзаголовок поясняет MVP-модель
  (snapshot потребностей на заказе при запуске, scan/маршрут не
  трогает). В правом краю — primary-кнопка **«Новая техкарта»** на
  `/admin/tech-cards/new`.
- **Таблица** — `data-table`: «Код» (`<code>`), «Название»,
  «Активна», «Материалов» (счётчик `materialLinesCount`),
  «Подрядов» (счётчик `outsourceLinesCount`), «Обновлена», ссылка
  «Открыть →». Пустой стейт — «Техкарт пока нет» с inline-ссылкой
  на создание первой.

#### Создание `/admin/tech-cards/new` и редактирование `/admin/tech-cards/[id]`

Используют общую клиентскую форму `TechCardForm` (одна и та же
UI-модель для create / edit). Header — `DetailPageHeader` со своим
back-link'ом «← К списку техкарт».

Форма:

1. **Шапка формы** — поля `code` (валидация по тому же стилю, что
   у `RouteTemplate.code`), `name`, чекбокс «Активна». Поля
   компактно живут в одной строке.
2. **Материалы** — список строк с кнопкой **«Добавить строку»**.
   Каждая строка — `name`, `unit`, `qtyPerUnit` (positive decimal),
   `note?`, кнопка **×** для удаления. Без drag-and-drop:
   порядок строк = порядок в форме, backend ставит `sortOrder` сам
   (`(index + 1) * 10`).
3. **Внешние потребности (подряд)** — те же controls + поле
   `vendorName?` и **`<select>` «Когда активировать»** (MVP-2
   техкарт, ADR-0022 §«Cut-ready readiness»). Опции:
   - «Вручную» (`MANUAL`, дефолт) — текущее поведение, никакого
     индикатора готовности на карточке заказа.
   - «Когда крой размещён в ячейки» (`CUT_READY`) — карточка
     заказа покажет derived-индикатор готовности по правилу
     ALL_PASSPORTS (см. §7.3, блок «Внешние потребности»).
   `unit` и `qtyPerUnit` опциональны (типичный кейс «подряд за
   партию»).
4. **Submit** — единая кнопка «Создать техкарту» / «Сохранить
   изменения». Сохранение строк — **полная замена** обоих списков
   (см. `api.md §18`); пустой массив = удалить все строки этого
   типа. Ошибки валидации показываются inline по полю строки.

В режиме `edit` под формой — пояснительный блок про независимость
snapshot-а: уже запущенные заказы продолжают идти по своему
`OrderMaterialRequirement[]` / `OrderOutsourceRequirement[]`. Для
типового «убрать из списка выбора» предлагаем снять чекбокс
«Активна» в форме выше — DELETE-эндпоинта сознательно нет (см.
`api.md §18`).

#### Использование техкарты на `/orders/new` и `/orders/:id/edit`

Селект «Техкарта» (только активные, отсортированные по `name`).
Если техкарт нет — селект скрывается, и заказ создаётся без
техкарты (полный backward-compat). На `/orders/:id/edit` опция
показывается ровно до запуска заказа; после `start()` snapshot
фиксируется, и менять `techCardId` нельзя (`409
ORDER_TECH_CARD_ALREADY_STARTED`). См. §7.4.

#### Чтение snapshot-а на `/orders/:id`

Блоки «Материалы» и «Внешние потребности» (см. §7.3). Источник
истины — snapshot заказа, а не live-шаблон. Empty-state «… не
зафиксированы» — нормальное состояние и для DRAFT, и для запущенных
заказов без техкарты.

### 10g. Display-экраны (`/admin/display-screens`)

Управленческий каталог больших мониторов цеха. Каждая запись — это
пара «`DisplayScreenConfig` + DISPLAY-учётка `Employee`». Контракт
API — `docs/api.md §11a`, доменная модель — `prisma/schema.prisma →
DisplayScreenConfig`. Доступ — `SHOP_MANAGER` и `ADMIN` (для
`DISPLAY` раздел не показывается ни в админ-панели, ни в шапке —
см. `apps/web/lib/rbac.ts`, `apps/web/middleware.ts`).

#### Список `/admin/display-screens`

- **Шапка** — заголовок «Display-экраны», подзаголовок поясняет
  модель «1 экран = 1 DISPLAY-учётка + 1 подразделение» и упоминает,
  что без `?divisionCode=` в URL `/shopfloor/display` теперь сам
  фильтруется по конфигу.
- **Action-кнопка** в правой части шапки: «Создать экран» — ссылка
  на `/admin/display-screens/new` (тот же UX, что у
  `/admin/employees`, `/admin/equipment`, `/admin/operations`).
- **Таблица** — колонки `Название`, `Подразделение`, `Логин дисплея`,
  `Активен`. Сортировка — по `createdAt DESC` (свежий сверху).
  Inactive-экраны выведены в отдельную мягкую секцию «Отключённые»
  с `opacity: 0.7`.
- **Empty-state** — «Пусто». Никаких заглушек или fake-данных.
- **Карточки экрана нет.** На MVP редактировать конфиг нельзя (это
  мини-фича: имя/подразделение/PIN правится через «удалить и
  создать заново»; тумблер `isActive` через UI пока тоже не
  выведен — меняется при необходимости через Prisma напрямую). Это
  сознательное упрощение по модели «универсальный экран-конфиг,
  простой create-flow».

#### Создание `/admin/display-screens/new`

- **DetailPageHeader** — eyebrow «Display-экран», заголовок «Новый
  display-экран», back-link «← К списку дисплеев».
- **Поля формы** (`apps/web/app/admin/display-screens/create-form.tsx`):
  - **Название экрана** (`name`, 2–120 символов) — для админ-листинга;
  - **Подразделение** (`companyDivisionId`, FK на `CompanyDivision`) —
    определяет `divisionCode`-фильтр для `/shopfloor/display` под
    этой DISPLAY-учёткой;
  - **Логин дисплея** (`login`, 2–64) — нормализуется в lower-case;
  - **PIN** (`pin`, 4–100) — храним только bcrypt-hash;
  - **Активен** (`isActive`, default `true`) — мягкий выключатель.
- **Submit** — «Создать экран». При успехе server-action
  `createDisplayScreenAction` зовёт `POST /api/display-screens`,
  ревалидирует список и редиректит обратно на
  `/admin/display-screens`. Локальные guards до сетевого round-trip
  перехватывают «логин короче 2», «PIN короче 4», «не выбрано
  подразделение» — менеджер получает понятную ошибку без 400.
- **Ошибки backend** показываются в `detail-form__error`. Ключевой
  кейс — `409 DISPLAY_LOGIN_TAKEN`: поле «Логин дисплея» подсвечивается
  понятным текстом, ничего в БД не создаётся (транзакция откатывает
  и `Employee`, и `DisplayScreenConfig`).
- **«Привязать к существующему DISPLAY-сотруднику» отсутствует
  принципиально.** В `/admin/employees/new` роль `DISPLAY` тоже
  скрыта (см. §10d, `EMPLOYEE_ROLES`); единственный поддерживаемый
  путь завести DISPLAY-учётку — это эта форма.

#### Use-case (зачем экраны)

1. SHOP_MANAGER заходит в `/admin/display-screens/new`, заполняет
   «ТВ маркетплейс / `MARKETPLACE` / `display-mp` / `1234`» и жмёт
   «Создать».
2. Backend одной транзакцией создаёт `Employee(role=DISPLAY)` и
   `DisplayScreenConfig`. Менеджер записывает себе логин и PIN.
3. На физическом мониторе у входа цеха он логинится под `display-mp`.
   `apps/web/middleware.ts` сразу уводит DISPLAY-роль на
   `/shopfloor/display` и не пускает её ни на одну другую страницу.
4. Страница `/shopfloor/display` шлёт `GET /api/shopfloor/display`
   (без `?divisionCode=`). Backend по cookie видит `role = DISPLAY`,
   находит `DisplayScreenConfig` по `employeeId` и сужает выборку
   до `companyDivision.code = MARKETPLACE`. Никаких URL-настроек на
   TV-панели менять не нужно.

### 10h. Настройки компании (`/admin/company-settings`)

Единый экран для двух независимых сущностей:

- **Реквизиты организации** (`CompanySettings`, singleton) — три
  карточки:
  - «Реквизиты организации» — полное/краткое название, ИНН (10/12),
    КПП (9), ОГРН (13/15), юридический и фактический адрес.
  - «Контакты и руководители» — телефон, email, ФИО директора и
    главного бухгалтера.
  - «Банковские реквизиты» — название банка, БИК (9), расчётный
    счёт (20), корреспондентский счёт (20).

  Все поля идут в один PATCH `/api/company-settings` и Submit «Сохранить»
  внизу формы. Идемпотентный PATCH (без реальных изменений) аудит-строку
  не плодит.

- **Подразделения** (`CompanyDivision`) — карточка-таблица:
  - Колонки: «Код» (моноширинно), «Название», «Описание», «Порядок»,
    «Статус», действия.
  - Кнопка «Добавить подразделение» в шапке секции раскрывает inline-
    форму создания (без ухода в отдельный URL — подразделений мало,
    отдельная detail-страница не оправдана).
  - Каждая строка имеет inline-кнопку «Изменить» (раскрывает inline-
    форму редактирования) и кнопку «Отключить» / «Включить» (отдельная
    `<form>` без useFormState, server action возвращается на ту же
    страницу). Hard-delete сознательно нет.

Шапка экрана — стандартный `AdminPageShell` с иконкой `Settings`,
заголовком «Настройки компании» и подзаголовком «Реквизиты
организации, контакты, банк и подразделения».

RBAC — `SHOP_MANAGER` / `ADMIN` (на backend), плюс `app/admin/layout.tsx`
редирект остальных. Pinned-ссылка «Настройки» (иконка `Settings`)
живёт в футере sidebar — рядом с кнопкой «Выйти», и в десктоп-, и в
мобильном sidebar (`apps/web/components/admin-sidebar.tsx`). В
основном `SECTIONS`-списке навигации её нет — это сознательное
решение, чтобы доменные разделы не разбавлялись «настроечной»
страницей.

Доменные правила — `docs/domain.md §16`, контракт API —
`docs/api.md §42`, ER — `docs/erd.md §2.15`.

> **CompanyDivision = master-справочник подразделений.**
> Подразделения, заведённые здесь, являются источником истины для
> поля «Подразделение» в карточках заказа (`Order.companyDivisionId`)
> и в конфиге display-экранов (`DisplayScreenConfig.companyDivisionId`).
> Базовые карточки `MARKETPLACE` / `OTHER` гарантированно созданы
> миграцией и seed-ом — менеджер их видит, может переименовать.
> `EarningsService` использует `code` для выбора схемы начисления
> закройщика (см. `getCutterCompensationSchemeForDivision`), поэтому
> переименование `code` карточек `MARKETPLACE` / `OTHER` сломает
> marketplace-flow. См. `docs/domain.md §«Подразделения заказа»` и
> `docs/erd.md §«CompanyDivision»`.

## 12. Зарплата (`/earnings`) — Шаг 9 MVP

Минимальный экран на просмотр сдельных начислений (`OperationEntry`).
Реализовано: `apps/web/app/earnings/page.tsx`. Контракт API —
`docs/api.md §10`. Бизнес-правила и моменты создания/подтверждения —
[ADR-0005](./adr/0005-salary-timing.md), идемпотентность —
[ADR-0012](./adr/0012-earning-deduplication.md).

### 12.1. `/earnings` (список + сводка)

Экран двухрежимный: менеджерский (`SHOP_MANAGER`, `ADMIN`) и личный
кабинет «Мои начисления» для всех остальных ролей. Backend сам режет
данные по правам (см. `docs/api.md §10` — RBAC видимости), UI лишь
адаптирует подачу.

**Менеджерский режим (`SHOP_MANAGER` / `ADMIN`):**

- **Шапка** с пояснением: «Раскройщик подтверждается сразу при выпуске
  паспорта, пошив — после упаковки. Окладные роли (ОТК, помощник
  раскройщика, упаковщики, ВТО) сюда не попадают (см. ADR-0005)».
- **Сводка** (три карточки) из `GET /api/earnings/summary`:
  *Подтверждено* (`totalApproved`, `countApproved`), *Ожидает выпуск*
  (`totalPending`, `countPending`), *Всего* (сумма + количество).
  Считается по тем же фильтрам, что и таблица.
- **Фильтры** (отправляются GET-формой, без JS):
  - сотрудник — select со всеми активными `Employee` из `GET /api/shifts/meta`;
  - статус — `PENDING_RELEASE` / `APPROVED` / `REVERSED` (последний
    зарезервирован, на MVP не выставляется);
  - период — `dateFrom` / `dateTo` (`<input type="date">`), сравнивается
    с `OperationEntry.createdAt`.
- **Таблица** из `GET /api/earnings`: *дата* (createdAt + ✓ approvedAt,
  если отличается) · *сотрудник* · *операция* (имя + код) · *паспорт*
  (ссылка на `/passports/[id]` + номер заказа) · *размер* · *кол-во* ·
  *ставка, ₽* · *сумма, ₽* · *статус* (бейдж). Сортировка — `createdAt DESC`.
- **Пагинация** — `page=N` в query, по 50 строк (`pageSize=50`),
  кнопки «← Назад» / «Вперёд →».
- Если ничего не нашлось — заглушка с подсказкой про триггеры
  (выпуск паспорта / сканирование).

**Личный режим (любая не-менеджерская роль):**

- Заголовок — «Мои начисления»; шапка-пояснение объясняет, что в
  списке только свои подтверждённые суммы.
- Сводка сворачивается в **одну** карточку «Подтверждено» — обычный
  сотрудник не должен даже визуально видеть, что в системе бывают
  чужие или неподтверждённые начисления.
- Фильтр по сотруднику и фильтр по статусу **не отображаются**;
  доступен только период (`dateFrom`/`dateTo`). Любые `employeeId`/
  `status` в query игнорируются и не пробрасываются в API.
- В таблице нет колонок «Сотрудник» и «Статус» — все строки и так
  свои и `APPROVED`.

### 12.2. Блок «Начисления» в `/passports/[id]`

Под блоком ОТК и над «Размещение в ячейке». Показывает срез по одному
паспорту через `GET /api/passports/:id/earnings`. Так же двухрежимный:

- **Менеджер (`SHOP_MANAGER` / `ADMIN`).** Заголовок «Начисления»,
  три суммы сверху (Подтверждено / Ожидает выпуск / Всего), таблица
  c колонками *дата* · *сотрудник* · *операция* · *кол-во* · *ставка* ·
  *сумма* · *статус*. Если начислений нет — заглушка со ссылкой на
  `/earnings`.
- **Обычный сотрудник.** Заголовок «Мои начисления по паспорту», одна
  сумма «Подтверждено», таблица без колонок «Сотрудник» и «Статус».
  Если по этому паспорту своих подтверждённых строк нет — аккуратный
  empty state «у вас по паспорту пока нет подтверждённых начислений»,
  без подсветки факта чужих строк.

### 12.3. Окладные начисления в `/earnings` (ADR-0021)

Под таблицей сдельных начислений на той же странице `/earnings`
показывается отдельный блок **«Окладные начисления»**. Источник
данных — `GET /api/salary` + `GET /api/salary/summary` (см.
`api.md §10a`). Двухрежимность та же — backend сам режет данные
по правам.

- **Сводная карточка наверху страницы** включает окладную сумму
  отдельной строкой («Оклад: N₽ за M дней»), чтобы менеджер видел
  итог по обеим частям одновременно.
- **Таблица** под сдельной частью: *дата* · *сотрудник* (только в
  менеджерском режиме) · *тип* (всегда «Оклад за смену» —
  `source = SHIFT_DAY`) · *сумма* · *исправлено вручную?* (бейдж
  «Исправлено вручную» с tooltip-ом `editedByFullName + updatedAt`,
  если флаг стоит) · *комментарий менеджера* · *действия*.
- **Действия (только `SHOP_MANAGER` / `ADMIN`)** — инлайн-компонент
  `SalaryEntryEditor`:
  - кнопка **«Исправить»** разворачивает форму с двумя полями
    (`amount` + `managerComment`) и кнопкой «Сохранить». Server
    action дёргает `PATCH /api/salary/:id` с переданными полями;
    `editedManually` поднимается на `true` автоматически. Ошибки
    backend-а (`SALARY_RATE_MISSING`, `VALIDATION_ERROR`) выводятся
    под формой через `useFormState`.
  - кнопка **«Вернуть в авто»** видна только для записей с
    `editedManually = true` и сразу шлёт `PATCH /api/salary/:id
    { reset: true }`. После reset запись снова синхронизируется с
    `Employee.salaryPerShift` на ближайшем `start shift`.
- В личном режиме (не-менеджер) колонок «Сотрудник» и «Действия»
  нет, как и кнопок «Исправить»/«Вернуть в авто» — рабочий
  сотрудник видит только свои окладные суммы и может прочитать
  комментарий менеджера, но не редактирует ничего.
- Если окладных строк нет — пустой стейт «Окладных начислений за
  этот период нет. Записи появляются автоматически, когда
  сотрудник с `compensationType ∈ { SALARY, MIXED }` начинает
  смену».

### За рамками Шага 9 MVP (на UI)

- Ведомость за месяц / экспорт в Excel/PDF.
- Учёт часов и half-day для окладных ролей (на MVP — плоская
  ставка за день, см. ADR-0021).
- Отмена/коррекция сдельных начислений (`REVERSED` создаётся только
  будущим flow возврата паспорта в производство).
- Drill-down по «виновной операции» брака.

## 17. Себестоимость выпуска (`/production-cost`)

Управленческая read-only страница. Контракт API — `api.md §17`,
бизнес-правила — `domain.md §17`.

Доступ — `SHOP_MANAGER`, `ADMIN`. Layout (`apps/web/app/production-cost/
layout.tsx`) самостоятельно проверяет роль через `canSeeProductionCost`
и редиректит остальных на `/`. Backend (`/api/costs/production`)
тоже защищён `@Roles('SHOP_MANAGER', 'ADMIN')` — это страховка от
прямых API-вызовов и от бага в RBAC-хелпере.

В навигации страница появляется как:

- пункт «Себестоимость» в шапке (`apps/web/app/layout.tsx`);
- тайл «Себестоимость» на главной плитке менеджера (`apps/web/app/page.tsx`).

### Содержимое страницы

1. **Заголовок и пояснение.** Что такое «себестоимость» в этой
   системе (sum piecework + распределённый оклад) и как считается
   простой (отдельная строка, не входит в себестоимость изделия).
   Подсвечивается активный период (например, «2026-04-01 — 2026-04-14»).
2. **Summary-карточки** (4 штуки):
   - Выпущено (шт);
   - Себестоимость (₽), снизу — разбивка `pieceworkCost / salaryCost`;
   - Себестоимость / шт (₽), снизу — `trackedMinutes`;
   - Простой (₽), снизу — `idleMinutes`.
3. **Фильтр периода.** Два `<input type="date">` — `dateFrom` и
   `dateTo`. Submit — обычный GET, страница серверная (`force-dynamic`).
4. **График динамики** (`production-cost-chart.tsx`). Лёгкий SVG-чарт
   без внешних зависимостей. Три серии:
   - выпущено (шт, зелёная);
   - себестоимость (₽, синяя);
   - простой (₽, красная).
   Y-шкалы у серий разные (штуки vs рубли) — каждая нормируется в
   `[0..1]` от своего max, чтобы линии были сопоставимы на одном
   холсте. Точные числа — в таблице ниже.
5. **Таблица по дням.** Колонки: дата, выпущено, себестоимость,
   сдельщина, оклад (распред.), учтено мин, простой мин, простой ₽.

### UX-инварианты

- Период всегда возвращается полным: дни без событий показываются
  с нулями, чтобы график не «прыгал». Backend гарантирует это в
  `CostsService.getProductionCost`.
- Все суммы форматируются как `XX XXX,XX ₽` (`ru-RU` locale).
- Данные read-only: ни одного `POST/PATCH` со страницы не идёт.
- Drill-down (по сотруднику / по паспорту) — за рамками MVP.
  Сейчас экран отвечает на единственный вопрос «как себя ведёт
  выпуск и простой по дням», без объяснения «почему».

## 18. Дашборд начальника производства (`/admin/production-dashboard`)

Единый управленческий экран. Контракт API — `api.md §11b`,
бизнес-правила — `domain.md §17`.

Доступ — `SHOP_MANAGER`, `ADMIN`. Layout `/admin/*`
(`apps/web/app/admin/layout.tsx`) проверяет роль через `canSeeAdmin`
и редиректит остальных. Backend (`/api/dashboard/production`) тоже
защищён `@Roles('SHOP_MANAGER', 'ADMIN')`.

Назначение — собрать на одном экране ответы на ключевые вопросы
начальника производства, чтобы не приходилось вручную обходить
`/shopfloor`, `/production-cost`, `/admin/overview`, `/earnings` и
`/admin/employees`:

1. Что выпустили?
2. Что сейчас в работе?
3. Где простой?
4. Где узкое место?
5. Сколько стоит выпуск?

В навигации страница появляется как:

- пункт «Дашборд» в шапке (`apps/web/app/layout.tsx`, для
  `SHOP_MANAGER`/`ADMIN`);
- крупный primary-тайл «Дашборд начальника» на главной плитке
  менеджера (`apps/web/app/page.tsx`).

### Содержимое страницы (порядок фиксирован)

1. **Шапка** — заголовок, пояснение «KPI «сегодня» считаются по
   UTC-сегодня; график и сводки за период — за `N` дней
   (`dateFrom — dateTo`)», момент обновления, переключатель периода
   `7 / 14 / 30` дней (`?days=`).
2. **KPI-карточки.** Шесть крупных summary:
   - Выпущено сегодня (шт) + сноска «… за период»;
   - В работе сейчас (шт + кол-во паспортов);
   - Заказы в производстве (шт);
   - Себестоимость / шт сегодня (₽) + сноска «… ₽ за период»;
   - Простой сегодня (₽) + сноска «… ₽ за период», подсветка красным
     при `> 0`;
   - Загрузка цеха сегодня (%), цвет: зелёный ≥ 60, серый 30–59,
     красный < 30.
3. **Pipeline — где сейчас изделия.** Карточки по стадиям
   `CUT · SEWING · QC · QC_DONE · WTO · WTO_DONE · PACKING · FINISHED`
   и пунктирная карточка «Брак». Bottleneck-стадия выделена красной
   рамкой. Внизу строка-подпись «Узкое место: …». Ссылка «Открыть
   `Цех` →».
4. **Динамика по дням.** Лёгкий SVG-чарт `trend-chart.tsx` (без
   внешних зависимостей). Три серии: выпуск (шт, зелёная),
   себестоимость (₽, синяя), простой (₽, красная). Шкалы независимые
   (см. `production-cost-chart.tsx` в §17 — здесь та же логика).
5. **Загрузка по ролям (день `dateTo`).** Таблица `ОТК / ВТО /
   Упаковка`, колонки: окладников, оплачено мин, учтено мин, простой
   мин, простой ₽, загрузка %. `idleCost > 0` — красным.
6. **Требует внимания.** Список карточек-алертов (см. `api.md §11b`).
   Цветной dot и сумма справа; алерт может быть ссылкой
   (`PIPELINE_BOTTLENECK → /shopfloor`, `PEAK_IDLE_DAY → /production-cost`).
   Если алертов нет — empty-hint «Сегодня всё спокойно».
7. **Быстрые переходы.** Ссылки-кнопки `Цех / Себестоимость / Зарплата
   / Сотрудники / Операции / Склад / Заказы / Операционный обзор`.

### UX-инварианты

- Backend = источник истины. Страница ничего не пересчитывает
  (никаких манипуляций с `OperationEntry` / `SalaryEntry` /
  `PassportEvent` на клиенте) — UI делает только разметку.
- Все суммы — `XX XXX,XX ₽` (`ru-RU` locale); даты — `DD.MM.YYYY` /
  `DD.MM` на тиках графика.
- Данные read-only: ни одного `POST/PATCH` со страницы не идёт.
- Поллинга нет: страница серверная (`force-dynamic`), переходом по
  ссылке `?days=` или ручным refresh-ом начальник управляет
  обновлением осознанно (та же логика, что у `/admin/overview`,
  см. §10 и `api.md §11a`).
- Любой блок может оказаться пустым (без выпуска / без смен / без
  алертов) — каждый рендерит свой empty-hint, чтобы экран не
  выглядел «сломанным».
- Существующие экраны (`/shopfloor`, `/production-cost`,
  `/admin/overview`, `/earnings`) дашборд не заменяет — только
  склеивает обзор и ведёт в них через quick-actions.

## 10c. Detail-page standard (UI Refresh v2)

После того как list/overview-экраны (`/`, `/admin/production-dashboard`,
`/production-cost`, `/earnings`, list-страницы справочников) приведены к
modern visual layer, аналогичный canonical-стандарт распространён и на
**detail-страницы** — все они теперь делятся одним каркасом.

### Каноническая структура detail-page

Каждая detail-page (employee, operation, warehouse, equipment, passport,
box, qc passport — всё, что является «карточкой одной сущности»)
собирается из:

1. `page-shell` — внешний flex-column контейнер.
2. **Hero / шапка** через общий компонент
   `components/detail-page-header.tsx` (`<DetailPageHeader …>`):
   - `back-link` к списку (опционально),
   - `page-eyebrow` + иконка раздела (`Сотрудник`, `Операция`, `Склад`,
     `Оборудование`, `Паспорт`),
   - `page-title` + та же иконка (UI самодокументируется),
   - `page-subtitle` (контекст для менеджера: что вообще делает экран),
   - `meta-line` (код, login, даты, qty),
   - `badges` (`pill` / `status-badge` для статусов),
   - `actions` справа (Печать, основная кнопка действия).
3. Один или несколько **секций-карточек** (`section`/`AppSectionCard` /
   `card`) с `section-header` внутри (иконка + заголовок + хинт справа).
4. **Формы** строятся через единый класс `detail-form`:
   - `.detail-form__grid` для двух/трёх колонок,
   - `.detail-form__field` для label+control пары,
   - `.detail-form__field--inline` для checkbox+label,
   - `.detail-form__hint` под группой полей,
   - `.detail-form__actions` — кнопочный ряд внизу,
   - `.detail-form__success` / `.detail-form__error` (с иконкой и
     `requestId`-плашкой) — единые success/error блоки.
5. **Таблицы внутри карточек** оборачиваются в
   `.inline-table-wrap` + используют общий `.data-table` (те же
   header/row hover/num-выравнивание, что на list-страницах).
6. **Action-rows** — `.table-actions` (кнопки в одной ячейке таблицы),
   `actions-row` (под формой), `.danger-zone` (опасные операции).
7. **Empty states** — `.empty-state` с иконкой + заголовком + хинтом.
8. **Pricing-mode / option-list / rate-table-grid** — специальные
   primitives для операций и оборудования (см. ниже).

## 11. Общие UI-правила

- Дизайн-токены и принципы — [`docs/ui-mobile.md`](./ui-mobile.md).
  Используем переменные из `:root { … }`, без хардкода цветов.
- Крупные тач-цели (≥ 44 px на любом интерактиве; ≥ 56 px на основных

## 18. `/admin/printers` — управление принтерами и печать через агент (MVP)

См. `docs/domain.md §17b`, `docs/api.md §16`, `apps/agent/README.md`.

### `/admin/printers` (список)

Доступ: `SHOP_MANAGER`, `ADMIN`. В шапке навигации — отдельный пункт
«Принтеры».

- **Primary-кнопка «Добавить принтер»** — в правом краю шапки списка
  (`admin-overview__actions`), ведёт на отдельную страницу
  `/admin/printers/new`. Тот же UX уже применён к `/admin/equipment`
  (ADR-0017), `/admin/operations` (ADR-0020) и `/admin/warehouses` —
  раньше форма создания жила прямо в списке и визуально его
  перегружала.
- **Таблица «Список»** — для каждого принтера:
  - имя (ссылка на карточку);
  - тип;
  - привязка к рабочему месту (имя + код, ссылка на
    `/admin/equipment/:id`) или «не привязан»;
  - статус: pill `онлайн` (зелёный) / `офлайн` (серый) +
    `lastSeenAt`;
  - количество PENDING-job-ов в очереди.

### `/admin/printers/new` (создание)

Отдельный detail-экран со своим header'ом и back-link'ом «К списку
принтеров» (тот же `DetailPageHeader`, что и у `/admin/equipment/new`,
`/admin/warehouses/new`). Форма — `CreatePrinterForm` (`name`,
`type` (`PASSPORT`/`QR`/`LABEL`/`DEFAULT`), `equipmentId` —
select из `/api/equipment` с опцией «— без привязки —»). Submit
→ server action `createPrinterAction` → `POST /api/printers` →
редирект на `/admin/printers/:id` нового принтера, чтобы менеджер
сразу сгенерировал `pairingCode` и подключил агент.

Если `/api/equipment` отвалился — страница не падает, рендерим
форму с пустым select-ом и сообщением «можно создать без привязки и
доцепить позже на карточке». RBAC прежний: `app/admin/layout.tsx`
пускает только `ADMIN`/`SHOP_MANAGER`, backend независимо защищает
`POST /api/printers` через `@Roles('SHOP_MANAGER', 'ADMIN')` (см.
`docs/api.md §16`).

### `/admin/printers/:id` (карточка)

Карточки-секции (одна страница):

1. **Параметры** — форма `PATCH /api/printers/:id`:
   `name`, `type`, `equipmentId`, чекбокс `isActive`. Pre-existing
   паттерн `detail-form` (см. equipment).
2. **Подключение агента** — текущий `pairingCode` крупно, кнопка
   «Сгенерировать код» (`POST /api/printers/:id/pairing-code`) и
   кнопка «Скачать агент (Windows .exe)» (ссылка на `GET
   /api/printers/agent-download/sewing-print-agent.exe`,
   `download="sewing-print-agent.exe"`). Под кнопкой — короткая
   инструкция оператору (`sewing-print-agent.exe --pair --server <URL>
   --code <CODE>`, затем `sewing-print-agent.exe`); упоминаются папки
   `spool/`, `printed/`, `failed/`, которые агент создаёт рядом с exe.
   Сборка exe — `cd apps/agent && npm run build:win`
   (`apps/agent/README.md`).
3. **Физический принтер Windows** — отдельный блок,
   `apps/web/app/admin/printers/[id]/windows-printer-form.tsx`.
   Показывает:
   - `agentHostName` («Подключённый компьютер: `QC-PC-01`») и pill
     «онлайн / офлайн» с относительным `lastSeenAt`;
   - текущий `selectedWindowsPrinter` (badge) и
     `windowsPrintersUpdatedAt` («список от 2026-04-20 14:32»);
   - `<select>` «Печатать на:» с опциями из `availableWindowsPrinters`
     + опция «— не выбран —» (значение `""`, означает `null`);
   - кнопка «Сохранить выбор» — server action
     `selectWindowsPrinterAction` → `PATCH /api/printers/:id
     { selectedWindowsPrinter }`. Если backend ответил
     `WINDOWS_PRINTER_NOT_FOUND_FOR_AGENT` — показываем сообщение,
     просим запустить агент рядом с принтером и обновить страницу.

   Empty-state: если `availableWindowsPrinters` пуст — текст
   «Агент ещё не прислал список системных принтеров. Запустите
   `sewing-print-agent.exe` на Windows-машине рядом с принтером».
   Если агент офлайн, но `availableWindowsPrinters` непустой —
   показываем последний известный список и предупреждение «агент
   офлайн, печать сейчас не пойдёт».
4. **Тестовая печать** — `POST /api/print-jobs { sourceType: 'TEST',
   printerId }`. Возвращает `PrintJob`, статус которого вскоре станет
   `PRINTED` или `FAILED` — менеджер видит это в секции «Последние
   задания» (после revalidate). Если `selectedWindowsPrinter` ещё
   не выбран, агент сразу закроет job как `FAILED` с понятным
   `errorMessage`.
5. **Последние задания** — таблица `GET /api/print-jobs?printerId=&limit=20`,
   колонки: `createdAt`, `sourceType + sourceId`, `status` (pill),
   `completedAt`, `errorMessage`.
6. **Опасная зона** — кнопка «Удалить принтер» (с native `confirm`).
   `DELETE /api/printers/:id`, каскадно удаляет историю заданий.

### Кнопка «Печать» в системе

Существующие кнопки печати (паспорт, QR, этикетка коробки, QR ячейки)
**не убираем и не переименовываем** — заменяем только их поведение
на компонент `<PrintButton sourceType="…" sourceId="…" fallbackHref="…">`
(см. `apps/web/components/print-button.tsx`):

- сначала `POST /api/print-jobs { sourceType, sourceId }` →
  backend сам выберет принтер по активной смене сотрудника;
- если backend ответил `PRINTER_NOT_CONFIGURED_FOR_EQUIPMENT` или
  `SHIFT_SESSION_REQUIRED` — открываем `fallbackHref` в новой
  вкладке. Это сохраняет совместимость на тех рабочих местах, где
  агент ещё не настроен;
- иначе — короткий toast «Отправлено на принтер рабочего места»
  / «Не удалось отправить на печать».

RBAC: рабочие роли видят только кнопку «Печать» (без `printerId`).
Тестовая печать с явным `printerId` доступна только из
`/admin/printers/:id`.
