## Pilot Rollout Plan

> Этап Pilot Rollout / UAT / Bugfix Sprint. Цель — провести пилот системы
> в реальном цехе, собрать обратную связь, починить блокирующие баги,
> довести UX до «цехового уровня». Это НЕ разработка новых бизнес-фич:
> всё уже реализовано в Шагах 1–11 MVP (см. `docs/index.md`).

---

### 1. Цель пилота

Подтвердить, что система:

1. реально используется в цехе на 3–5 пользователях;
2. выдерживает живые сценарии (заказ → паспорт → ячейка → крой → пошив →
   ОТК → ВТО → упаковка → выпуск → начисление);
3. понятна сотрудникам без сопровождения разработчика;
4. не падает при базовых действиях (двойной скан, повторная упаковка,
   попытка работы без смены и т. п.);
5. даёт цифры, совпадающие с фактом
   (`order.summary`, `earnings`, `shopfloor`).

Главный KPI пилота — **полный цикл проходит без блокирующих багов**.

---

### 2. Длительность

5–7 рабочих дней. Допускается удлинение, если в первые 2 дня нашли много
critical-багов и не успели их закрыть.

| День | Активность                                                              |
| ---- | ----------------------------------------------------------------------- |
| -1   | Развёртывание stage/prod, прогон seed, печать QR оборудования и ячеек   |
| 0    | Onboarding (1 час): прогон сценариев, выдача учёток                     |
| 1–2  | «Шёлковый запуск»: 1 заказ, 5 паспортов, ручной контроль                |
| 3–5  | Полная нагрузка: реальные заказы, цех работает обычным образом          |
| 6–7  | Bugfix sprint, ретро, Go/No-go                                          |

---

### 3. Состав пилота

| Роль                 | Кол-во | Задача                                                                  |
| -------------------- | ------ | ----------------------------------------------------------------------- |
| Начальник цеха       | 1      | Создаёт заказ, наблюдает на `/shopfloor`, согласовывает зарплату        |
| Помощник раскройщика | 1      | Выпускает паспорта, печатает, кладёт в ячейку (`/orders → /passports`)  |
| Швея                 | 1–2    | Старт смены, выдача кроя, скан паспортов на операциях (`/work`)         |
| ОТК                  | 1      | Фиксирует брак (`/qc`)                                                  |
| Упаковщик            | 1      | Создаёт коробку, добавляет паспорта, закрывает (`/packing`)             |

Рекомендуется ОДНА смена в день. Двухсменная работа — после пилота.

---

### 4. Критерии успеха

Пилот пройден, если за 5–7 дней одновременно выполнены:

- минимум 5 паспортов прошли путь `CREATED → PACKED`;
- нет открытых багов с критичностью `critical`;
- все ключевые действия делаются без вопросов «что нажать»;
- цифры в карточке заказа (`/orders/:id`), на «Цехе» (`/shopfloor`)
  и в зарплате (`/earnings`) совпадают с фактом и между собой
  (`qtyCutFact == Σ Passport.qtyCut`,
  `qtyFinishedTotal == Σ qtyGood по PACKED`);
- система не падает при типовых стресс-сценариях (двойной скан,
  повторное добавление в коробку, попытка скана без смены);
- есть актуальная документация запуска (этот файл + `onboarding.md`
  + `operator-checklist.md`).

---

### 5. Что считаем «блокирующим багом» (`critical`)

Любой из:

1. Невозможно завершить полный цикл (`CREATED → PACKED`).
2. Расхождение цифр в `order.summary` и факте `Σ Passport.*`.
3. Двойное начисление зарплаты или «пропавшее» начисление.
4. Невозможно войти в систему / открыть смену / отсканировать паспорт.
5. Падение API на 5xx без понятной причины.

Любая `critical`-проблема немедленно эскалируется в `feedback.md` и
фиксится в тот же день (см. § 8 «Bugfix sprint»).

---

### 6. Pre-flight checklist (за 1 день до пилота)

- [ ] `npm run prisma:migrate` применён на stage/prod;
- [ ] `npm run db:seed` выполнен (демо-учётки и базовые ставки на месте);
- [ ] переменные окружения проверены (`JWT_SECRET`, `APP_URL`, `API_URL`,
      `CORS_ALLOWED_ORIGINS`) — см. `.env.example`;
- [ ] напечатаны и наклеены QR-коды:
      оборудования (`equipment:{id}`), ячеек (`cell:{id}`);
- [ ] заведены реальные сотрудники в `/admin/employees` (или временно
      используем демо-учётки `seamstress`, `cutter-helper`, `qc`,
      `packer`, `shop-chief` с паролем `Demo12345!`);
- [ ] заведены piece rates на все актуальные пары
      (operationCode, sizeCode) — иначе создание паспорта вернёт
      `PIECE_RATE_NOT_FOUND` 422;
- [ ] открыты `https://stage.teeon.ru` и `/api/health` — отвечают 200;
- [ ] на каждом рабочем месте проверен сканер QR (камера телефона /
      USB-сканер) и печать паспорта (`/api/passports/:id/print`).

---

### 7. Health monitoring во время пилота

- `GET /api/health` — liveness, должен возвращать `200 ok`.
- `GET /api/ready` — readiness, проверяет PostgreSQL.
- `GET /api/admin/overview` — лёгкая операционная сводка для начальника
  цеха (см. `docs/api.md §11a`): активные смены, открытые коробки,
  паспорта в работе/в ячейках, события за сегодня. Удобный UI —
  `/admin/overview`.

Все ошибки API (4xx/5xx) включают `requestId` (uuid) — этот id видно в
красной плашке UI и в логах сервера. При обращении в поддержку
пользователь сообщает `requestId` — это сразу даёт нужную строку лога.

---

### 8. Bugfix sprint

Параллельно пилоту работает однопоточный bugfix sprint:

1. Каждое утро (10:00) — короткое стендап-ревью `feedback.md`.
2. `critical` — фиксится в тот же день, без обсуждения новых фич.
3. `medium` — фиксится в течение пилота.
4. `low` — попадает в backlog «после пилота».

Все правки — минимальные PR; новых модулей и архитектурных решений в
этот этап не вводим (см. ADR-0001…0016).

---

### 9. Go / No-go

В конце пилота — короткое решение:

- **Go (полный запуск)** — все критерии § 4 выполнены, нет открытых
  `critical`-багов, есть согласие у начальника цеха на ежедневное
  использование.
- **Soft go** — § 4 выполнены, но есть `medium`-баги; запуск идёт, баги
  фиксятся в течение 1–2 недель.
- **No-go** — есть открытые `critical`-баги или система не вписывается в
  цеховой ритм. Возвращаемся в пилот ещё на 3–5 дней.
