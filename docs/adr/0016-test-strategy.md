# ADR-0016. Стратегия тестов MVP 1.1

- Статус: Принято
- Дата: 2026-04
- Контекст: MVP 1.1 / Stabilization

---

## 1. Контекст

В MVP 1.0 автоматизированных тестов не было: верификация шла руками
по сценариям из `flows.md`. Для внутреннего запуска нам нужен
минимально достаточный набор, который:

- ловит регрессии в ключевых производственных сценариях
  (заказ → паспорт → смена → ОТК → упаковка → начисления);
- проверяет, что критичные DB-инварианты реально живут в Postgres
  (см. ADR-0015), а не «существуют только в схеме»;
- не превращается в инфраструктурный проект — мы стабилизируем,
  а не строим новую тест-платформу;
- не ломает локальный `npm test` без работающей PostgreSQL.

## 2. Решение

1. **Один отдельный workspace `tests/`.** Не размазываем тесты
   по `apps/api` и `apps/web`: в монорепо удобнее иметь общую тест-
   точку входа, которая видит и API-исходники, и shared-пакет.
2. **Vitest + supertest + `@nestjs/testing`.** Vitest — самый легковесный
   рантайм с хорошим watch-режимом; `@nestjs/testing` поднимает
   реальный `AppModule`, `supertest` стучит в него HTTP-ом.
   `unplugin-swc` обеспечивает `experimentalDecorators` /
   `emitDecoratorMetadata` (без них NestJS DI не соберёт зависимости).
3. **Тесты против реальной Postgres.** Из ключевого: проверки прав,
   транзакций и инвариантов нет смысла мокировать — sqlite не имеет
   partial-индексов, in-memory Prisma всё равно вызывает реальный
   движок. Тесты используют отдельную БД, заданную
   `TEST_DATABASE_URL`. Если переменной нет — `describeWithDb`
   превращается в `describe.skip`, чтобы CI/локальный прогон без БД
   проходил «зелёным».
4. **Состояние БД сбрасывается перед каждым тестом** через `TRUNCATE
   ... RESTART IDENTITY CASCADE`, дальше — минимальный seed
   (`tests/utils/seed.ts`). Используем **минимальный** seed, а не
   prod-овский, чтобы тесты были быстрыми и читаемыми. Полный seed
   проверяется отдельно сценарием smoke «migrate + seed → login».
5. **Скоуп.** Покрываем то, что перечислено в ТЗ MVP 1.1:
   - `smoke/auth.smoke.test.ts` — login/logout/me, RBAC happy-path;
   - `smoke/health.smoke.test.ts` — health/ready;
   - `integration/production-flow.test.ts` — длинный сценарий A→G
     (orders, passports, shifts, qc, packing, earnings, shopfloor);
   - `integration/db-invariants.test.ts` — каждый инвариант ADR-0015
     прямым `prisma.*.create`.
6. **Скрипты.** На корне `npm test`, `npm run test:smoke`, `npm run
   test:integration` делегируют в `tests` workspace. Контракт прост:
   зелёный без БД — тоже зелёный (skip), красный с БД — реальная
   регрессия.

## 3. Альтернативы

- **Jest вместо Vitest.** Конфигурация Nest+Jest проще из коробки,
  но Jest медленнее и не даёт того же ESM-friendly опыта, который мы
  получаем для shared-пакета. Vitest оказался дешевле, особенно с swc.
- **In-memory Postgres (pg-mem).** Не поддерживает partial unique и
  ряд RAW SQL — то есть не покрывает именно то, что мы хотели проверить.
- **Полные e2e через Playwright.** Полезно, но это уже не MVP 1.1.
  Backlog.
- **Unit-тесты на сервисы.** Возможны, но дают мало уверенности в
  потоке — мы выбрали интеграционный путь как первый слой.

## 4. Последствия

- Локально: `cp .env.example .env`, поднять Postgres, выставить
  `TEST_DATABASE_URL`, `npm install`, `npm test` — реальная проверка
  всех инвариантов и потоков.
- В CI (когда появится): отдельный шаг с docker-compose Postgres и
  выставленным `TEST_DATABASE_URL`.
- Любая регрессия в auth, RBAC, инвариантах, основных сервисах
  ловится в первом же прогоне.
- Тесты не покрывают UI и SW — только API/бизнес-сервисы. Это
  явное ограничение этапа.

## 5. Будущее

- Контрактные тесты shared-DTO (Zod-схемы).
