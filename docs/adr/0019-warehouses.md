# ADR-0019. Склады как управленческая группировка ячеек

- Статус: Принято
- Дата: 2026-04
- Контекст: пост-ADR-0017/0018, перед стабилизацией физической инвентаризации цеха

---

## 1. Контекст

В цехе появились реальные физические места хранения, которые удобно
называть «складами» — стеллаж в раскройной, тележка готового кроя,
полка ОТК. До этого решения сущностью «куда положить» в системе
была только `Cell` — атомарная QR-ячейка, которую помощник
раскройщика сканирует, прежде чем разместить паспорт
(`POST /api/passports/:id/place`, см. ADR-0008/ADR-0010, flow F3b в
`docs/flows.md`).

Что хочет начальник цеха:

- видеть список складов и их состав (какие ячейки куда привязаны);
- быстро создать новый склад, дать ему понятное имя и опционально код;
- привязать существующие ячейки к складу — без переседывания QR;
- распечатать QR-этикетку любой ячейки, не открывая отдельный
  принтерный экран на каждую.

Чего **категорически не хочется** делать ради этого:

- ломать существующий flow «scan cell → place passport» — он работает
  на пилоте, и любая регрессия там стоит дороже, чем удобство админки;
- менять QR-payload `cell:{id}` (ADR-0008) — поверх уже напечатаны
  десятки этикеток;
- городить полноценный WMS (зоны, секции, полки, capacity, history of
  movements) — это перебор для пилотного цеха.

## 2. Решение

1. **Минимальная доменная модель.** Заводим `Warehouse(id, name UNIQUE,
   code UNIQUE NULL, isActive, createdAt, updatedAt)`. На `Cell`
   добавляем nullable `warehouseId` с FK `ON DELETE SET NULL`. Связь
   one-to-many: `Warehouse 1..N Cell`. Полная схема — `docs/erd.md
   §2.13a`, доменное описание — `docs/domain.md §16`.

2. **Cell.warehouseId nullable — это сознательно.** Существующие
   ячейки в seed/проде не получают склада автоматически — менеджер
   привязывает их по мере физической инвентаризации цеха. Это:
   - не требует data-migration «придумать первый склад и натянуть
     все ячейки на него»;
   - оставляет flow `place` 1:1 как сейчас — он не зависит от
     `warehouseId`;
   - моделирует реальность («есть тележки, которые мы пока не
     описывали»).

3. **`ON DELETE SET NULL`, без удаления склада через API.**
   Удаление склада в API сознательно не выставлено: менеджер выключает
   `isActive`. Но если склад всё-таки удалят (Prisma Studio, миграция,
   bug-fix), ячейки не должны исчезнуть — они физически существуют.

4. **Backend как источник истины.** Новый модуль
   `apps/api/src/modules/warehouses`:
   - `GET /api/warehouses` — список с `cellsCount`;
   - `GET /api/warehouses/:id` — карточка с упорядоченным `cells[]`
     и готовым `printUrl` для каждой ячейки;
   - `POST /api/warehouses` — создать;
   - `PATCH /api/warehouses/:id` — точечно менять `name`/`code`/`isActive`.
   - Всё под `@Roles('SHOP_MANAGER', 'ADMIN')`.
   `WAREHOUSE_NAME_TAKEN` / `WAREHOUSE_CODE_TAKEN` / `WAREHOUSE_NOT_FOUND`
   — три бизнес-ошибки, чтобы UI показывал понятный текст вместо
   «P2002». Контракт — `docs/api.md §15`.

5. **Привязка ячейки к складу — `PATCH /api/cells/:id`.** Тело
   `{ warehouseId: string | null }`, единственное поле в MVP. Это:
   - не требует отдельного эндпоинта `/warehouses/:id/cells/:id`;
   - симметрично с тем, как уже работает `PATCH /api/equipment/:id`;
   - даёт явную операцию «отвязать» (`null`) и «перепривязать»
     (новый `warehouseId`) без лишних батч-ручек.
   Доступ — те же `SHOP_MANAGER`/`ADMIN`. Перепривязка между складами
   разрешена явно — это менеджерское действие. Никакой проверки «нельзя
   двигать ячейку с активными паспортами»: складская группировка не
   влияет на flow `place`/`issue`.

6. **QR-печать ячейки — переиспользуем модель ADR-0010.**
   - `GET /api/cells/:id/print` — публичный (`@Public()`) HTML A6,
     QR встраивается как data URL PNG;
   - `GET /api/cells/:id/qr` — публичный PNG (для QR-стикеров).
   - Payload не меняется — `cell:{id}` (ADR-0008). Тем самым
     уже напечатанные этикетки остаются валидными.
   Публичность — та же модель, что у passports/equipment: принтер-станция
   в типографии работает без сессии (физически изолирована).

7. **Web-UI: вкладка «Склад» (мобайл/десктоп).**
   - `/admin/warehouses` — список + форма создания (`docs/screens.md §10b`);
   - `/admin/warehouses/[id]` — реквизиты склада, список его ячеек с
     кнопкой «Печать QR», блок «Привязать ячейку» с select-ом из общего
     списка ячеек.
   - Ссылка появляется в админ-нав-баре и тайл на главной (только
     `ADMIN`/`SHOP_MANAGER`). Защита раздела — существующий
     `app/admin/layout.tsx` через `canSeeAdmin`. Backend
     перепроверяет `@Roles` независимо.

## 3. Альтернативы

- **Не заводить отдельную сущность, хранить «склад» как строку в
  `Cell.zone`.** Дешево, но: нельзя инкрементально перенастраивать
  стеллаж (нет уникальных id), нельзя выключить склад целиком, и
  агрегаты «сколько ячеек на складе» становятся scan-ом.
- **Полноценный WMS: Warehouse → Zone → Aisle → Shelf → Cell.**
  Соответствует «классической» модели склада, но кратно усложняет
  админку и UI помощника. На пилотном цехе с 20–40 ячейками это
  оверкилл, и шаг легко сделать позже надстройкой над `Warehouse`.
- **Делать `Cell.warehouseId NOT NULL` с обязательной data-migration.**
  Аккуратно по схеме, но требует придумать «дефолтный склад» в
  миграции и поломать инвариант для старых ячеек, у которых
  склада физически нет. Менеджеру удобнее видеть честное «не привязан»
  и точечно навешивать.
- **Делать удаление склада через API.** Тогда нужно решать, что
  делать с ячейками (cascade vs orphan). `SET NULL` + админский
  «деактивировать» проще, безопаснее и не уносит данные.

## 4. Последствия

- В админке появляется явный экран «инвентаризация цеха», и
  начальник цеха может без релиза:
  - заводить новые склады,
  - переименовывать,
  - двигать ячейки между складами,
  - печатать этикетки QR ячеек.
- Flow помощника раскройщика и швеи не меняется ни на байт:
  `POST /api/passports/:id/place`, `POST /api/cells/by-code`,
  `GET /api/shifts/meta` — все возвращают то же самое, что и до
  ADR-0019. Тесты в `tests/integration/warehouses.test.ts`
  фиксируют это (см. сценарии «GET /api/cells: ячейки без склада
  продолжают возвращаться» и «POST /api/cells/by-code: резолвит
  ячейку без склада»).
- `CellDetailDto` теперь несёт `warehouse: { id, name, code } | null`.
  Это аддитивное расширение — ни один существующий клиент не должен
  сломаться (поле опциональное по смыслу, мы просто перестаём отдавать
  `undefined`).
- Удаление склада в БД (через Prisma Studio или ручную миграцию)
  теперь безопасно: ячейки сохраняются, `warehouseId` становится
  `NULL`. Покрыто тестом «Удаление склада на уровне БД — ячейки
  остаются».

## 5. Открытые вопросы / future work

- Зоны/секции/полки внутри склада. Если пилот покажет, что одного
  уровня группировки мало, надстройка `Zone` ставится поверх
  `Warehouse` без переезда `Cell` (ячейка получит `zoneId`,
  `warehouseId` останется денормализованной ссылкой или уйдёт в
  view).
- Capacity / план «сколько паспортов помещается». Сейчас сознательно
  нет — ячейка либо есть, либо нет, физический предел знают люди
  на месте.
- Audit log изменений склада (кто переименовал, кто перевесил
  ячейку). Сейчас фиксируем только `updatedAt` склада и пишем event
  в логи (`event=warehouse.create`, `event=cell.warehouse.assign`).
  Полноценный audit выйдет общим шагом для админки.
- API на удаление склада. Если когда-нибудь понадобится — добавим
  `DELETE /api/warehouses/:id` + cascade-логика «отвязать все ячейки»;
  схема FK уже это позволяет (`ON DELETE SET NULL`).
