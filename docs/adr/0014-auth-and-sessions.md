# ADR-0014. Авторизация и сессии (MVP 1.1)

- Статус: Принято
- Дата: 2026-04
- Контекст: MVP 1.1 / Stabilization

---

## 1. Контекст

В MVP 1.0 «авторизация» сводилась к выбору сотрудника через demo-cookie
`demo-employee-id` и явной передаче `employeeId` в body запросов. Этого
было достаточно для разработки, но для внутреннего запуска нужно:

- ограничить, кто может выполнять чувствительные действия (заказы,
  закрытие коробки, фиксация брака);
- сделать identity сотрудника недоступной к подделке с клиента;
- работать в схеме «UI на `prod.teeon.ru`, API на `api.prod.teeon.ru`»
  (cross-subdomain cookie);
- остаться совместимым с тем, что сотрудники Employee живут в одной
  таблице, и не плодить отдельную модель «User».

При этом MVP 1.1 — этап стабилизации, не «enterprise IAM»: refresh-токенов,
multi-device session-list-а, 2FA и SSO не делаем.

## 2. Решение

1. **Identity = `Employee`.** Не вводим отдельную модель. У `Employee`
   уже есть `login` и `pinHash` (bcrypt) — этого хватает.

   > Дополнение 07.08.2026 (фича «показать пароль сотрудника»). Рядом с
   > `pinHash` появилась колонка `pinEnc` — обратимая AES-256-GCM копия
   > того же PIN'а, из которой карточка `/admin/employees/[id]`
   > показывает пароль менеджеру. **Аутентификация её не касается:**
   > `AuthService.login` по-прежнему сверяет только bcrypt-хеш, и
   > `pinHash` остаётся обязательной колонкой. Решение осознанное:
   > обратимое хранение пароля — это ослабление, и принято оно ради
   > конкретного цехового сценария (менеджер обязан уметь продиктовать
   > забытый код, не ломая уже розданные бумажки), с компенсацией —
   > RBAC (не-админ не видит PIN админской учётки) и аудит каждого
   > просмотра (`EMPLOYEE_PIN_VIEWED`). Обе колонки считает
   > `apps/api/src/common/pin-columns.ts` — единственная точка, иначе
   > они разъезжаются и показ врёт.
2. **Сессия = подписанная cookie.** Используем собственную HMAC-SHA256
   подпись на `JWT_SECRET` (Node `crypto`). JWT-библиотек не тащим:
   формат `base64url(JSON payload).base64url(HMAC)` решает задачу
   тривиально и не требует ротации алгоритмов.
3. **Cookie:** имя `sewing_session`, `HttpOnly`, `SameSite=Lax`,
   `Path=/`, в production — `Secure` и `Domain=.teeon.ru`. TTL —
   `JWT_EXPIRES_IN` (по умолчанию `12h`), дублируется в `Max-Age` и
   во внутренний `exp`.
4. **AuthGuard глобальный.** Зарегистрирован через `APP_GUARD`. Декоратор
   `@Public()` помечает исключения (`/api/auth/login`, `/logout`,
   `/api/health`, `/api/ready`).
5. **RBAC через `@Roles(...)`.** ADMIN — wildcard. На UI
   `middleware.ts` Next.js перенаправляет неавторизованных на
   `/login?next=<url>`.
6. **Сотрудник всегда из сессии.** На state-changing endpoint-ах
   `employeeId` в body/query запрещён (см. `api.md §12`).
7. **Свежие role/active при каждом запросе.** `AuthGuard.resolvePrincipal`
   подгружает Employee из БД, чтобы деактивация работала мгновенно
   (а не «через 12 часов»).
8. **Logout идемпотентен.** Возвращает `204` и `Set-Cookie` с
   `Max-Age=0`. UI дополнительно чистит cookie в `cookies()` Next-а.

## 3. Альтернативы

- **`@nestjs/jwt` + `passport-jwt`.** Тянет 2-3 пакета и Passport-стек
  ради функциональности, которая у нас в 60 строк HMAC.
- **Server-side session store (Redis/БД).** Позволяет revocation, но
  на MVP 1.1 у нас нет операционной потребности — TTL 12h и
  деактивация через БД покрывают сценарии. Можно ввести позже без
  слома cookie-формата (флаг `kind` в payload).
- **OAuth/OIDC.** Внешних identity provider-ов в швейном цехе нет.

## 4. Последствия

- Производственные потоки стали проверяемы по ролям сразу на API,
  без дублирования в UI.
- demo-cookie / demo-employee-id убраны из всех потоков.
- На prod обязательно переопределить `JWT_SECRET` (>= 32 случайных байт).
  При дефолтном значении API логирует warning при старте.
- Сценарий «migrate + seed → login» работает: seed всегда переустанавливает
  `pinHash` для demo-учёток (`Demo12345!`).

## 5. Совместимость

Все MVP 1.0 endpoint-ы остались по адресам и контрактам, изменилось
только: 1) откуда берётся `employeeId`, 2) как присылается identity
(cookie вместо явного поля). Schema БД не менялась.

## 6. Будущее

- Forgot/reset password через admin-flow (без email — внутренний
  инструмент).
- Возможный переход на отдельную таблицу `User` под админскую
  не-производственную аудиторию — без слома cookie-контракта.
- Server-side revocation (если появится требование).
