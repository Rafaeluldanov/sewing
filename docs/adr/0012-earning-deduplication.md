# ADR-0012: Идемпотентность сдельных начислений

Статус: **Принято** (Шаг 9 MVP)

## Контекст

На Шаге 9 модель `OperationEntry` начинает заполняться автоматически
из тех же транзакций, что и `PassportsService.create`,
`PassportsService.scanOnOperation` и `PackingService.addPassport`
(см. ADR-0005, `docs/flows.md §F2/§F4/§F7`). Это удобно для денежной
консистентности, но создаёт риск дублей:

- швея случайно сканирует один и тот же паспорт два раза подряд;
- сетевой ретрай на стороне `/work` повторяет `POST /scan` после уже
  применённой транзакции;
- административный пересчёт/реимпорт ивентов в будущем повторно
  «прокручивает» те же `PassportEvent(OPERATION_SCAN)`;
- параллельные экземпляры API при гонке могут попытаться создать
  начисление одновременно.

Дубль начисления — это деньги дважды. Бизнес-эффект: швея получит
оплату за партию повторно, начальник цеха увидит «откуда взялись
лишние ₽». Защита нужна на уровне БД, а не только на уровне сервиса.

При этом наш `PassportsService.scanOnOperation` уже идемпотентен «по
состоянию» (повторный скан той же сменой = no-op, ADR-0003 §6) —
значит, в большинстве случаев дубля и не будет. Но мы не хотим
полагаться только на это: достаточно одного будущего изменения
логики, чтобы получить regression на деньгах.

## Решение

Защищаем `OperationEntry` от дублей **техническим уникальным ключом
по бизнес-смыслу источника**, а не суррогатным id события.

1. Расширяем `OperationEntry` тремя новыми полями:

   - `approvalMode` (`ApprovalMode`: `IMMEDIATE` / `AFTER_RELEASE`) —
     режим подтверждения по ADR-0005.
   - `sourceEventType` (`EarningSource`: `PASSPORT_CREATED` /
     `OPERATION_TRANSITION`) — *почему* возникло начисление.
     Дискриминатор источника, **часть уникального ключа**.
   - `sourceEventId` (`String?`) — опциональная ссылка на конкретный
     `PassportEvent.id`-триггер. Используется только для аудита,
     **не часть** уникального ключа.

2. Добавляем уникальный индекс
   `@@unique(passportId, operationId, employeeId, sourceEventType)`
   с именем `OperationEntry_idem`.

3. В `EarningsService.safeCreate` ловим
   `Prisma.PrismaClientKnownRequestError(P2002)` и трактуем как no-op
   (без бросания `EARNING_ALREADY_EXISTS`). Сервис продолжает
   транзакцию: её цель — гарантировать, что после выхода
   начисление *существует*, а не «именно сейчас создалось».

4. `EarningsService.approvePendingForPassport` — массовое
   `UPDATE WHERE status IN (PENDING_RELEASE, PENDING)` — тоже
   идемпотентно: повторный вызов просто обновит 0 строк.

## Почему `sourceEventType` в ключе, а не `sourceEventId`

Альтернатива — таскать `sourceEventId = PassportEvent.id` и делать
ключ `(sourceEventId)` или `(passportId, sourceEventId)`. Минусы:

- `PassportEvent` живёт ради аудита, а не как «owning entity»
  начисления. Делать его частью ключа — связывать денежную таблицу с
  журналом сильнее, чем хочется.
- Для immediate-раскроя «своего» события на уровне семантики нет:
  раскройщику начисление принадлежит самому акту создания паспорта,
  а не конкретному `PassportEvent(CREATED).id`.
- Будущий «реимпорт ивентов» поменяет `PassportEvent.id`, а
  бизнес-смысл начисления тот же — пришлось бы вручную
  перепрошивать `sourceEventId`.

Дискриминатор `sourceEventType` снимает оба пункта: `(passportId,
operationId, employeeId, sourceEventType)` — это то, что в реальности
**должно быть** уникально по бизнес-смыслу. Совпадение тройки
*(паспорт, операция, исполнитель)* допустимо, если источник разный
(например, паспорт можно теоретически вернуть в производство — будет
другой `sourceEventType`).

## Почему ловим `P2002` молча

Бизнес-ошибка `EARNING_ALREADY_EXISTS` не нужна:

- Триггер находится **внутри** транзакции `passport.create` /
  `scan` / `pack` — пользователь не делает «POST /earnings» напрямую,
  чтобы что-то получить из ответа.
- Идемпотентность скана = no-op для пользователя; падение всей
  транзакции из-за повторного начисления было бы хуже, чем silent
  proceed.
- Логирование в случае гонки делаем на уровне сервиса (debug-лог),
  но без эскалации.

## Почему всё в одной транзакции, а не через event bus

`@nestjs/event-emitter` есть в проекте (см. `events.md §3`), но для
денег мы сознательно отказываемся от async-обработчика. Иначе:

- начисление может «потеряться», если процесс упадёт между записью
  паспорта и обработкой события;
- появятся отдельные транзакции с собственной семантикой ретраев;
- придётся городить outbox/saga, которые на MVP не нужны.

Sync-вызов `EarningsService.*` внутри той же `prisma.$transaction`
проще и атомарнее. См. `events.md §3` (MVP-упрощение).

## Что НЕ делаем на MVP (последствия)

- **Брак не пересчитывает старые начисления.** Если ОТК зафиксирует
  брак после `OPERATION_SCAN`, ранее созданное `PENDING_RELEASE`
  *не* уменьшается. Причина: для корректного перерасчёта нужен flow
  «виновная операция» (см. `domain.md §10`, «За рамками Шага 7»),
  которого на MVP нет. Деньги мы платим швее за то, что она
  передала на следующий этап в момент `OPERATION_SCAN`; брак ловит
  ОТК позже и адресуется в будущем процессе разбора.
- **Возврат паспорта в производство** (будущий flow) → создаст
  отдельные `OperationEntry` с `sourceEventType = PASSPORT_RETURNED`
  (или аналогичный, см. `EarningSource`-enum). Тогда же станет
  использоваться `EntryStatus.REVERSED`.
- **Отмена упаковки** на MVP запрещена (`PASSPORT_ALREADY_PACKED` на
  любом мутирующем эндпоинте). Если когда-нибудь появится
  «распаковать», мы переведём `OperationEntry → REVERSED` массово
  по `passportId`, а не удалим.
