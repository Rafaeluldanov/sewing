# ADR-0015. Инварианты на уровне БД (MVP 1.1)

- Статус: Принято
- Дата: 2026-04
- Контекст: MVP 1.1 / Stabilization

---

## 1. Контекст

В MVP 1.0 ряд критичных для бизнеса инвариантов защищался только
сервисным слоем. Это работало в одиночных тестах, но в проде между
запросами есть гонки (две параллельные транзакции, ручные SQL-правки,
seed). Для стабилизации нужно защитить «нельзя ни при каких условиях»
напрямую в Postgres.

Под «критичными» понимаем те, нарушение которых ломает бухгалтерию
или физическую логистику:

- два паспорта с одним номером;
- паспорт, упакованный одновременно в две коробки;
- две активные смены у одного сотрудника на разном оборудовании;
- две строки в одном заказе под один и тот же `(product, size)`.

## 2. Решение

Все инварианты ниже **должны** жить в БД (Prisma + raw SQL для partial
index). Сервисный код по-прежнему бросает читаемые `BusinessException`
и не должен полагаться только на Postgres-ошибку.

### 2.1. Уникальные номера и QR (decl. через Prisma)

| Поле                  | Уровень        |
| --------------------- | -------------- |
| `Order.number`        | `@unique`      |
| `Passport.number`     | `@unique`      |
| `Passport.qrCode`     | `@unique`      |
| `Box.number`          | `@unique`      |
| `Box.qrCode`          | `@unique`      |
| `Equipment.code`      | `@unique`      |
| `Equipment.qrCode`    | `@unique`      |
| `Cell.code`           | `@unique`      |
| `Cell.qrCode`         | `@unique`      |
| `Employee.login`      | `@unique`      |

### 2.2. Композитные уникальности

- `OrderItem(orderId, productId, sizeId)` — одна строка под размер
  внутри заказа (защищает от случайных дублей при импорте/UI-багах).
- `BoxItem(boxId, passportId)` — был и в MVP 1.0.
- `BoxItem.passportId` — **глобально-уникальный** (новое в MVP 1.1).
  Один паспорт физически в одной коробке. Без этого можно «дописать»
  тот же passportId в другую коробку и получить переучёт.
- `OperationEntry(passportId, operationId, employeeId, sourceEventId)` —
  идемпотентность сдельных начислений (см. ADR-0012).

### 2.3. Partial unique для активной смены

Самый интересный кейс. Хотим:

> На сотрудника не более одной строки `ShiftSession` с `endedAt IS NULL`.

Prisma 5.x не описывает partial-уникальные индексы декларативно. Решение:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS shift_session_active_employee_uniq
  ON "ShiftSession" ("employeeId")
  WHERE "endedAt" IS NULL;
```

Индекс создаётся идемпотентно при старте API в
`PrismaService.onModuleInit` (`prisma/invariants.ts`). Это позволяет:

- в dev — переживать `prisma db push` без ручных шагов;
- в prod — гарантированно иметь индекс к моменту приёма запросов;
- в тестах — не плодить отдельный setup-step.

`ShiftsService.start` дополнительно ловит `Prisma.P2002` именно на этом
индексе и бросает `SHIFT_ALREADY_ACTIVE`, чтобы клиент получил знакомый
бизнес-код, а не raw constraint-ошибку.

## 3. Альтернативы

- **Prisma migrations с raw SQL.** Это «правильный» путь, но в репозитории
  пока используется `prisma db push` без `migrations/` директории.
  Заводить полноценный migration set ради одного индекса — overkill
  для этапа стабилизации; перевод на migrations записан в backlog.
- **Триггер вместо partial-индекса.** Триггер дороже, требует
  поддержки и не блокирует concurrent insert на уровне B-tree.
- **Только сервисный guard.** Уже есть, и его недостаточно — что и было
  явным требованием этапа.

## 4. Последствия

- Любая попытка создать «вторую активную смену» падает с
  `SHIFT_ALREADY_ACTIVE` (наш код) даже под нагрузкой.
- Любая попытка положить паспорт в две коробки падает с
  `UNIQUE_CONSTRAINT_VIOLATION` (или соответствующим бизнес-кодом, если
  пройдёт через `PackingService`).
- При старте API логи показывают «ensured invariant indexes»; если
  что-то падает — сервис не стартует, и это сигнал прекращать deploy.
- Тесты в `tests/integration/db-invariants.test.ts` пробивают каждый
  инвариант через прямые `prisma.*.create` — гарантия, что индекс
  реально создан, а не просто описан.

## 5. Будущее

- Перевод на полноценный `prisma migrate` (отдельный ADR).
- При появлении split-паспорта пересмотреть `BoxItem.passportId` unique
  (возможно, придётся завести `BoxItemPart`).
