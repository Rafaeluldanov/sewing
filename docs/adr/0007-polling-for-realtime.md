# ADR-0007: Realtime через polling на MVP

- Статус: принято
- Дата: 2026-04-17

## Контекст

ТЗ §18: на экране «Цех» нужны live-обновления (анимация перемещений).
WebSocket/SSE — полноценная инфраструктура, которая требует
отказоустойчивости соединений, heartbeat, сложного деплоя.

## Решение

На MVP:

- Клиент делает `GET /api/shopfloor/state` и `GET /api/dashboard/sizes`
  каждые **5–10 секунд** (исторический целевой диапазон ТЗ §18).
- Анимация перелёта партии — чисто клиентская, на основе дельт между
  предыдущим и текущим снапшотом матрицы `size × stage → qty`.
- Сервер отдаёт ответ с полем `timestamp`, клиент логирует задержки для
  отладки.

После MVP — переезд на SSE (`/api/shopfloor/stream`), без смены фронта
(wrapper с одинаковым интерфейсом «подписаться на состояние»).

### Уточнение для `/shopfloor/display` (большой монитор)

Большой монитор цеха (`apps/web/app/shopfloor/display/display-board.tsx`)
живёт круглосуточно на планшете на стене и должен переживать
случайные glitch'и сети. Поэтому он использует адаптивный
recursive-`setTimeout`-планировщик с двумя cadence'ами в окне 5–10 c:

| Состояние    | Polling interval        | Что показывает шапка                    |
| ------------ | ----------------------- | --------------------------------------- |
| online       | `POLL_INTERVAL_MS = 7 c`        | «онлайн» (зелёный)                      |
| degraded     | `POLL_INTERVAL_DEGRADED_MS = 15 c` | «обновление замедлено» (жёлтый)         |
| offline      | `POLL_INTERVAL_DEGRADED_MS = 15 c` | «Нет связи» (красный, snapshot жив)     |
| auth         | `POLL_INTERVAL_DEGRADED_MS = 15 c` | «Сессия истекла» (жёлтый, snapshot жив) |

`FETCH_TIMEOUT_MS = 6 c` — комфортный запас над реальной p99 latency
backend'а. Старая связка «3000 / 2500» (cadence / timeout) почти
всегда обрезала даже честные 1–2-секундные ответы при чуть-чуть
деградировавшей сети, и экран ложно уходил в «Нет связи».

Ошибки явно классифицируются (`FetchErrorKind` в коде):
`timeout / network / server / client / parse` суммируются в
soft-счётчик; `MAX_SOFT_ERRORS = 5` подряд soft-ошибок переключают
индикатор в «Нет связи». `auth` (HTTP 401/403) идёт отдельным
сигналом и НЕ инкрементирует soft-счётчик — иначе истёкший
session-cookie маскировался бы под сетевую проблему. Любой
успешный ответ моментально сбрасывает оба состояния.

**Retained snapshot.** Последний УСПЕШНО полученный
`ShopfloorDisplayDto` НИКОГДА не очищается ошибкой и продолжает
отрисовываться даже в degraded/offline/auth-режимах — меняется
только индикатор в шапке. Это критично: read-only монитор не должен
гасить цифры из-за единичного 502.

**Backend-сторона.** `getDisplaySummary` гонит независимые Prisma-
запросы параллельно (`Promise.all`: `eventMaxes / packedToday /
listEquipmentStatus`), `listEquipmentStatus` внутри тоже
параллелизован (`[equipment, activeShifts]` одним `Promise.all`).
Это убирает 2 лишних DB round-trip'а с каждого polling-tick'а и
снижает риск таймаута на фронте без введения backend-кэша. Никакого
in-memory TTL сознательно не вводим: данные «почти realtime» —
маленький TTL только сбивал бы оператора.

## Последствия

+ Простой деплой и отладка.
+ Работает через любые прокси.
+ `/shopfloor/display` переживает короткие glitch'и сети без
  потери последнего успешного снимка и без «мерцания» индикатора.
− 6–12 запросов в минуту на DISPLAY-планшет в healthy режиме (4 в
  минуту в degraded). Менеджерский `/shopfloor` остаётся в окне
  оригинальных 5–10 c. Для цеха (5–20 планшетов) — нормально.
