# ADR-0010: Печатная форма паспорта, текущая ячейка и условие выпуска

- Статус: принято
- Дата: 2026-04-18
- Связано: [ADR-0004](./0004-simplified-cells.md), [ADR-0006](./0006-plan-is-immutable.md), [ADR-0008](./0008-qr-format.md)

## Контекст

Шаг 5 MVP вводит модуль паспортов. Требуется зафиксировать три решения,
о которых раньше не было консенсуса в `docs/`:

1. Чем рендерить печатную форму (PDF или HTML).
2. Хранить ли «где сейчас лежит этот паспорт» — учитывая, что ADR-0004
   явно отказывался от привязки «паспорт ↔ ячейка».
3. В каком статусе заказа разрешён выпуск паспорта.

## Решения

### 1. Печатная форма — серверный HTML

Печатная форма паспорта (`GET /api/passports/:id/print`) отдаётся как
`text/html; charset=utf-8`. Браузер пользователя сам открывает системный
диалог печати (на устройстве или термопринтере через ОС).

В шаблоне:

- стили `@page A6` + `@media print` — корректно для A4 и термопринтера;
- QR вставлен как `<img src="data:image/png;base64,…">` (генерируется
  библиотекой `qrcode` на API);
- payload QR — строго формат [ADR-0008](./0008-qr-format.md): `passport:{id}`;
- дополнительно показываем человекочитаемый URL `${APP_URL}/passports/{id}`
  (берётся из `APP_URL` / `NEXT_PUBLIC_APP_URL`, см. `docs/index.md`).

**Почему не PDF на этом шаге:**

- любой PDF-рендерер (`pdfkit`, `@react-pdf/renderer`, headless-Chrome)
  тащит заметные runtime-зависимости и/или нативные сборки;
- стабильность PDF-стека влияет на CI/деплой, а Шаг 5 узко скоупирован
  («не делать тяжёлую инфраструктуру ради PDF» — задание);
- HTML-печать достаточна: страница печатается в один клик, на экране
  выглядит как карточка, в распечатке — как лейбл.

PDF-рендеринг сможет заменить эту реализацию на следующих шагах без
изменения внешнего контракта: `printUrl` в `PassportDetailDto` остаётся
тем же.

### 2. `Passport.currentCellId` — единственная текущая ячейка

ADR-0004 (упрощённая модель ячеек) сознательно отказывался от привязки
«паспорт ↔ ячейка», ограничиваясь срезом `CellContent(cellId, sizeId,
quantity)`. Шаг 5 этого требования (правило бизнеса №11: «один паспорт
может быть размещён только в одной текущей ячейке») удовлетворить не
может.

Поэтому добавляем минимальное расширение схемы:

- `Passport.currentCellId String? @db FK→Cell`;
- индекс `@@index([currentCellId])`;
- relation `Cell.currentPassports Passport[]`.

Это **дополняет**, а не отменяет ADR-0004:

- срез `CellContent` остаётся источником истины «сколько штук какого
  размера сейчас в ячейке» — на нём строятся выдача кроя и UI ячейки;
- `currentCellId` отвечает только на вопрос «куда положили этот
  конкретный паспорт» и используется для запрета двойного размещения.

Полноценное перемещение между ячейками, история размещений, частичный
сплит/мердж паспортов — за рамками Шага 5.

### 3. Выпуск паспорта разрешён только в `IN_PRODUCTION`

Заказ в статусе `DRAFT` ещё допускает редактирование плана
([ADR-0006](./0006-plan-is-immutable.md)). Выпуск паспорта на черновик
поломал бы инвариант «факт ≤ план», как только пользователь решит
изменить план. Поэтому:

- API возвращает 409 `ORDER_NOT_IN_PRODUCTION`, если статус заказа
  не `IN_PRODUCTION`;
- кнопка «Выпустить паспорт» в карточке заказа доступна только при
  `IN_PRODUCTION`;
- DONE / CANCELLED — также 409 (терминальные статусы).

## Последствия

+ Минимальный объём изменений в схеме (одно поле + индекс) и в стеке
  (одна dev-зависимость `qrcode`).
+ HTML-печать работает на любом современном браузере, включая мобильный
  Safari/Chrome — соответствует mobile-first.
+ Жёсткое требование `IN_PRODUCTION` снимает классы багов с
  «фактом сверх плана» и с «отменой плана с уже выпущенными паспортами».
− Печать не выглядит «как настоящий PDF» (нет точной A4-лэйаута без
  поправок на принтер). Достаточно для MVP, до Шага 8 заменим на PDF,
  если будет реальный запрос от цеха.
− `currentCellId` не повторяет всю историю размещений — её придётся
  пересобирать из `PassportEvent(CELL_PLACED|CELL_REMOVED)`. Для MVP ОК.
