# ADR-0017. Equipment ↔ allowed operations: backend как источник истины

- Статус: Принято
- Дата: 2026-04
- Контекст: пост-Шаг 13, перед стабилизацией админ-настроек

---

## 1. Контекст

На /work швея после скана QR оборудования выбирает операцию из списка
доступных. До этого решения список «какие операции доступны на каком
станке» жил во фронте — `apps/web/lib/equipment-operations.ts`
содержал жёсткую карту префиксов `Equipment.code → Operation.code[]`:

```
overlock-*    → SEW_OVERLOCK_1, SEW_OVERLOCK_2
coverstitch-* → SEW_COVERSTITCH
binding-*     → SEW_BINDING
qc-station-*  → QC
wto-station-* → WTO
packing-*     → PACKING
```

Это было нормально для MVP: операций мало, оборудования мало,
конфигурация менялась только разработчиком. Но дальше:

- начальник цеха не может перенастроить оборудование без релиза;
- backend не знает, какие операции реально допустимы на станке —
  и не сможет применить эту проверку, когда понадобится;
- бизнес-связь `Equipment ↔ Operation` существует, но в схеме её нет —
  это «магия» во фронте, которой тяжело верить;
- появление любого нового станка требует кода, а не данных.

При этом нам **не** нужен полноценный ERP-модуль оборудования: достаточно
явной конфигурации связей и минимального админ-экрана.

## 2. Решение

1. Заводим явную M2M-таблицу `EquipmentOperation`
   (`equipmentId`, `operationId`, `sortOrder`, `isActive`,
   `createdAt`, `updatedAt`) с уникальным составным индексом
   `(equipmentId, operationId)`. FK на `Equipment` и `Operation` —
   `ON DELETE CASCADE` (это конфигурация, а не история, см. §5).
   Полная схема — `docs/erd.md §2.5a`.
2. **Backend становится источником истины.** `prisma/seed.ts`
   идемпотентно создаёт стартовый набор связей по той же логике, что
   была во фронтовой карте, чтобы поведение `/work` для уже работающих
   станков не изменилось.
3. **Передача на фронт.** Расширяем существующий `GET /api/shifts/meta`:
   у каждой единицы `equipment` появляется `allowedOperationIds: string[]`
   (отсортировано по `sortOrder`, отфильтровано по
   `EquipmentOperation.isActive` и `Operation.active`). Не вводим
   отдельный публичный эндпоинт «операции по оборудованию» — это
   удваивает контракт и кэш, а meta уже грузится /work-ом.
4. **Удаляем фронтовую карту префиксов.**
   `apps/web/lib/equipment-operations.ts` теперь читает только
   `equipment.allowedOperationIds`. Хардкод по `Equipment.code` уходит
   полностью — fallback'а не оставляем, чтобы не было «двух источников
   истины». Если у станка пуст allow-лист — UI явно показывает
   empty-state со ссылкой на админку, а не пустой селект.
5. **Админ-управление.** Новый модуль `apps/api/src/modules/equipment`:
   - `GET /api/equipment` — список с `allowedOperationsCount`;
   - `GET /api/equipment/:id` — карточка с упорядоченным
     `allowedOperations[]`;
   - `PATCH /api/equipment/:id/operations` — полная замена набора
     (delete missing, insert new, обновить `sortOrder` по индексу
     массива) в одной транзакции.
   - Все три — `ADMIN` / `SHOP_MANAGER`.
   - UI — `/admin/equipment` (список) и `/admin/equipment/[id]`
     (чеклист операций + Server Action). Layout `/admin/*` защищён
     `canSeeAdmin`.
6. **Не делаем server-side enforcement в `POST /api/shifts/start`.**
   Сервис продолжает проверять только `Equipment.active` /
   `Operation.active`, без проверки allow-листа. Причины:
   - нормальный путь — UI, который выбор уже ограничивает;
   - жёсткая проверка повлекла бы новый код ошибки и регресс-риск
     по живым станкам с пустым allow-листом;
   - решение явно «MVP equipment-config», и оно зафиксировано как
     ограничение в `docs/api.md §3a` и `domain.md §5c`.

## 3. Альтернативы

- **Оставить фронтовый mapping и сделать его конфигом.** Лечит только
  «нельзя поменять без релиза», но не лечит «backend ничего не знает» и
  не даёт админ-UI без лишней инфраструктуры.
- **Запихнуть allow-лист в JSON-поле `Equipment.metadata`.** Просто, но
  ломает реляционную целостность (`Operation` можно удалить, ссылка
  останется висеть), и индекс/сортировка делаются неудобно. Плюс
  `sortOrder` и `isActive` хочется иметь как обычные колонки.
- **Полноценный CRUD оборудования + операций + ставок в одной админке
  «equipment manager».** Перебор для текущего шага — выходит за рамки
  «минимально достаточного расширения», увеличивает поверхность
  изменений и риск регресса по уже работающим экранам.
- **Сразу делать server-side enforcement allow-листа в `/shifts/start`.**
  Аккуратно, но это новый код ошибки и потенциальный регресс на
  существующих станках; такой шаг лучше делать отдельно после
  стабилизации админ-настроек.

## 4. Последствия

- `/work` становится управляемым из UI: SHOP_MANAGER без релиза меняет
  список операций станка; на следующем чтении `/api/shifts/meta` швея
  уже видит новый allow-лист (`/admin/equipment/[id]` дополнительно
  ревалидирует `/work`).
- Фронт перестаёт быть источником истины — это упрощает аудит
  и тестирование: интеграционный тест проверяет, что PATCH меняет
  ответ `/api/shifts/meta`.
- Появляется явная зависимость seed → backend → admin UI; миграция
  обратима (drop table), но удаление таблицы вернёт нас к хардкоду —
  поэтому удалять её не планируется.
- Новые тесты в `tests/integration/equipment-operations.test.ts`
  фиксируют контракт (порядок, фильтрация неактивных, RBAC,
  ошибки на дубликаты/несуществующие операции).

## 5. Открытые вопросы / future work

- Server-side enforcement allow-листа в `POST /api/shifts/start`
  (новый код ошибки `OPERATION_NOT_ALLOWED_FOR_EQUIPMENT`) — отдельным
  шагом после стабилизации админки.
- CRUD самих `Equipment` (создать/деактивировать/перепечатать QR) —
  отдельная админ-история, не входит в этот ADR.
- Логирование изменений allow-листа (кто и когда менял) — пока
  ограничились `updatedAt`; полноценный audit log выйдет вместе с
  общим audit-логом админских действий.
