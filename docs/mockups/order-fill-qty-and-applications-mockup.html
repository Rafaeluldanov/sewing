Заполнение заказа: количество без нуля + «Нанесение» на всём пути

Две правки в форме заказа. Первая — ячейки количества в расцветках стартуют с настоящего 0 в поле, и чтобы ввести 12, менеджер сначала стирает ноль (а если не стёр — получает «012»). Вторая — блок «Нанесение» есть только на одном экране из трёх: если заказ пошёл через «Создать изделие» → черновик → /admin/orders/[id]/edit, нанесения ввести негде.

Пустая ячейка = 0Не показываем ноль как значение: бледный placeholder «0», ввод начинается с чистого поля. Итоги считают пусто как 0 — арифметика не меняется.
Уже есть в системеТак работает размерная матрица без расцветок (size-plan-selector) — переносим тот же приём в расцветки, а не изобретаем новое.
Нанесение = атрибут заказаЗначит, доступно всюду, где заказ ещё заполняется: мастер создания, страница правки черновика, карточка заказа.
Минимальная дельтаКомпоненты OrderApplicationsEditor и OrderApplicationsCard уже написаны — второй просто нигде не подключён. Новых экранов не рисуем.

3. Где сейчас разрыв

Три пути заполнения заказа. Нанесение доступно только в одном.

Путь A · «Выбрать изделие»

1 /orders/new — шапка—
2 выбор лекала из справочника—
3 план по размерам—
4 Нанесениеесть
5 «Создать заказ»—

Путь B · «Создать изделие»

1 /orders/new — шапка—
2 изделие заводится инлайннет
3 «Сохранить изделие» → черновикнет
4 редирект на /[id]/editнет
5 карточка заказанет

Путь C · заявка в КБ

1 /orders/new — шапка—
2 «Отправить конструктору»нет
3 черновик + задача КБнет
4 дозаполнение на /[id]/editнет
5 карточка заказанет

Формально данные не теряются: API PUT /api/orders/:id/applications и форма OrderApplicationsForm существуют — просто ни один экран их не рендерит. После правки все три пути ведут в одно и то же место ввода.
