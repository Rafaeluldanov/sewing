Техкарта внутри заказа: норма приходит из номенклатуры, параметры правятся на месте

Симптом от менеджера: «подтянули техкарту из номенклатуры — нормы не подтянулись; и параметров для редактирования нет, есть только нормы». Оба симптома — про одно окно: «Материалы техкарты» в карточке заказа (тот же компонент разворачивается и в форме создания, кнопка «Настроить материалы»).

Что нашлось в коде: (1) кнопка «Подтянуть из номенклатуры» в шаблоне техкарты сознательно не переносит числа — строка создаётся с заглушкой qtyPerUnit: '1', и в заказ приезжает ровно эта единица; (2) окно заказа умеет править только название, норму, ед., цвет и плотность — подтип и остальные характеристики (ширина рулона, размер, тип, длина, толщина, материал) в контракт заказа вообще не выведены. То есть менеджер видит не баг отображения, а две дырки в контракте.

Норма — число, а не «1»Норма живёт в номенклатуре («Фурнитура и нормы», «Погонные метры по размерам»). Заказ показывает её и подписывает источник.
Параметры рядом с нормойПодтип + характеристики правятся в той же строке, а не только в справочнике техкарт.
Правка остаётся в заказеНичего не уезжает в шаблон и в номенклатуру. Источник значения виден бейджем: номенклатура / шаблон / правлено в заказе.
Один писатель на ячейкуЯчейка под слот-параметром не правится напрямую — только через значение параметра (правило уже есть, 409 ORDER_TECH_CARD_CELL_TAKEN).

Дырка 1 — норма. tech-card-form.tsx::rowFromPulledLine создаёт строку с qtyPerUnit: '1', а pullMaterialLinesFromPatternAction по старому ТЗ возвращает только роль/подтип/единицу («сами числовые значения в техкарту не переносятся»). В шаблоне поле нормы вообще скрыто как legacy — исправить единицу можно только здесь, в заказе, вручную по каждой строке.

Дырка 2 — параметры. В контракте заказа (OrderTechCardLineDto) есть только densityGsm; subtypeKey и characteristics не отдаются и не принимаются (UpdateOrderTechCardLineSchema: name / unit / qtyPerUnit / colorText / densityGsm). Секция «Параметры» показывается только при слот-параметрах техкарты — у обычной техкарты их нет, поэтому окно выглядит как «одни нормы».

Важно: закупка при этом считается правильно — WorkshopNeedsService берёт нормы прямо из номенклатуры (PATTERN_PARAMETER_NORM, LINEAR_M_BY_SIZE). Расходятся не расчёты, а то, что менеджер видит в спецификации. Это и есть самое неприятное: цифра на экране не совпадает с цифрой, по которой закупают.

2. Как предлагается то же окно, две новые вещи: источник нормы + колонка «Параметры»

Колонка «Параметры» показывает заполненные характеристики строки чипами, каретка слева раскрывает панель правки. Под нормой — бейдж источника: из номенклатуры из шаблона правлено в заказе.

Норма. При сборке снимка строка ищет свой источник в номенклатуре по паре роль + подтип/характеристика: нашла — берёт число оттуда (PatternItemParameterNorm.qtyPerItem или погонные метры по размерам), не нашла — остаётся значение шаблона. Ручная правка в заказе всегда главнее и переживает пересчёт — ровно как сегодня переживает правка нормы (ветка recompute в rebuildMaterialRequirementsSnapshot).

Параметры. Чипы = заполненные характеристики строки. Пустая строка показывает + параметр — вход в панель одинаковый и когда параметры есть, и когда их нет (та же логика, что уже применили к «Материалы · N»: вход должен быть безусловным, иначе нечем начать).

3. Раскрытая строка — панель параметров подтип + характеристики из MATERIAL_CHARACTERISTICS

Набор полей — не свободный: он выводится из подтипа (getMaterialSubtypesByGroup → subtype.characteristics), ровно как в редакторе шаблона. Значит «параметры» в заказе и в справочнике — это одни и те же поля, а не второй словарь.

Два писателя в одну ячейку по-прежнему запрещены. Ячейка под слот-параметром показана замком и read-only — как сегодня отбивается на бэке (ORDER_TECH_CARD_CELL_TAKEN). Новое здесь только одно: раньше замок было не на чем показать, потому что самой ячейки в окне не было.

Зеркало обязательно. Запись характеристики должна идти через normalizeMaterialLineCells / applyParametersToCells: density → densityGsm, rollWidth → plannedWidthCm, size → hardwareSizeText, material → hardwareMaterialText. Запись только в JSON тихо откатится ближайшим пересчётом и не доедет до закупки — это уже ловили на параметрах техкарт.

4. Норма по размерам PatternItemSizeParameterValue · LINEAR_M_BY_SIZE

В номенклатуре погонные метры заданы по каждому размеру, а строка снимка хранит одну норму на штуку. Прятать это за средним числом нельзя — менеджер не поймёт, откуда «1.24». Поэтому строка честно говорит «по размерам» и раскрывается.

apps/web/components/orders/colorways/colorway-spec.tsx Колонка «Параметры» (чипы), каретка + панель параметров строки, бейдж источника нормы, раскрытие нормы по размерам, «обновить нормы из номенклатуры».
apps/web/app/admin/tech-cards/tech-card-form.tsx + actions.ts pullMaterialLinesFromPatternAction возвращает и числа; rowFromPulledLine ставит реальную норму вместо '1'. Шаблон при этом остаётся «сеялкой» — истина в номенклатуре.

Правок схемы БД, скорее всего, не нужно: characteristics/subtypeKey уже есть на OrderMaterialRequirement. Отдельное поле под qtySource — единственный кандидат на миграцию (можно вывести и без него: «норма ≠ норме источника» = правлено, но явное поле честнее).

7. Что нужно решить до кода

1. Кто главный по норме — номенклатура или заказ? Предлагаю: номенклатура — источник, заказ — переопределение с бейджем. Альтернатива «заказ всегда копия шаблона» оставляет сегодняшнюю дырку.
2. Нормы по размерам — правим по размерам или одной цифрой? Предлагаю показывать по размерам (как в номенклатуре) + кнопку «одна норма на все». Хранение в снимке остаётся одной нормой/шт, если правят одной цифрой.
3. Что делает «Подтянуть из номенклатуры» в шаблоне? Предлагаю переносить числа как стартовое значение (сегодня строка молча получает 1). Но истина всё равно у номенклатуры, шаблон — структура.
4. Правка параметров в производстве (AMENDMENT)? Предлагаю разрешить наравне с нормой: то же предупреждение, та же запись в журнал правок заказа.
